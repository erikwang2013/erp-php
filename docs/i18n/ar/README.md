## مقدمة المشروع

«نظام إدارة موارد المؤسسات المفتوح» (open-erp) هو **نظام ERP مفتوح المصدر ومتكامل الحزمة** موجَّه للمؤسسات الصغيرة والمتوسطة، ويغطي مجالات الأعمال الكاملة: الشراء/البيع/المخزون، والمحاسبة المالية، والتصنيع (BOM/MRP/الإبلاغ عن العمليات/حمل الطاقة)، وإدارة علاقات العملاء، وسير عمل الموافقات، والموارد البشرية، وإشعارات الرسائل، والتقارير المخصصة. الخلفية مبنية على webman v2 + MySQL 8.0 (بادئة الجداول `erp_`، ومفاتيح أساسية فريدة عالميًا بخوارزمية Snowflake)، وتوفّر لوحة الإدارة ثلاث تطبيقات: Angular 22 (`apps/angular/`)، وReact 19 + Vite (`apps/react/`)، وFlutter 3.x Web (`apps/flutter/`)؛ ويُكمّلها عميل أصلي للجوال بنظام HarmonyOS (`apps/harmonyos/`).

يعتمد النظام على **الدفع بالمستندات والترابط التلقائي** كتصميم أساسي: اعتماد المستندات التجارية يطلق تلقائيًا حركة المخزون وتوليد الذمم المدينة/الدائنة وتجميع التكلفة؛ ويسري سير عمل الموافقات وإشعارات الرسائل عبر جميع المستندات الرئيسية؛ ويحسب MRP متطلبات المواد بناءً على أوامر البيع وقائمة المواد BOM ويولّد مقترحات الشراء/الإنتاج، لتشكيل حلقة أعمال متكاملة من استلام أمر البيع إلى استلام الشراء، ومن جدولة الإنتاج إلى الإقفال المالي.

## وصف المشروع

- **حساب عشري دقيق**: تُعتمد القيم التجارية (المبالغ والكميات والأوزان) على حساب bcmath العشري، وتُخرَج التكلفة المتوسطة المرجّحة المتحركة وتسويات الذمم المدينة/الدائنة ومختلف التقارير بدقة نصية بلا أخطاء الفاصلة العائمة
- **خط أساس أمني بمستوى المؤسسات**: رمز JWT + تخويل على مستوى الدوال عبر RBAC، ودفاع متعمق (لوحة الطبقات L0–L12 + 35 كاشف هجمات + سلسلة 7 وسائط، تشمل XSS وحقن SQL وCSRF وتحديد المعدل وCSP)، وتشفير تخزين الحقول الحساسة وتشفير نقل الواجهات، وتدقيق كامل للعمليات
- **قدرات قابلة للتهيئة**: سير عمل موافقات متعدد العقد (مع لوحة مصمّم سير العمل المرئي)، ومحرك قوالب طباعة المستندات (عرض العناصر النائبة + إخراج PDF عبر dompdf + ملصقات QR)، واعتراض فوري لحد الائتمان للعميل، وتتبع أمامي/عكسي كامل لسلسلة الدفعات/الأرقام التسلسلية
- **قابلية تتبع البيانات**: كل حركة تجارية تُترك لها أثرًا سطرًا بسطر، وتمتد الدفعة والرقم التسلسلي عبر دورة الحياة الكاملة (إدخال ← صرف ← إخراج ← تتبع)، ويصل احتساب التكلفة إلى مستوى سطر المستند
- **نشر ميسَّر**: تشغيل بأمر واحد عبر Docker Compose v2 (MySQL/Redis/Elasticsearch)، كما يمكن التشغيل مباشرة محليًا بـ `composer install`
- **التدويل**: 13 لغة (zh/en/ja/ko/de/fr/es/pt/ru/ar/hi/bn/id)، بتغطية كاملة لرسائل الخلفية وواجهتي الإدارة Angular/React، مع تحميل القواميس الأمامية حسب اللغة عند الطلب، وREADME متاح بـ 12 لغة أخرى

## وحدات ERP

تدفق البيانات بين وحدات الأعمال:

- استلام الشراء ← إدخال تلقائي للمخزون (تكلفة المتوسط المتحرك المرجح) ← توليد ذمم دائنة تلقائيًا
- شحن المبيعات ← إخراج تلقائي من المخزون ← توليد ذمم مدينة تلقائيًا
- المقبوضات/المدفوعات ← تسوية الذمم المدينة/الدائنة ← تحديث دفتر اليومية
- مراجعة القيود ← تحديث تلقائي لدفتر الأستاذ العام (ملخص الحسابات) + دفتر الأستاذ التفصيلي (تسجيل كل معاملة)
- الميزانية العمومية ← توليد تلقائي من ملخص الأرصدة الختامية لدفتر الأستاذ
- قائمة التدفق النقدي ← توليد تلقائي من دفتر اليومية النقدية والبنكية (ثلاثة تصنيفات: تشغيلي/استثماري/تمويلي)
- سير عمل الموافقات ← إرسال مستندات الأعمال للموافقة ← تدفق متعدد العقد ← استدعاء النتيجة في وحدات الأعمال
- إشعارات الرسائل ← أحداث الموافقات/التنبيهات/النظام ← دفع فوري ← المستخدم يحدد كمقروء
- MRP ← بناءً على أوامر المبيعات + BOM ← حساب احتياجات المواد ← توليد اقتراحات شراء/إنتاج
- OMS ← استيراد طلبات متعددة القنوات ← حجز المخزون (ATP) ← إنشاء التنفيذ ← إرسال لمهام انتقاء/تغليف WMS
- WMS ← تجميع الموجات ← مهام انتقاء ← تأكيد الانتقاء ← اكتمال التغليف ← إطلاق شحنة TMS
- TMS ← مقارنة أسعار الشحن ← إنشاء الشحنة ← تأكيد الشحن (stockOut+AR) ← تتبع المسار اللوجستي ← التوقيع على الاستلام
- إدخال WMS ← إشعار ASN ← استلام ← فحص الجودة ← تأكيد الرفع للأرفف (stockIn+AP) ← تحديث المخزون
- RMA ← طلب إرجاع ← موافقة ← إدخال الإرجاع للمخزون ← استرداد المبلغ

- بعد تسجيل الخروج، يُدرج التوكن فوراً في القائمة السوداء

### 4. محرك البحث النصي الكامل (اختياري)

تُنجَز مزامنة الفهرس عبر `erikwang2013/webman-scout` (بعد إضافة خاصية `Searchable` إلى النموذج، يُزامَن الفهرس تلقائيًا عند الحفظ). ويدعم المحركَين **Elasticsearch** و**OpenSearch**، اختر أحدهما:

**① ثبّت العميل الموافق (يجب توافق حزمة Composer مع المشغّل، وإلا ظهر الخطأ "Please install the ... client")**

| المحرك | عميل Composer |
|---|---|
| Elasticsearch | `composer require elasticsearch/elasticsearch:^9.5` |
| OpenSearch | `composer require opensearch-project/opensearch-php:^2.0` |

**② اضبط `.env` لاختيار المشغّل**

```ini
# elasticsearch | opensearch (مطابق للعميل المثبَّت أعلاه)
SCOUT_DRIVER=opensearch
# بادئة اسم الفهرس / الشُّرَط / النسخ / حجم كتلة الدفعة / الحذف الناعم (مشتركة بين المحركين)
SCOUT_PREFIX=erp_
SCOUT_SHARDS=1
SCOUT_REPLICAS=0
SCOUT_CHUNK_SIZE=500
SCOUT_SOFT_DELETE=true
```

**③ إعداد الاتصال (يختلف موضع القراءة بين المحركين)**

- **Elasticsearch**: من `SCOUT_HOSTS` في `.env` (عُقَد متعددة مفصولة بفواصل، مثل `http://localhost:9200`)، اتصال مباشر بلا مصادقة؛
- **OpenSearch**: الصورة الرسمية تُفعّل إضافة الأمان افتراضيًا (TLS موقَّع ذاتيًا + مصادقة بحساب)، وتُقرأ من قسم `opensearch` في `config/scout.php` ولا تقرأ `SCOUT_HOSTS`:

  ```ini
  # .env
  SCOUT_OPENSEARCH_HOST=https://localhost:9200
  SCOUT_OPENSEARCH_USERNAME=admin
  SCOUT_OPENSEARCH_PASSWORD=كلمة المرور
  ```

  قسم `opensearch` في `config/scout.php` يستخدم افتراضيًا `ssl_verification=false` (شهادة موقَّعة ذاتيًا محليًا)؛ وفي الإنتاج يجب تغييرها إلى `true` مع ضبط الشهادة، ويُمنع تمامًا استخدام كلمات مرور ضعيفة.

> يتضمن Docker Compose في هذا المشروع Elasticsearch (خدمة `open-admin-es`): عند النشر عبر Docker اختر **مشغّل elasticsearch + عميل ES**؛ وعند استخدام حاوية OpenSearch خارجية/مستقلة اختر **مشغّل opensearch + opensearch-php**.
>
> **نطاق الفهرسة**: جميع النماذج الـ 224 في `app/model/` تحمل `Searchable`، وأي كتابة/حذف ناعم يُزامَن مع الفهرس عبر `ModelObserver`؛ ومنها 4 نماذج (AdminUser وCustomer وProduct وSupplier) تُعرّف `toSearchableArray()` بقائمة حقول مسموحة، وتدخل بقية النماذج الفهرس بالوضع الافتراضي (الصف كاملًا).
>
> **تعذّر المحرك لا يؤثر على كتابة الأعمال** (مُختبَر: بعد توجيه المشغّل إلى منفذ غير قابل للوصول يبقى `save()` ناجحًا، ولا يزيد سوى زمن انتهاء مهلة اتصال واحد) — محرك البحث مكوّن اختياري، ويمكن تشغيل كامل الأعمال بدونه.
>
> **ملاحظة النطاق**: يقتصر المشروع حاليًا على **مزامنة الفهرس** (مزامنة فورية عند الكتابة/الحذف)، ولا يوفّر واجهة بحث أو شاشة بحث؛ وعند الحاجة إلى البحث استدعِ واجهة الاستعلام في Scout بنفسك (تصفية صفحات القوائم في لوحة الإدارة تمر عبر استعلام `where` في الخلفية ولا تمر بمحرك البحث).

## مواصفات قاعدة البيانات

- **بادئة الجداول**: `erp_`
- **المفتاح الأساسي**: مفتاح أساسي `id BIGINT UNSIGNED NOT NULL` في جميع الجداول، **ممنوع AUTO_INCREMENT**
- **توليد المعرفات**: تولد معرفات المفاتيح الأساسية في طبقة التطبيق عبر `SnowflakeService::generate()`، فريدة موزعة
- **الحقول الإلزامية**: يجب أن يحتوي كل جدول على `id`, `created_at`, `updated_at`
- **الحذف الناعم**: الجداول التي تحتاج حذفًا ناعمًا تضيف `deleted_at DATETIME DEFAULT NULL`
- **الحقول الحساسة**: أرقام الهواتف والبريد الإلكتروني وأرقام الهوية وغيرها تُشفَّر وتُفكَّ تلقائيًا عبر إضافة `encryptable`، وتُخزن حقول قاعدة البيانات كـ `VARCHAR(500)` بنص مشفر

## مواصفات API

### وثائق API

يستخدم المشروع erikwang2013/apidoc-php لتوليد وثائق الواجهات تلقائيًا، افتح `/apidoc` لعرضها.

- واجهات الإدارة (Admin): 25 مجموعة وحدات، مع معاملات الطلب وهياكل الاستجابة الكاملة
- واجهات العميل (Service API): 3 مجموعات — المصادقة/التحقق/المنتجات
- جميع الواجهات موضحة برؤوس عامة: مصادقة JWT والتدويل وغيرها

### تنسيق الاستجابة الموحد

```json
{
    "code": 0,
    "message": "success",
    "data": {}
}
```

### أكواد أخطاء الأعمال

| كود الخطأ | المعنى | الوصف |
|-------|------|------|
| `0` | نجاح | |
| `400` | خطأ في معاملات الطلب | |
| `401` | غير مسجل دخول (رمز غير صالح أو منتهي) | |
| `403` | لا صلاحية / اعتراض أمني | فشل تفويض RBAC / كشف هجوم SecurityFilter |
| `404` | المورد غير موجود | |
| `422` | فشل التحقق من المعاملات | |
| `413` | حجم جسم الطلب كبير جدًا | تفعيل SecurityFilter، يتجاوز 10MB |
| `405` | طريقة الطلب غير مسموحة | تفعيل SecurityFilter، يسمح فقط GET/POST/PUT/DELETE/OPTIONS/HEAD |
| `415` | نوع الوسائط غير مدعوم | تفعيل SecurityFilter، Content-Type ليس JSON |
| `429` | الطلبات كثيرة جدًا | تفعيل RateLimit / قفل الحساب (5 محاولات فاشلة تقفل 15 دقيقة) |
| `500` | خطأ داخلي في الخادم | |

### التدويل

يتبدل الرأس `Accept-Language` اللغة تلقائيًا (zh-CN → الصينية، en → الإنجليزية)، والصينية هي الافتراضية.

### معالجة المعرفات

- **المعرفات في الطلب/الاستجابة**: تُشفَّر كسلاسل عبر hashids، دون كشف معرفات قاعدة البيانات الحقيقية
- **مسار الواجهة**: `GET /admin/v1/user/{hashid}` — `{id}` في المسار عبارة عن سلسلة hashid
- **تخزين قاعدة البيانات**: القيمة الأصلية BIGINT، مولدة عبر snowflake

### إصدارات API

يوضع إصدار API في مسار عنوان URL (مثل `/admin/v1/*` و`/api/v1/*` و`/open/v1/*`)، **ولا يحتاج العميل إلى أي رأس إصدار**:

- الواجهات العامة المُصدَّرة بإصدار تُربط مباشرة بفئة وحدة التحكم الخاصة بذلك الإصدار (`app/api/v1/controller/`)
- عند إضافة إصدار جديد يُسجَّل مجموعة مسارات `/api/vN` جديدة، وتوضع وحدات تحكم الإصدار في `app/api/vN/`
- أُزيل التحليل الديناميكي السابق عبر `v()` ووسيط رأس `ApiVersion`

### تحديد المعدل

خوارزمية نافذة منزلقة قائمة على Redis، افتراضيًا 60 مرة/دقيقة/IP/مسار. الواجهات الحساسة أكثر صرامة:
- تسجيل الدخول: 10 مرات/دقيقة
- التسجيل: 5 مرات/دقيقة (مغلق افتراضيًا، يتطلب تفعيل `REGISTRATION_ENABLED=1`)

تحتوي رؤوس الاستجابة على `X-RateLimit-Limit` و`X-RateLimit-Remaining` و`X-RateLimit-Reset`. عند تجاوز الحد تُرجع 429 مع `Retry-After`.

### معمارية الوسائط

وسائط عامة (`config/middleware.php`) تسري على جميع الطلبات وتُنفذ بالترتيب:

```
Cors (معالجة CORS الأولية + رؤوس الاستجابة)
  → SecurityFilter (تقييد طرق HTTP/حجم جسم الطلب/فحص Content-Type/اعتراض XSS/حقن SQL/اجتياز المسارات/حقن الأوامر/CSRF)
  → RateLimit (تحديد المعدل بنافذة منزلقة عبر Redis + قفل الحساب: 5 محاولات دخول فاشلة → قفل 15 دقيقة)
  → TracingId (معرّف تتبع كامل المسار)
```

وسائط مجموعة التوجيه: `/admin/v1` تحمل `AdminAuth (مصادقة JWT + قائمة سوداء) → AdminPermission (تفويض RBAC) → OperationLog (تسجيل تلقائي لـ POST/PUT/DELETE، مع كشف الجهة المصدر)`؛ و`/open/v1` تحمل `OpenApiAuth`؛ ورد نداء تتبع TMS يحمل `TrackingSignature`. وتُحلَّل اللغة عبر `app/common/I18n.php` من `Accept-Language`، و**ليست وسيطًا**.

`/health` و`/api/docs` و`/install` نقاط عامة، وتمر فقط عبر `Cors → SecurityFilter → RateLimit → TracingId`.

تعزيزات أمنية:
- **قفل الحساب**: 5 محاولات تسجيل دخول فاشلة متتالية تقفل الحساب 15 دقيقة، وتُرجع 429 خلال فترة القفل
- **حد الجلسات المتزامنة**: حتى 3 رموز صالحة لنفس المستخدم، عند التجاوز يُضاف أقدم رمز تلقائيًا للقائمة السوداء
- **security.txt**: `GET /.well-known/security.txt` يوفر معلومات الاتصال الأمني القياسية RFC 9116
- **إعداد Nginx الأمني**: راجع `nginx-security.conf` للحصول على مثال كامل لتعزيز أمان الوكيل العكسي

### المصادقة

يتطلب تسجيل الدخول والتسجيل التحقق عبر **كابتشا النقر** أولاً:

1. يطلب العميل `POST /api/v1/captcha/generate` للحصول على صورة كابتشا (PNG بصيغة base64) وقائمة النصوص الهدف
2. ينقر المستخدم مواقع النصوص المقابلة في الصورة بالترتيب، ويجمع إحداثيات النقر `[{x, y}, ...]`
3. عند تسجيل الدخول يرسل معه `captcha_key` و`clicks`، ويتحقق الخادم أولاً من الكابتشا ثم من بيانات الاعتماد

```http
POST /api/v1/auth/login
Content-Type: application/json

{
  "username": "admin",
  "password": "******",
  "captcha_key": "abc123...",
  "clicks": [{"x": 120, "y": 85}, {"x": 210, "y": 140}, {"x": 95, "y": 170}]
}
```

واجهات لوحة الإدارة اللاحقة تتطلب مصادقة JWT:

```http
Authorization: Bearer <token>
```

بعد نجاح تسجيل الدخول يُرجع access_token بصلاحية ساعتين، وrefresh_token بصلاحية 14 يومًا.

عند تسجيل الخروج يُضاف الرمز إلى قائمة Redis السوداء ولا يمكن إعادة استخدامه خلال صلاحيته. POST /admin/v1/profile/logout

### التأكيد الثانوي للعمليات الحساسة

تتطلب العمليات الحساسة مثل حذف المستخدمين والأدوار والصلاحيات إدخال `password` للمستخدم المسجل حاليًا في جسم الطلب لتأكيد الهوية ثانويًا:

```http
DELETE /admin/v1/user/{id}
Content-Type: application/json
Authorization: Bearer <token>

{ "password": "******" }
```

## معايير التطوير

- الاستشهاد بالوظائف/الفئات العامة بدون بادئة `\`، باستخدام `use` للاستيراد
- يجب أن تحتوي رؤوس جميع ملفات PHP على بيان حقوق النشر
- يجب أن تحتوي جميع ملفات الإعداد على تعليقات توضيحية بالصينية
- يجب توليد المفاتيح الأساسية لقاعدة البيانات عبر snowflake في طبقة التطبيق، ويُمنع التزايد التلقائي
- يجب تشفير/فك تشفير جميع المعرفات في معاملات واستجابات طبقة API عبر hashids
- يستخدم وسيط AdminPermission ذاكرة Redis لتخزين صلاحيات المستخدم (TTL=60s)، مما يزيل اختناق استعلامات N+1

## النشر

### Docker Compose (موصى به)

في جذر المشروع `docker-compose.yml`، ينسق 5 خدمات:

| الخدمة | الصورة | المنفذ |
|------|------|------|
| `nginx` | nginx:alpine | 80, 443 |
| `app` | مبنية من `Dockerfile` محلي | 8788 |
| `mysql` | mysql:8.0 | 3306 |
| `redis` | redis:7-alpine | 6379 |
| `elasticsearch` | elasticsearch:8.x | 9200 |

تُبنى صورة PHP عبر `Dockerfile`، الصورة الأساسية `php:8.3-cli`، مع تفعيل OPcache.

```bash
cp .env.docker .env
# استبدال المفاتيح المبدئية بقيم عشوائية (idempotent)
bash scripts/gen-env-keys.sh .env
docker compose up -d
```

### CI/CD

خط أنابيب التكامل المستمر في GitHub Actions: `.github/workflows/ci.yml`، بخمس مهام:

| المهمة | المحتوى |
|------|------|
| `php` (مصفوفة PHP 8.3 / 8.4، مع خدمتي MySQL 8 + Redis 7) | التحقق من composer وتدقيق الأمان ← `php -l` ← **PHPStan** (level 5 + baseline) ← **PHP CS Fixer** (dry-run) ← استيراد `install.sql` الكامل ← **PHPUnit** (يشمل حالات التكامل) ← جمع التغطية عبر pcov ← حدود التغطية (الإجمالي ≥ 4%، و`app/service` ≥ 10%، وتُشدَّد تدريجيًا) |
| `flutter` | `flutter analyze` + `flutter test` (`continue-on-error: true`، ويُشدَّد بعد استقرار البيئة) |
| `docs` | `bash scripts/doc-stats.sh --check`: يتحقق من مطابقة تعليقات `<!-- stats:key=value -->` في README وdocs مع الإحصاءات الفعلية في الكود المصدري (وحدات التحكم/الخدمات/النماذج/الجداول/الاختبارات)، وأي انحراف يُفشل المهمة |
| `e2e` | تشغيل خدمة webman الحقيقية ← فحص الصحة ← اختبار دخاني لمسارات HTTP الأساسية + تغطية واجهات الإدارة |
| `release` | بعد الدفع إلى `main` ونجاح المهام أعلاه، يُنشئ وسم patch+1 وينشر Release (انظر أدناه) |

> تغطية الفحص الساكن للواجهة: CI يشغّل Flutter فقط حاليًا؛ أما Angular/React (`tsc --noEmit`) وHarmonyOS (`hvigorw assembleHap`) فيجب تشغيلهما محليًا أو في مهام تُضاف لاحقًا.

### عملية الإصدار (زيادة الإصدار)

بعد الدفع إلى `main` ونجاح فحوص php / docs / e2e جميعًا، تُنشئ المهمة `release` في `ci.yml` تلقائيًا وسمًا جديدًا بزيادة **patch+1** عن أحدث وسم وتدفعه (`v1.1.4` → `v1.1.5`)، ثم تُنشئ GitHub Release بالاسم نفسه (`--generate-notes` يولّد وصف التغييرات تلقائيًا).

- **التحفيز**: الدفع إلى `main` فقط (طلبات PR لا تحفّز؛ ودفع الوسوم لا يطابق مرشّح الفرع فلا يُحفّز سير العمل هذا بشكل متكرر)
- **الصلاحية للتكرار (idempotent)**: عند وجود وسم أو release بالاسم نفسه على الطرف البعيد (CI متزامن / وسم يدوي) يُتخطى تلقائيًا دون خطأ
- **تجربة محلية**: `bash scripts/bump-version.sh --check` يطبع رقم الإصدار التالي (قراءة فقط، ولا يكتب إلى الطرف البعيد)

### النسخ الاحتياطي لقاعدة البيانات

مجلد `database/backup/`:

- `backup.sh` — نسخ mysqldump + gzip، تنظيف تلقائي للنسخ الأقدم من 30 يومًا
- `restore.sh` — استعادة تفاعلية، تعرض النسخ الاحتياطية المتاحة للاختيار

### إعداد Nginx الأمني

يرجى الرجوع إلى `nginx-security.conf` لتكوين تعزيز أمان الوكيل العكسي في نشر الإنتاج.
