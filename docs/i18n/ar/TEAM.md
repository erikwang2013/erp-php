## 2. تكوين الفريق

### 2.1 الفريق الأساسي (مقيم دائمًا، 5 أدوار)

| الدور | الوكيل الحالي المقابل | المسؤولية (لهذا المشروع) |
|------|-----------------|--------------------|
| **قائد المشروع Lead** | `planner` / `swarm/hierarchical-coordinator` | تحليل المتطلبات ← التوجيه ← القبول؛ صيانة قائمة مهام الوحدات الـ 22؛ تحديد نمط pipeline / fan-out / supervisor؛ ترحيل الرسائل بين الأدوار |
| **مهندس النظام المعماري** | `sparc/architecture` | تصميم بنية الجداول (163 جدولًا، schema مصدره الوحيد database/install.sql)؛ تدفقات البيانات عبر الوحدات (استلام الشراء←المخزون←المستحقات، شحن المبيعات←المستحقات←الإخراج وغيرها)؛ قرارات حدود تقسيم الخدمات المصغرة |
| **مطور الخلفية** | `core` / مخصص `backend-dev` | تنفيذ وحدات التحكم/الخدمات/النماذج؛ الالتزام بطبقات `app/service` وسلسلة الوسائط (Locale→Cors→SecurityFilter→RateLimit→TracingId→وسائط الأعمال) |
| **مهندس الاختبارات** | `testing/tdd-london-swarm` + `production-validator` | حالات PHPUnit أولًا (اختبارات حدود المحركات)؛ التحقق من الانحدار عبر الفروع الثلاثة؛ سد فجوات تغطية `tests/` |
| **مراجع الكود** | `consensus/security-manager` | PHPStan صفر إضافات على baseline، توافق CS-Fixer، فحص نمط الأمان من 18 طبقة؛ حراسة بوابة الجودة قبل التقديم |

### 2.2 الفريق المتخصص (يُستدعى حسب نوع المهمة، 4 أدوار)

| الدور | الوكيل الحالي المقابل | سيناريو التفعيل | المهام النموذجية |
|------|-----------------|----------|----------|
| **خبير محركات الأعمال** | مخصص `business-engineer` | الوحدات الخوارزمية مثل المالية/الرواتب/MRP | تقوية خوارزميات محرك القيد المزدوج ومحرك احتساب الرواتب ومحرك MRP ومعالجة حدودها (متطلب درجة A «الصناعية») |
| **مهندس الواجهة (Flutter)** | مخصص `frontend-flutter` | أي تغيير يمس `apps/flutter/` | صفحات لوحة إدارة الويب، حالات GetX، ربط ApiService/التصدير، صيانة الصفحات الـ 97 |
| **مهندس الواجهة (HarmonyOS)** | مخصص `frontend-harmonyos` | أي تغيير يمس `apps/harmonyos/` | صفحات ArkTS، تجديد الرمز دون إحساس، مواءمة مجموعة الوظائف مع Flutter (صيانة 34 صفحة) |
| **مهندس الأمان/DevOps** | `consensus/security-manager` + `performance-benchmarker` | التحصين الأمني والأداء والنشر | انحدار الحماية من 18 طبقة، الخدمات الفرعية Docker/gRPC، استرجاع الهجرات، القابلية للمراقبة، مؤشرات Prometheus |

### 2.3 الأدوار حسب الحاجة (تُفعّل بالمهام، دورا)

| الدور | الوكيل الحالي المقابل | شرط التفعيل |

## 3. أنماط التعاون

### 3.1 القواعد العامة (تبع CLAUDE.md في جذر المشروع)

- **SendMessage-First**: يتواصل الوكلاء مباشرة عبر SendMessage، دون استقصاء أو مشاركة حالة قابلة للتغيير؛
- **التسمية إلزامية**: يجب تسمية كل وكيل (`name: "role"`)؛
- **إطلاق واحد**: تُطلق المهام الفرعية المستقلة دفعة واحدة في الخلفية، ويتوقف Lead لانتظار النتيجة دون استقصاء الحالة؛
- **الرسالة إلزامية المحتوى**: يكتب كل prompt «بعد الإكمال أرسل SendMessage إلى من وبماذا».

### 3.2 ثلاث طوبولوجيات تنسيق

| النمط | التدفق | سيناريو الاستخدام |
|------|------|----------|
| **Pipeline** | Lead ← المهندس المعماري ← الخلفية ← الاختبار ← المراجعة | تطوير وظائف ذات تبعيات تسلسلية (وحدات جديدة، تدفقات بيانات عبر الوحدات) |
| **Fan-out** | Lead ← A, B, C ← تجميع Lead | أعمال متوازية مستقلة (صفحات متعددة، دراسة وحدات متعددة) |
| **Supervisor** | جولات متعددة Lead ↔ الأعضاء | أعمال معقدة تتطلب تنسيقًا مستمرًا (تقسيم الخدمات المصغرة، إعادة هيكلة واسعة) |

### 3.3 جدول توجيه المهام

| نوع المهمة | التنسيق | الأدوار المشاركة |
|----------|------|----------|
| وحدة/وظيفة جديدة (مثل تعميق DMS و BI) | pipeline | Lead ← مهندس معماري (تصميم الجداول) ← خلفية ← اختبار ← مراجعة |
| خوارزميات مستوى المحركات (قيد مزدوج/رواتب/MRP) | pipeline + TDD | Lead ← خبير محركات الأعمال (تصميم) ← اختبار (حالات الحدود أولًا) ← مراجعة |
| صفحات الواجهة (Flutter / HarmonyOS متوازيان) | fan-out | Lead ← واجهة ×2 + خلفية (مواءمة API) بالتوازي ← تجميع Lead |
| تدفقات البيانات عبر الوحدات (شراء←مخزون←مستحقات وغيرها) | pipeline | Lead ← مهندس معماري ← خلفية ← اختبار ← مراجعة |
| تقسيم الخدمات المصغرة / إعادة هيكلة واسعة | supervisor | جولات Lead ↔ مهندس معماري + خلفية + مراجعة |
| تخصصات الأمان/الأداء | حفر أحادي المسار | Lead ← مهندس أمان/DevOps ← مراجعة |
| إصلاح الأخطاء (ملف واحد / سطر أو سطران) | خارج الفريق | يعالجه Lead مباشرة، أو يكملها وكيل واحد |
| فروق الفروع الثلاثة / إصدار النسخ | pipeline | Lead ← منسق الإصدارات ← اختبار (انحدار عبر الفروع) ← مراجعة |

### 3.4 بوابة الجودة (إلزامية قبل التقديم، يحرسها المراجع)

```
phpunit            # 137 اختبارًا / 805 تأكيدًا خضراء بالكامل، الحالات الجديدة تُقدَّم مع التغيير
phpstan            # لا يُسمح بإضافة مشاكل خارج baseline
php-cs-fixer       # يمر --dry-run
composer audit     # لا ثغرات تبعيات عالية الخطورة
```

التغييرات التي تمس قاعدة البيانات يجب أن تمر بالمهندس المعماري (163 جدولًا، schema مصدره الوحيد database/install.sql)؛ والتغييرات التي تمس الواجهة يجب أن تشغّل `flutter analyze` الخاص بـ Flutter بنتيجة 0 error / 0 warning.

## 4. توصيات حجم الفريق

| شكل العمل | الحجم المقترح | الشرح |
|----------|----------|------|
| صيانة يومية / إصلاحات صغيرة | 1-2 أشخاص | يعالجه Lead مباشرة، تجنبًا للإفراط في التنسيق |
| تكرار وحدة واحدة | 3 أشخاص | Lead + خلفية + اختبار |
| وظيفة عبر الوحدات | 4-5 أشخاص | Lead + مهندس معماري + خلفية + اختبار + مراجعة |
| توازي الواجهتين | 4-5 أشخاص | Lead + Flutter + HarmonyOS + خلفية (API) + اختبار |
| مستوى المحركات / إعادة هيكلة معقدة | 5-7 أشخاص | ما سبق كاملًا + خبير محركات الأعمال أو أمان/DevOps |

> متوافق مع `.claude-flow/config.yaml` (`maxAgents: 15`، `hierarchical-mesh`، استراتيجية تنسيق `consensus`)، ولا تتجاوز المهمة الواحدة الحد الأقصى.

## 5. خطوات التنفيذ

1. **إكمال تعريفات الأدوار**: لدى `.claude/agents/` بالفعل planner / sparc / testing / swarm / consensus، وتنقص خمسة تعريفات: `business-engineer` و `frontend-flutter` و `frontend-harmonyos` و `researcher` و `edition-coordinator`؛ تُكتمل بإضافة ملف واحد لكل منها وفق تنسيق YAML/MD القائم؛
2. **تثبيت التوجيه**: اكتب جدول التوجيه في §3.3 إلى منطق routing في `.claude-flow/hooks`، ليجعل خطاف `UserPromptSubmit` يوزّع المهام تلقائيًا على الأدوار المقابلة؛
3. **تقسيم الذاكرة**: فُعّل `agentScopes` في `.claude-flow` (`defaultScope: project`)، ويُقترح الأرشفة في أربعة مجالات `backend / frontend / ops / security`، لتجنب تلويث سياق محركات المالية لمهام الواجهة؛
4. **تشغيل تجريبي**: اختر مهمة عبر الوحدات (مثل تعميق DMS أو تكرار لوحات BI) وشغّلها جولة كاملة وفق توجيه §3.3، وعدّل ووسّع بعد التحقق من سلسلة الرسائل والبوابة.
