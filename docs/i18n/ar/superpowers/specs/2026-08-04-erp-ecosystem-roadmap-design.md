## 2. الاستراتيجية العامة

```
شلال تسلسلي: P0 → P1 → P2 → P3
المهام الفرعية المستقلة داخل كل مرحلة يمكن دفعها بالتوازي
```

### 2.1 اختيار تقنية الواجهة

- **لوحة إدارة الويب**: Flutter Web، إعادة استخدام الكود الحالي في `apps/flutter`، بأسلوب لوحة إدارة الكمبيوتر، إدارة الحالة عبر GetX
- **الموبايل**: Flutter (iOS/Android)، يشارك الويب كود الأعمال في `apps/flutter/lib/app/`
- **HarmonyOS**: ArkTS، محاذاة لمجموعة وظائف Flutter

### 2.2 استراتيجية الخلفية

- **بمستوى صناعي** (فئة A): القيد المزدوج، حساب الرواتب، محرك MRP — خوارزميات مكتملة، معالجة حدودية كافية، جاهز للإنتاج
- **قابل للاستخدام أساسيًا** (فئة B): إدارة الجودة، نظام الإشعارات، لوحات BI — تنفيذ القواعد الأساسية، التكرار لاحقًا حسب الحاجة

## 4. P1 — عمق الأعمال (4-6 أسابيع)

> **الهدف**: ترقية الوحدات الأساسية من هيكل CRUD إلى محركات حساب أعمال حقيقية

### 4.1 محرك القيد المزدوج المالي (بمستوى صناعي)

```
app/service/finance/
├── DoubleEntryService.php        # التحقق من توازن المدين/الدائن + توليد القيود تلقائيًا
├── PeriodCloseService.php        # إقفال نهاية الفترة (ترحيل الأرباح/الخسائر وتكاليف الإقفال)
├── AccountBalanceService.php     # تجميع أرصدة الحسابات (شهريًا/ربع سنويًا/سنويًا)
├── ConsolidationService.php      # بيانات مالية موحدة بعملات متعددة (تحويل أسعار الصرف)
└── FinancialRatioService.php     # حساب تلقائي للنسب المالية

app/controller/finance/
├── PeriodCloseController.php     # عمليات إقفال نهاية الفترة
├── AccountBalanceController.php  # استعلام أرصدة الحسابات
└── FinancialRatioController.php  # استعلام تحليل النسب
```

**القواعد الأساسية**:
- فرض «لكل مدين دائن، والمدين والدائن متساويان دائمًا» عند حفظ السندات
- السندات المعتمدة غير قابلة للتعديل، تتطلب إقفالًا بالحبر الأحمر
- إقفال نهاية الفترة: أرصدة حسابات الأرباح/الخسائر ← أرباح العام، يدعم الإقفال متعدد الخطوات
- عملات متعددة: التحويل بسعر صرف نهاية الفترة، وحساب فروق الصرف تلقائيًا

### 4.2 محرك حساب الرواتب (بمستوى صناعي)

```
app/service/hr/
├── SalaryEngineService.php       # المحرك الرئيسي لحساب الرواتب
├── SocialInsuranceService.php    # حساب التأمين الاجتماعي (تقاعد/طبي/بطالة/إصابة عمل/ولادة)
├── HousingFundService.php        # حساب صندوق الإسكان
├── TaxCalculatorService.php      # حساب ضريبة الدخل بالمعدلات التصاعدية
└── BankPayrollService.php        # تصدير ملفات الدفع البنكي

app/controller/hr/
└── PayrollController.php         # حساب/صرف/استعلام الرواتب
```

**القواعد الأساسية**:
- حدود أساس التأمين الاجتماعي (تُعدل سنويًا في كل منطقة، قابلة للتكوين)
- أساس صندوق الإسكان + نسبة الاشتراك (5%-12%، قابلة للتكوين)
- جدول معدلات ضريبة الدخل التصاعدية (3%-45%، تسوية سنوية شاملة)
- تنسيق الدفع البنكي: دعم البنوك الرئيسية ICBC/BOC/CCB/CMB وغيرها
- توليد قسائم الرواتب (تشمل جميع التفاصيل)

### 4.3 محرك MRP (بمستوى صناعي)

```
app/service/manufacturing/
├── MrpEngineService.php           # المحرك الرئيسي لعمليات MRP
├── DemandForecastService.php      # تجميع الطلب (أوامر + تنبؤ + مخزون أمان)
├── NetRequirementService.php      # حساب صافي الاحتياج (إجمالي الطلب - في المخزون - في الطريق)
├── BomExplosionService.php        # توسيع BOM (طبقة بطبقة حتى المواد الخام)
└── OrderSuggestionService.php     # توليد الأوامر المقترحة (شراء/إنتاج/تعاقد خارجي)

app/model/
├── MfgMrpRunLog.php              # سجلات عمليات MRP
└── MfgOrderSuggestion.php        # الأوامر المقترحة
```

**القواعد الأساسية**:
- توسيع BOM طبقة بطبقة، مع مراعاة معدل الهدر
- صافي الاحتياج = إجمالي الطلب - المخزون الحالي - المخزون في الطريق + الكميات المخصصة + مخزون الأمان
- رمز الطبقة المنخفضة (LLC) يضمن حساب المادة نفسها مرة واحدة فقط
- استنتاج تاريخ أمر الاقتراح بالمدة الزمنية التمهيدية
- قواعد الدفعات: دفعة ثابتة/دفعة اقتصادية/حسب الحاجة

## 12. ما لا يُنفَّذ (استبعاد صريح)

- ❌ لا إدخال لتقسيم الخدمات المصغرة — البنية الأحادية الحالية كافية، والمنطق المعقد يُحصر عبر طبقة Service
- ❌ لا إدخال لـ Kubernetes — Docker Compose يكفي للحجم الحالي
- ❌ لا وظائف AI/ML — خارج خارطة طريق MVP
- ❌ لا تطوير تطبيقات iOS/Android أصلية مستقلة — تغطية Flutter عبر المنصات كافية
- ❌ لا إدخال لـ GraphQL — واجهات RESTful كافية، واستراتيجية إصدارات API ناضجة
- ❌ لا توقيع إلكتروني/تكامل أجهزة WMS (PDA/ماسح باركود) — على مستوى البرمجيات فقط
