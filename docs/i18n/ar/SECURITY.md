## 1. بانوراما الدفاع المتعمق

يعتمد النظام نموذج دفاع متعمق من 7 طبقات، يفلتر الطلبات الخبيثة طبقة تلو الأخرى من الخارج إلى الداخل، لضمان أنه عند تعطل أي طبقة مفردة تبقى خطوط دفاع لاحقة تعمل كشبكة أمان.

سلسلة الوسائط بأكملها تُنفَّذ بالترتيب التالي (انظر `config/middleware.php`):

```
الطلب → Cors → SecurityFilter → RateLimit → [وسائط مجموعة التوجيه: AdminAuth → AdminPermission → OperationLog] → Controller
```

| الطبقة | الوسيط/الآلية | هدف الحماية |
|----|--------|---------|
| 1 | SecurityFilter | اعتراض XSS / حقن SQL / اجتياز المسار / حقن الأوامر / هجمات CSRF |
| 2 | Cors | أمان عبر النطاقات + حقن رؤوس الاستجابة الأمنية |
| 3 | RateLimit | تحديد معدل Redis بنافذة منزلقة، لمنع القوة الغاشمة |
| 4 | AdminAuth | مصادقة JWT + تسجيل خروج بالقائمة السوداء |
| 5 | AdminPermission | تفويض RBAC بدقة method.path |
| 6 | OperationLog | تدقيق العمليات + تتبع جهة المصدر |
| 7 | تشفير البيانات | إخفاء المعرفات Hashids + تشفير قاعدة البيانات Encryptable + تشفير النقل EncryptionService |

طبقات الواجهة الثلاث (Flutter) لديها أيضًا تحقق مستقل من المدخلات، ولا تثق الخلفية بأي طبقة، فكل طبقة تدافع بشكل مستقل.

## 2. محرك كشف الهجمات

### 2.0 تقييد طرق HTTP

يتحقق SecurityFilter من طريقة HTTP قبل كل عمليات كشف الهجمات، ولا يسمح إلا بالطرق القياسية التالية:

```
GET, POST, PUT, DELETE, OPTIONS, HEAD
```

الطرق غير القياسية (مثل TRACE وCONNECT وPATCH والطرق المخصصة وغيرها) تُرجع مباشرة **405 Method Not Allowed**، بجسم HTML فارغ، دون الدخول في كشف الهجمات أو منطق الأعمال اللاحق.

هذا هو خط الدفاع الأول في الدفاع المتعمق، ويمنع بفعالية:
- هجمات التتبع عبر المواقع TRACE (XST)
- إساءة استخدام النفق الوكيل CONNECT
- استطلاع طرق WebDAV غير القياسية
- تعداد طرق HTTP من قبل الماسحات الآلية

### 2.1 XSS النصوص البرمجية عبر المواقع

جميع التعبيرات النمطية من `SecurityFilter::PATTERNS['XSS']`، والمطابقة غير حساسة لحالة الأحرف.

| نمط الكشف | التعبير النمطي | الهجوم المُدافَع عنه |
|----------|------|-----------|
| وسوم البرامج النصية | `<\s*\/?\s*s\s*c\s*r\s*i\s*p\s*t\b` | `<script>`, `<script >`, `< script>` وغيرها من الأشكال بمسافات |
| خصائص الأحداث | `\bon\w+\s*=\s*[\"\']?\s*(?:javascript\|vbscript):` | `onclick="javascript:..."` وغيرها من الأحداث المضمنة |
| البروتوكولات الزائفة JS | `(?:javascript\|vbscript)\s*:\s*(?:[^\s]*\s*)?(?:eval\|alert\|prompt\|confirm\|document\.cookie\|location\s*=)` | `javascript:eval(...)`, `javascript:alert(1)` وغيرها |
| XSS عبر Data URI | `data\s*:\s*text\s*\/\s*html\s*(?:;base64)?\s*,` | `data:text/html,<script>`, `data:text/html;base64,...` وغيرها |
| حقن القوالب | `\{\{.*?\}\}` | حقن قوالب الخادم/Angular/Vue مثل `{{constructor}}` و`{{7*7}}` |

### 2.2 حقن SQL

| نمط الكشف | التعبير النمطي | الهجوم المُدافَع عنه |
|----------|------|-----------|
| استعلام UNION | `\bUNION\s+(?:ALL\s+)?SELECT\b` | `UNION SELECT`, `UNION ALL SELECT` لسحب قاعدة البيانات |
| حقن OR الدائم الصدق | `(?:[\"\']\s*OR\s+[\"\']?\s*\d+\s*=\s*\d+\|[\"\']\s*OR\s+[\"\']?1[\"\']?\s*=\s*[\"\']?1)` | `' OR 1=1--`, `" OR '1'='1'` |
| تدمير بنية الجداول | `\b(?:DROP\|ALTER\|TRUNCATE)\s+(?:TABLE\|DATABASE\|INDEX\|VIEW)\b` | `DROP TABLE users`, `TRUNCATE TABLE logs` |
| استدعاء الإجراءات المخزنة | `\b(?:xp_cmdshell\|sp_executesql\|sp_addsrvrolemember)\b` | تنفيذ أوامر إجراءات MSSQL الممتدة المخزنة |
| استطلاع البيانات الوصفية | `\b(?:INFORMATION_SCHEMA\|sys\.(?:tables\|columns\|databases)\|pg_class\|sqlite_master\|mysql\.(?:user\|db))\b` | استطلاع بنية قواعد MySQL/PG/SQLite/MSSQL |
| تجاوز التعليقات | `(?:[\"\'])\s*(?:--\|#)\s*[\"\']?\s*(?:OR\|AND\|SELECT\|INSERT\|UPDATE\|DELETE\|DROP)` | تجاوز التعليقات `'-- OR SELECT`, `'# AND UPDATE` |

### 2.3 اجتياز المسار

| نمط الكشف | التعبير النمطي | الهجوم المُدافَع عنه |
|----------|------|-----------|
| الرجوع للخلف في الدلائل | `\.\.[\/\\\\]{2,}` | `../`, `..\`, `....//` رجوع متعدد المستويات |
| استطلاع الملفات الحساسة | `\/(?:etc\/(?:passwd\|shadow\|hosts)\|proc\/self\|boot\.ini\|win\.ini\|WEB-INF\|\.env\|\.git\/)` | `/etc/passwd`, `/proc/self/environ`, `.env`, `.git/HEAD` وغيرها |
| القطع بالبايت الصفري | `%00` | `../../../etc/passwd%00.jpg` لتجاوز التحقق من الامتداد |

### 2.4 حقن الأوامر

| نمط الكشف | التعبير النمطي | الهجوم المُدافَع عنه |
|----------|------|-----------|
| أوامر الأنابيب/الفاصلة المنقوطة | `[;\|&]\s*(?:ls\|cat\|rm\|wget\|curl\|nc\|bash\|sh\|cmd\|powershell\|python\|perl)\b` | `;cat /etc/passwd`, `\|bash` |
| استبدال علامتي الاقتباس الخلفية | `` `[^`]*\b(?:cat\|ls\|id\|whoami\|pwd\|rm\|wget\|curl)\b[^`]*` `` | `` `cat /etc/passwd` `` |
| استبدال $() | `\$\(\s*(?:cat\|ls\|id\|whoami\|rm\|wget\|curl)\b` | `$(whoami)`, `$(cat flag)` |
| التنزيل عن بعد عبر أنبوب | `(?:wget\|curl)\s+.*(?:\b-o\b\|\b-O\b\|pipe\|bash\|python).*\bhttps?:\/\/` | `wget URL -O - \| bash`, `curl URL \| python` |

### 2.5 CSRF التزوير عبر المواقع

منطق التحقق منفذ في `SecurityFilter::checkCsrf()`:

```php
// التحقق يفعَّل فقط لـ POST/PUT/DELETE
// ترويسة Origin و Referer فارغتان → تمرير (عملاء غير المتصفح)
// Origin غير فارغ → تحليل نطاق Origin ومقارنته بـ Host
```

قواعد المقارنة:
- إزالة بادئة `www.` من Host ثم مقارنة دقيقة مع نطاق Origin
- إذا كان Host نطاقًا أبويًا لـ Origin (مثل `Origin: app.example.com`, `Host: example.com` — تفعيل `str_contains($originHost, '.' . $hostOnly)`) → تمرير
- لا تطابق دقيق ولا نطاق فرعي → إرجاع 403، حكم بهجوم CSRF

ملاحظة: عملاء غير المتصفح (مثل curl بدون Origin/Referer) يمررون مباشرة، وحماية CSRF فعّالة فقط في بيئة المتصفح.

### 2.6 رفع الملفات الخبيثة

| نمط الكشف | التعبير النمطي | الهجوم المُدافَع عنه |
|----------|------|-----------|
| تمويه الامتداد المزدوج | `\.(?:php\d?\|phtml\|phar\|cgi\|pl\|py\|jsp\|asp)x?\.(?:png\|jpg\|gif\|pdf)` | `shell.php.png`, `shell.phar.jpg` لتجاوز القائمة البيضاء |
| امتداد PHP | `\.php\s*$/m` | تمرير مسار `.php` مباشرة في معاملات الطلب |

## 3. تصعيد الهجوم والقائمة السوداء للـ IP

يحتوي SecurityFilter على آلية تصعيد هجمات مدمجة لمنع نفس الـ IP من مواصلة فحص الهجمات.

### عملية التصعيد

```
الضربة الأولى للفحص → Redis INCR security_escalate:{ip} = 1, TTL=60s
الضربة الثانية للفحص → INCR → 2
...
الضربة الخامسة للفحص → INCR → 5
    → تفعيل الحظر: SETEX security_ban:{ip} 900 1
    → مسح العدّاد: DEL security_escalate:{ip}
    → كتابة سجل أمني: [SECURITY] IP banned 15min
```

### السلوك أثناء الحظر

كل طلب يتحقق أولًا من `isBanned()` عند دخول SecurityFilter:

```php
if (Redis::get("security_ban:{$ip}")) {
    return response('<h1>403 Forbidden</h1>', 403);
}
```

الـ IP المحظور تُرجع جميع طلباته (بما فيها المشروعة) 403 مباشرة خلال 15 دقيقة، متجاوزة كل منطق الأعمال اللاحق.

### ثوابت الإعداد

| الثابت | القيمة | المعنى |
|------|-----|------|
| ESCALATE_LIMIT | 5 | عتبة عدد التنشيطات خلال نافذة 60 ثانية |
| ESCALATE_WINDOW | 60 | نافذة العدّاد (ثوانٍ) |
| BAN_DURATION | 900 | مدة القائمة السوداء (ثوانٍ)، أي 15 دقيقة |

### السجل الأمني

موقع الملف: `runtime/logs/security.log`

مثال على تنسيق السجل:
```
2026-05-20 14:32:11 [SECURITY] XSS attack blocked | IP: 192.168.1.100 | Path: /admin/user | Field: body.username | Source: body | Payload: <script>alert(1)</script>
2026-05-20 14:32:15 [SECURITY] IP banned 15min | IP: 192.168.1.100 | Triggers: 5
```

### حد حجم جسم الطلب

`Content-Length > 10MB` يُرجع مباشرة 413 Payload Too Large، لمنع هجمات DoS بجسم طلب ضخم.

### التحقق من Content-Type

طلبات POST/PUT **يجب** أن تعلن `Content-Type` كـ `application/json` أو `application/x-www-form-urlencoded`، وإلا تُرجع 415 Unsupported Media Type. طلبات رفع الملفات (التي تحمل حقل file) تتجاوز هذا الفحص.

## 4. رؤوس الاستجابة الأمنية

تُحقن جميع الرؤوس في وسيط `Cors`، عبر `$response->withHeaders()` على كل استجابة.

| الرأس | القيمة | الوظيفة |
|----|-----|------|
| Access-Control-Allow-Origin | `*` | السماح بأي مصدر عبر النطاقات (سيناريو لوحة إدارة الشبكة الداخلية) |
| Access-Control-Allow-Methods | `GET,POST,PUT,DELETE,OPTIONS` | مجموعة الطرق المسموحة |
| Access-Control-Allow-Headers | `Authorization,Content-Type,API-Version` | الرؤوس المخصصة المسموحة |
| Access-Control-Max-Age | `86400` | تخزين طلب ما قبل الفحص 24 ساعة |
| X-Content-Type-Options | `nosniff` | منع تخمين نوع MIME في المتصفح |
| X-Frame-Options | `DENY` | منع كل التضمين عبر iframe، لمنع اختطاف النقر |
| X-XSS-Protection | `1; mode=block` | تفعيل فلتر XSS المدمج في المتصفح وحجب عرض الصفحة |
| Referrer-Policy | `strict-origin-when-cross-origin` | إرسال URL كامل لنفس الأصل، والنطاق فقط عبر الأصول |
| Permissions-Policy | `camera=(), microphone=(), geolocation=()` | تعطيل واجهات الكاميرا/الميكروفون/الموقع في الموقع كله |

طلبات OPTIONS لما قبل الفحص تُرجع مباشرة 204 بجسم فارغ، دون الدخول في سلسلة الوسائط اللاحقة.

### 4.2 Content-Security-Policy (CSP)

يُحقن مع بقية الرؤوس الأمنية في وسيط Cors، ويوفر دفاعًا عميقًا يقيّد مصادر الموارد التي يمكن للمتصفح تحميلها وتنفيذها.

| الرأس | القيمة | الوظيفة |
|----|-----|------|
| Content-Security-Policy | `default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` | تقييد مصادر البرامج النصية/الأنماط/الصور/الاتصالات/الأطر/النماذج وغيرها |
| X-Permitted-Cross-Domain-Policies | `none` | منع تحميل ملفات السياسات عبر النطاقات من Adobe Flash/PDF وغيرها |

نقاط سياسة CSP:
- `default-src 'self'`: السماح افتراضيًا بمصادر نفس الأصل فقط
- `script-src 'self' 'unsafe-inline' 'unsafe-eval'`: السماح ببرامج نفس الأصل + برامج مضمنة (ضرورية لـ Flutter Web) + eval (ضروري لتصحيح Flutter Web)
- `frame-ancestors 'none'`: منع التضمين في أي صفحة عبر iframe، حماية مزدوجة مع X-Frame-Options: DENY
- `base-uri 'self'`: تقييد وسم `<base>` على نفس الأصل فقط
- `form-action 'self'`: تقييد إرسال النماذج إلى نفس الأصل فقط

## 5. استراتيجية تحديد المعدل

### الخوارزمية

نافذة منزلقة عبر Redis Sorted Set + نص Lua ذري، العمليات الرئيسية:

```lua
-- 1. تنظيف السجلات القديمة خارج النافذة
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, windowStart)
-- 2. فحص عدد النافذة الحالية
local count = redis.call('ZCARD', KEYS[1])
-- 3. إذا تجاوز الحد أرجع {0, count}، وإلا ZADD وأرجع {1, count+1}
if count >= limit then return {0, count} end
redis.call('ZADD', KEYS[1], now, now . '.' . random)  -- لاحقة عشوائية لمنع الكتابة الفوقية في نفس المللي ثانية
redis.call('EXPIRE', KEYS[1], window + 10)
```

يُتنفَّذ نص Lua على خادم Redis في خيط واحد، **ذري بطبيعته**، ويلغي حالة السباق TOCTOU (Time-of-check to Time-of-use).

### إعدادات تحديد المعدل

| المسار | الحد | النافذة | السيناريو |
|------|------|------|------|
| الافتراضي (كل المسارات) | 60 مرة/دقيقة | 60s | API عام |
| `/api/auth/login` | 10 مرات/دقيقة | 60s | تسجيل الدخول (منع القوة الغاشمة) |
| `/api/auth/register` | 5 مرات/دقيقة | 60s | التسجيل (منع التسجيل الجماعي؛ مغلق افتراضيًا، يُفتح بـ `REGISTRATION_ENABLED=1`) |

### رؤوس الاستجابة

عند تفعيل تحديد المعدل يُرجع HTTP 429 مع جسم JSON:
```json
{"code": 429, "message": "الطلبات كثيرة جدًا، يرجى المحاولة لاحقًا", "data": []}
```

جميع الاستجابات (بما فيها الطبيعية) تحمل الرؤوس التالية:

| الرأس | الوصف |
|----|------|
| X-RateLimit-Limit | الحد الأقصى للطلبات المسموحة في النافذة الحالية |
| X-RateLimit-Remaining | الطلبات المتبقية المتاحة في النافذة الحالية |
| X-RateLimit-Reset | طابع Unix لإعادة تعيين النافذة |
| Retry-After | يُحمل فقط عند التحديد، ثواني الانتظار المقترحة |

### استراتيجية التدهور

عند شذوذ Redis (انتهاء مهلة الاتصال، عدم التوفر وغيرها) يُفعَّل **fail-open**:

```php
try {
    $result = Redis::eval($lua, ...);
} catch (\Throwable $e) {
    return $handler($request); // Redis down, السماح بكل الطلبات
}
```

الأفضل فقدان حماية تحديد المعدل لفترة قصيرة من حجب طلبات الأعمال المشروعة.

### 5.4 آلية قفل الحساب

يضيف واجهة تسجيل الدخول، فوق تحديد المعدل، آلية **قفل الحساب** لمنع القوة الغاشمة الموجهة لمستخدم محدد.

**عملية القفل**:

```
فشل تسجيل الدخول → Redis INCR account_lockout:{userId} TTL=900s
5 فشلات متتالية → Redis SETEX account_locked:{userId} 900 1
            → إرجاع 429 "تم قفل الحساب، يرجى المحاولة بعد 15 دقيقة"
            → مسح العدّاد: DEL account_lockout:{userId}
```

**السلوك أثناء القفل**:

أثناء القفل تُرجع جميع طلبات تسجيل الدخول 429 مباشرة، دون التحقق من كلمة المرور، مانعة تمامًا محاولات القوة الغاشمة.

**ثوابت الإعداد**:

| الثابت | القيمة | المعنى |
|------|-----|------|
| MAX_LOGIN_ATTEMPTS | 5 | الحد الأقصى للفشل المتتالي |
| LOCKOUT_DURATION | 900 | مدة القفل (ثوانٍ)، أي 15 دقيقة |

ملاحظة: قفل الحساب مبني على `userId` وليس الـ IP، لذا لا يستطيع المهاجم تجاوز القفل بتغيير الـ IP. مع تحديد معدل الـ IP (10/دقيقة) يشكلان حماية مزدوجة:
- مستوى الـ IP: تحديد 10/دقيقة يمنع القوة الغاشمة الموزعة
- مستوى الحساب: قفل بعد 5 فشلات يمنع القوة الغاشمة الموجهة

## 6. المصادقة والتفويض

### 6.1 مصادقة JWT

منفذة في وسيط AdminAuth، مركبة على مجموعات التوجيه التي تحتاج المصادقة.

**إعدادات المعاملات** (`config/plugin/erikwang2013/jwt/jwt`، يُحقن عبر `.env`):

| المعامل | القيمة | الوصف |
|------|-----|------|
| الخوارزمية | HS256 | توقيع متماثل HMAC-SHA256 |
| المفتاح | `JWT_SECRET` | يُحقن عبر متغير بيئة، يجب تغييره في الإنتاج |
| TTL لـ access_token | 7200s (2h) | `JWT_TTL` |
| TTL لـ refresh_token | 1209600s (14d) | `JWT_REFRESH_TTL` |
| المُصدر | `open-admin` | `JWT_ISSUER` |
| الجمهور | `open-admin` | `JWT_AUDIENCE` |

**استخراج Token**: من رأس `Authorization: Bearer <token>`، بحذف بادئة `Bearer ` للحصول على JWT الأصلي.

**عملية المصادقة**:
1. token فارغ → 401 مباشرة `{"code": 401, "message": "غير مسجل الدخول"}`
2. فحص القائمة السوداء في Redis `jwt_blacklist:{md5(token)}` → إصابة → 401 `Token منتهي الصلاحية، يرجى إعادة تسجيل الدخول`
3. فك ترميز JWT → فشل (انتهاء الصلاحية/عدم تطابق التوقيع) → 401 `Token منتهي أو غير صالح`
4. نجاح → حقن `$request->adminId` و`$request->adminUsername`

**آلية القائمة السوداء**: عند تسجيل خروج المستخدم، يُكتب `md5(token)` في Redis بـ TTL يساوي المدة المتبقية لصلاحية JWT. عند عطل Redis يُتخطى فحص القائمة السوداء (fail-open)، عندها يمكن استخدام الـ Token المسجل خروجه لفترة قصيرة، لكن الصلاحية القصيرة لـ JWT نفسه (2h) تعمل كشبكة أمان.

### 6.2 تقييد الجلسات المتزامنة

لمنع إساءة استخدام Token مسرب عبر أجهزة متعددة، يقيّد النظام عدد Tokens الصالحة التي يحملها نفس المستخدم في وقت واحد.

**منطق التقييد**:

```
نجاح تسجيل الدخول → إصدار Token جديد
         → الاستعلام عن عدد Tokens الصالحة للمستخدم الحالي: Redis SCARD user_tokens:{userId}
         → إذا كان العدد >= 3 (MAX_CONCURRENT_SESSIONS):
            → الترتيب تصاعديًا حسب وقت الإنشاء، إزالة الأقدم:
              Redis SREM user_tokens:{userId} <oldest_token_id>
              Redis SETEX jwt_blacklist:{md5(oldest_token)} TTL remaining
         → إضافة الـ Token الجديد إلى المجموعة: Redis SADD user_tokens:{userId} <new_token_id>
            Redis SET user_token:{token_id} {userId} EX {TTL}
```

**ثوابت الإعداد**:

| الثابت | القيمة | المعنى |
|------|-----|------|
| MAX_CONCURRENT_SESSIONS | 3 | الحد الأقصى لـ Tokens المتزامنة لنفس المستخدم |

**سيناريو الطرد**: عندما يسجل المستخدم من الجهاز الرابع، يُضاف Token الجهاز الأول قسرًا إلى القائمة السوداء، وتُعيد طلباته اللاحقة 401 "Token منتهي الصلاحية، يرجى إعادة تسجيل الدخول".

عند تسجيل الخروج، يُزال الـ Token الحالي من المجموعة. عند انتهاء صلاحية الـ Token طبيعيًا، يزول مفتاح Redis تلقائيًا، ويتقلص عدد أعضاء المجموعة.

### 6.3 نموذج صلاحيات RBAC

منفذ في وسيط AdminPermission.

**نموذج البيانات**: ربط ثلاثي المستويات User -> Role -> Permission

- `erp_admin_user` (جدول المستخدمين)
- `erp_admin_user_role` (جدول ربط المستخدم-الدور)
- `erp_admin_role` (جدول الأدوار)
- `erp_admin_role_permission` (جدول ربط الدور-الصلاحية)
- `erp_admin_permission` (جدول الصلاحيات)

**أنواع الصلاحيات**:
| type | المعنى | مثال |
|------|------|------|
| 1 | صلاحية قائمة | التحكم في ظهور التنقل الجانبي |
| 2 | صلاحية زر | التحكم في أزرار العمليات داخل الصفحة (إضافة/تعديل/حذف) |
| 3 | صلاحية API | التحكم في استدعاء واجهات الخلفية |

تنسيق معرف صلاحية API: `{method}.{path}`

مثال:
- `post.admin/user` — إنشاء مستخدم
- `put.admin/user` — تعديل مستخدم
- `delete.admin/user` — حذف مستخدم
- `get.admin/user` — عرض قائمة المستخدمين

**عملية التفويض**:
1. `$request->adminId` فارغ → تمرير (لم تُعد مجموعة التوجيه بمصادقة مسبقة)
2. الحصول على المستخدم ← الأدوار (تخطي الأدوار المعطلة `status=0`) ← قائمة الصلاحيات
3. المسؤول الفائق (`slug = '*'`) → تمرير مباشر
4. بناء `strtolower(method) . '.' . trim(path, '/')` ← مقارنة مع قائمة الصلاحيات
5. فشل المطابقة → 403 `{"code": 403, "message": "لا صلاحية للوصول"}`

**تأكيد ثانٍ**: يوفر BaseController طريقة `confirmPassword()`، والعمليات الحساسة (حذف المستخدم، تصدير البيانات وغيرها) تتطلب إدخال كلمة المرور الحالية إضافيًا في طبقة وحدة التحكم، لمنع عمليات غير مصرح بها بعد اختطاف الجلسة.

## 7. سجلات التدقيق

### 7.1 سجل العمليات

يسجل وسيط OperationLog تلقائيًا سجلات العمليات لطلبات POST / PUT / DELETE. لا تُسجل طلبات GET.

**الحقول المسجلة**:

| الحقل | المصدر | الوصف |
|------|------|------|
| id | SnowflakeService::generate() | معرّف فريد عالمي |
| user_id | `$request->adminId` | معرّف المُنفِّذ، 0 إذا لم يكن مسجل الدخول |
| action | `$request->method()` | يعادل method |
| method | `$request->method()` | POST / PUT / DELETE |
| path | `$request->path()` | مسار الطلب |
| ip | `$request->getRealIp()` | الـ IP الحقيقي للعميل |
| source | detectSource() | منصة مصدر العميل |
| input | جسم الطلب (JSON بعد الإخفاء) | البيانات المقدمة في العملية |
| created_at | `date('Y-m-d H:i:s')` | وقت العملية |

**تصفية الحقول الحساسة**: عبور متكرر لجسم الطلب، قيمة الحقول التالية تُستبدل بـ `***`:

`password`, `old_password`, `new_password`, `new_password_confirmation`, `token`, `secret`, `access_token`, `refresh_token`

**كشف جهة المصدر** (`detectSource()`): حسب الأولوية:

1. قراءة الرأس المخصص `X-Client-Platform` أولًا (يعلنه العملاء الأصليون صراحة)
2. الانحدار إلى الاستدلال من سلسلة User-Agent (ترتيب كشف طريقة `detectSource()`):

| المنصة | كلمات مفتاحية في UA |
|------|----------|
| iPadOS | `iPad` |
| macOS | `Macintosh`, `Mac OS` |
| Windows | `Windows` |
| Linux | `Linux` |
| iOS | `iPhone`, `iOS`, `CFNetwork` |
| Android | `Android` |
| HarmonyOS | `HarmonyOS`, `OpenHarmony` |
| Web | القيمة الافتراضية الاحتياطية |

**تحمّل الأخطاء**: شذوذ كتابة السجل لا يحجب طلب الأعمال (`catch (\Throwable)` يبتلعه بصمت).

### 7.2 السجل الأمني

**موقع الملف**: `runtime/logs/security.log`

**المحتوى المسجل**:
- سجلات اعتراض الهجمات: فئة الهجوم، الـ IP، المسار، الحقل، المصدر، مقتطف payload (أول 200 حرف)
- إشعارات حظر الـ IP: الـ IP المحظور، عدد التنشيطات

صلاحيات السجل `FILE_APPEND | LOCK_EX`، لضمان كتابة آمنة مع التزامن.

## 8. حماية البيانات

يعتمد النظام استراتيجية حماية بيانات من ثلاث طبقات، تقابل ثلاث مراحل تدفق البيانات.

### 8.1 طبقة النقل — EncryptionService

يستخدم `EncryptionService` حزمة `erikwang2013/encryption` لتشفير وفك تشفير الحقول الحساسة في طلبات/استجابات API.

**التفاصيل التقنية**:
- الخوارزمية: `aes-256-cbc-hmac` (توقيع HMAC مدمج لمنع العبث)
- المفتاح: متغير البيئة `ENCRYPTION_KEY`، يُحاذى تلقائيًا إلى 32 بايت
- الاستخدام: نقل حقول مثل رقم الهاتف ورقم الهوية بين العميل وAPI

**طرق أدوات الإخفاء**:
- `maskPhone('13812341234')` → `138****1234`
- `maskEmail('abc@example.com')` → `a***@example.com` (اسم المستخدم أكثر من حرفين) أو `a**@example.com`

### 8.2 طبقة التخزين — Encryptable Cast

يستخدم نموذج `AdminUser` تحويل Eloquent `Erikwang2013\Encryptable\Encryptable`، الحقول المقابلة:

- `email` → تحويل إلى Encryptable، تشفير وفك تلقائي
- `phone` → تحويل إلى Encryptable، تشفير وفك تلقائي
- `id_card` → تحويل إلى Encryptable، تشفير وفك تلقائي

عند الكتابة إلى قاعدة البيانات يُشفر تلقائيًا إلى نص مشفر، وعند القراءة يُفك تلقائيًا إلى نص واضح. نوع عمود التخزين في قاعدة البيانات `VARCHAR(500)`، والنص المشفر يُخزن بصيغة base64.

**نظام المفاتيح**: يستخدم `ENCRYPTABLE_KEY` مستقلة عن تشفير طبقة النقل (`ENCRYPTION_KEY`)، تسريب مفتاح واحد لا يُسقط الطبقة الأخرى.

تدوير المفاتيح: يدعم متغير البيئة `ENCRYPTION_PREVIOUS_KEYS` قائمة مفاتيح تاريخية (مفصولة بفواصل)، عند قراءة البيانات القديمة تُحاول المفاتيح التاريخية فك التشفير، وعند الكتابة يُشفر بمفتاح تيار يستخدم المفتاح الحالي.

### 8.3 طبقة العرض — إخفاء المعرّفات وإخفاء البيانات

**إخفاء معرفات Hashids**: يستخدم `HashidsService` حزمة `erikwang2013/hashids`.

- تُرمَّز معرّفات BIGINT في قاعدة البيانات المرتجعة من API الخارجي إلى سلسلة hash (مثل `xK3mN9qR2pL7wV8b`)
- يمرر العميل سلسلة hash عند الطلب، وتفكها الخلفية تلقائيًا إلى المعرّف الأصلي
- ملح `HASHIDS_SALT` يُحقن عبر متغير بيئة، واختلاف الملح يغير نتائج الترميز وفك الترميز كليًا
- الحد الأدنى لطول hash 16 حرفًا، بمجموعة أحرف أبجدية رقمية من 62 حرفًا
- يوفر BaseController الطرق الملائمة `encodeId()`, `decodeId()`, `encodeIds()`

**إخفاء التصدير**: عند تصدير Excel/PDF (ExportController)، تُخفى الحقول الحساسة بشكل موحد:
- رقم الهاتف: `138****1234`
- البريد: `a***@example.com`
- رقم الهوية: تغطية كاملة بـ `********`

## 10. security.txt (RFC 9116)

يوفر النظام في `/.well-known/security.txt` نقطة نهاية بمعلومات الاتصال الأمنية المطابقة لمعيار RFC 9116، ليتسنى للباحثين الأمنيين إيجاد قناة الإبلاغ بسرعة عند اكتشاف ثغرات.

**طريقة الوصول**:

```
GET /.well-known/security.txt
```

**محتوى الاستجابة**:

```text
Contact: mailto:security@erik.xyz
Expires: 2027-05-20T00:00:00.000Z
Preferred-Languages: zh, en
Canonical: https://erik.xyz/.well-known/security.txt
Policy: https://erik.xyz/security-policy
```

**شرح الحقول**:

| الحقل | الوصف |
|------|------|
| Contact | وسيلة الإبلاغ عن الثغرات الأمنية |
| Expires | وقت انتهاء الملف، يتطلب تحديثًا دوريًا |
| Preferred-Languages | لغة التواصل المفضلة |
| Canonical | الـ URL الرسمي لهذا الملف |
| Policy | رابط سياسة الأمن/سياسة كشف الثغرات |

نقطة النهاية هذه لا تخضع لوسائط تحديد المعدل أو المصادقة، ويمكن لأي شخص الوصول إليها مباشرة.

## 11. إعدادات أمان Nginx

يوفر المشروع `docs/nginx-security.conf` كإعداد مرجعي لتقوية أمان الوكيل العكسي Nginx في بيئة الإنتاج.

**الإجراءات الأمنية المشتملة**:

| عنصر الإعداد | الوظيفة |
|--------|------|
| `server_tokens off` | إخفاء رقم إصدار Nginx |
| `client_max_body_size 10m` | تحديد حجم جسم الطلب، بالتنسيق مع SecurityFilter |
| `limit_req_zone` | تحديد تردد الطلبات على مستوى Nginx |
| `limit_conn_zone` | تحديد عدد الاتصالات المتزامنة |
| `add_header` رؤوس أمنية | إضافة رؤوس أمنية مثل X-XSS-Protection على مستوى Nginx |
| `if ($request_method)` | رفض طرق HTTP غير القياسية على مستوى Nginx |
| إعدادات SSL/TLS | إعدادات TLS 1.2/1.3 حديثة، تعطيل مجموعات التشفير الضعيفة |
| إخفاء رؤوس الخلفية | `proxy_hide_header` لإزالة رؤوس حساسة مثل إصدار webman |

**طريقة الاستخدام**: ادمج إعدادات `docs/nginx-security.conf` في كتلة server في Nginx لديك، مع ضبط النطاق ومسار الشهادة الفعليين.

### 12.2 القيود المعروفة

| القيد | نطاق التأثير | إجراءات التخفيف |
|------|---------|---------|
| حماية CSRF فعّالة للمتصفح فقط | عملاء غير المتصفح (curl, Postman, تطبيقات الجوال) يتجاوزون فحص Origin/Referer | عملاء غير المتصفح لا يتعرضون بطبيعتها لـ CSRF؛ الاعتماد على مصادقة JWT بدلًا من Cookies |
| عند عدم توفر Redis يتدهور تحديد المعدل والقائمة السوداء إلى fail-open | يستطيع المهاجم تجاوز تحديد المعدل والاعتراض عالي التردد | مراقبة توفر Redis مع تنبيهات؛ صلاحية JWT القصيرة كشبكة أمان |
| لا يوجد محرك WAF مستقل | يستخدم SecurityFilter مطابقة `@preg_match`، وليس محرك قواعد WAF متخصصًا | يُنصح في الإنتاج بتركيب Nginx ModSecurity أو Cloudflare WAF أمام النظام |
| JWT بلا حالة لا يمكن إبطاله بفعالية | لا يمكن سحب الـ Token قبل انتهاء صلاحيته من الخادم (خارج القائمة السوداء) | القائمة السوداء + TTL قصير 2h يقلل نافذة المخاطر |
| القائمة السوداء للـ IP في الذاكرة فقط | بعد إعادة تشغيل Redis تُفقد القائمة السوداء | مدة الحظر 15 دقيقة فقط، التأثير محدود |
| لا تحديد معدل خاص بنقاط نهاية المسؤول | واجهات المسؤول تشارك الواجهات العادية الحد الافتراضي 60/دقيقة | تردد عمليات المسؤول منخفض بطبيعته، لا حاجة للتمييز حاليًا |
| `@preg_match` يكتم الأخطاء | فشل صامت عند مدخلات تعبير نمطي مشوهة | يمكن إضافة مراقبة عبر `preg_last_error()`، غير منفذة حاليًا |
