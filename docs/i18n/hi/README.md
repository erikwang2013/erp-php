## परियोजना परिचय

open-erp छोटे और मध्यम उद्यमों के लिए बनाई गई एक **ओपन-सोर्स फुल-स्टैक ERP प्रणाली** है, जो क्रय-विक्रय-भंडार (क्रय/विक्रय/इन्वेंटरी), वित्तीय लेखांकन, विनिर्माण (BOM/MRP/प्रक्रिया रिपोर्टिंग/क्षमता भार), CRM, अनुमोदन वर्कफ़्लो, मानव संसाधन, संदेश अधिसूचना और कस्टम रिपोर्ट जैसे संपूर्ण व्यावसायिक क्षेत्रों को कवर करती है। बैकएंड webman v2 + MySQL 8.0 पर आधारित है (टेबल उपसर्ग `erp_`, Snowflake वैश्विक अद्वितीय प्राथमिक कुंजी); प्रशासन पक्ष तीन कार्यान्वयन प्रदान करता है — Angular 22 (`apps/angular/`), React 19 + Vite (`apps/react/`) और Flutter 3.x Web (`apps/flutter/`); मोबाइल पक्ष के लिए HarmonyOS नेटिव क्लाइंट (`apps/harmonyos/`) है।

प्रणाली का मुख्य डिज़ाइन **दस्तावेज़-चालित, स्वतः लिंकेज** है: व्यावसायिक दस्तावेज़ के अनुमोदन से स्वतः इन्वेंटरी परिवर्तन, प्राप्य/देय का सृजन और लागत संग्रहण ट्रिगर होता है; अनुमोदन वर्कफ़्लो और संदेश अधिसूचना सभी प्रमुख दस्तावेज़ों में व्याप्त हैं; MRP विक्रय आदेशों तथा BOM के आधार पर सामग्री आवश्यकता की गणना कर क्रय/उत्पादन सुझाव उत्पन्न करता है, जिससे विक्रय ऑर्डर प्राप्ति से क्रय प्राप्ति तक और उत्पादन शेड्यूलिंग से वित्तीय समापन तक का एंड-टू-एंड व्यावसायिक चक्र पूरा होता है।

## परियोजना विवरण

- **सटीक दशमलव गणना**: राशि, मात्रा, भार जैसे व्यावसायिक मान bcmath दशमलव गणना पर आधारित हैं; मूविंग वेटेड एवरेज लागत, प्राप्य/देय निपटान और सभी प्रकार के रिपोर्ट आउटपुट स्ट्रिंग परिशुद्धता में होते हैं, कोई फ़्लोटिंग-पॉइंट त्रुटि नहीं
- **एंटरप्राइज़-स्तरीय सुरक्षा आधाररेखा**: JWT टोकन + RBAC विधि-स्तरीय प्राधिकरण, गहन रक्षा (L0–L12 स्तरित पैनोरमा + 35 प्रकार के हमला डिटेक्टर + 7 परत मिडलवेयर श्रृंखला, XSS/SQL इंजेक्शन/CSRF/रेट लिमिट/CSP आदि), संवेदनशील फ़ील्ड का भंडारण एन्क्रिप्शन और इंटरफ़ेस ट्रांसमिशन एन्क्रिप्शन, ऑपरेशन ऑडिट की पूर्ण ट्रेसिंग
- **कॉन्फ़िगरेशन-आधारित क्षमताएँ**: बहु-नोड अनुमोदन वर्कफ़्लो (दृश्य प्रक्रिया डिज़ाइनर कैनवास सहित), दस्तावेज़ प्रिंट टेम्पलेट इंजन (प्लेसहोल्डर रेंडरिंग + dompdf से PDF + QR कोड लेबल), ग्राहक क्रेडिट सीमा की रीयल-टाइम रोक, बैच/सीरियल नंबर की पूर्ण-श्रृंखला आगे-पीछे ट्रेसिंग
- **डेटा ट्रेसबिलिटी**: व्यावसायिक प्रवाह की प्रत्येक प्रविष्टि दर्ज होती है, इन्वेंटरी बैच और सीरियल नंबर इनबाउंड→निकासी→आउटबाउंड→ट्रेसिंग के पूरे जीवनचक्र में व्याप्त हैं, लागत गणना दस्तावेज़ पंक्ति स्तर तक होती है
- **परिनियोजन-अनुकूल**: Docker Compose v2 से वन-क्लिक शुरुआत (MySQL/Redis/Elasticsearch), स्थानीय `composer install` से भी सीधे चलाया जा सकता है
- **अंतर्राष्ट्रीयकरण**: 13 भाषाएँ (zh/en/ja/ko/de/fr/es/pt/ru/ar/hi/bn/id), बैकएंड संदेश और Angular/React दोनों प्रशासन इंटरफ़ेस पूर्ण रूप से कवर, फ्रंटएंड शब्दकोश भाषा-अनुसार लेज़ी लोड, README में 12 भाषाओं के अतिरिक्त दस्तावेज़

## ERP मॉड्यूल

विभिन्न व्यावसायिक मॉड्यूलों के बीच डेटा प्रवाह:

- क्रय प्राप्ति → स्वतः इनबाउंड (मूविंग वेटेड एवरेज लागत गणना) → स्वतः देय उत्पन्न
- विक्रय डिलीवरी → स्वतः आउटबाउंड → स्वतः प्राप्य उत्पन्न
- प्राप्ति/भुगतान → प्राप्य/देय समायोजन → जर्नल अपडेट
- वाउचर अनुमोदन → स्वतः सामान्य खाता बही (खाता सारांश) + विवरण खाता बही (पंक्ति-दर-पंक्ति रिकॉर्ड) अपडेट
- बैलेंस शीट → सामान्य खाता बही के अंतिम शेष को स्वतः संकलित करके उत्पन्न
- कैश फ्लो स्टेटमेंट → नकद/बैंक जर्नल को स्वतः संकलित करके उत्पन्न (संचालन/निवेश/वित्तपोषण तीन श्रेणियां)
- अनुमोदन वर्कफ़्लो → व्यावसायिक दस्तावेज़ अनुमोदन हेतु सबमिट → बहु-नोड प्रवाह → अनुमोदन परिणाम व्यावसायिक मॉड्यूल को कॉलबैक
- संदेश अधिसूचना → अनुमोदन/अलर्ट/सिस्टम घटनाओं से ट्रिगर → रीयल-टाइम पुश → उपयोगकर्ता द्वारा पठित चिह्नित
- MRP → विक्रय आदेश + BOM पर आधारित → सामग्री आवश्यकता गणना → क्रय सुझाव/उत्पादन सुझाव उत्पन्न
- OMS → मल्टी-चैनल ऑर्डर आयात → स्टॉक रिज़र्वेशन (ATP) → फ़ुलफ़िलमेंट निर्माण → WMS पिकिंग/पैकिंग जारी
- WMS → वेव एकत्रीकरण → पिकिंग कार्य → पिकिंग पुष्टि → पैकिंग पूर्ण → TMS शिपमेंट ट्रिगर
- TMS → फ्रेट मूल्य तुलना → शिपमेंट निर्माण → डिलीवरी पुष्टि (stockOut+AR) → लॉजिस्टिक्स ट्रैकिंग → हस्ताक्षर प्राप्ति
- WMS इनबाउंड → ASN पूर्व-आगमन → प्राप्ति → गुणवत्ता निरीक्षण → पुटअवे पुष्टि (stockIn+AP) → स्टॉक अपडेट
- RMA → वापसी अनुरोध → अनुमोदन → वापसी इनबाउंड → रिफंड

## सिस्टम आर्किटेक्चर आरेख

> पूर्ण आकार देखने के लिए छवि पर क्लिक करें। आरेख अंग्रेज़ी नामों का उपयोग करते हैं, सिस्टम के सभी स्तरों के आर्किटेक्चर डिज़ाइन को पूर्ण और स्पष्ट रूप से प्रदर्शित करते हैं।

### सिस्टम टोपोलॉजी आर्किटेक्चर

![System Architecture](./diagrams/system-architecture-cn.svg)

**पाँच परतों वाला आर्किटेक्चर**: क्लाइंट परत → गेटवे एज परत (Nginx रिवर्स प्रॉक्सी) → एप्लिकेशन परत (webman v2 + मिडलवेयर श्रृंखला + प्रमाणीकरण/प्राधिकरण + व्यावसायिक तर्क + सामान्य सेवाएँ) → डेटा भंडारण परत (MySQL + Redis + Elasticsearch) → संचालन परत (CI/CD + Docker + Prometheus)

### व्यावसायिक डेटा प्रवाह आरेख

![Business Flowchart](./diagrams/business-flowchart-cn.svg)

**सात प्रमुख व्यावसायिक क्षेत्रों का अंतर्संबंध**: क्रय → इन्वेंटरी → विक्रय → वित्त मूल आपूर्ति श्रृंखला लूप बनाते हैं; ग्राहक संबंध प्रबंधन विक्रय को संचालित करता है; विनिर्माण MRP विक्रय आदेशों + सामग्री सूची के आधार पर क्रय योजना और उत्पादन योजना संचालित करता है; अनुमोदन वर्कफ़्लो, संदेश अधिसूचना, परियोजना प्रबंधन, मानव संसाधन समर्थन मॉड्यूल के रूप में पूरी प्रक्रिया में व्याप्त हैं।

### फ़ीचर मॉड्यूल अवलोकन

![Functional Modules](./diagrams/functional-modules-cn.svg)

**23 प्रमुख व्यावसायिक क्षेत्र, 227 डेटा तालिकाएँ, 159 कंट्रोलर**: प्रमाणीकरण सुरक्षा, डैशबोर्ड, सिस्टम प्रबंधन, सुरक्षा रक्षा, संचालन निगरानी, उत्पाद प्रबंधन, क्रय, विक्रय, इन्वेंटरी, वित्त (14 उप-मॉड्यूल), CRM (10 उप-मॉड्यूल), अनुमोदन वर्कफ़्लो, संदेश अधिसूचना, परियोजना प्रबंधन, मानव संसाधन, विनिर्माण (MRP), कस्टम रिपोर्ट, ऑर्डर प्रबंधन (OMS), वेयरहाउस प्रबंधन (WMS), परिवहन प्रबंधन (TMS), गुणवत्ता प्रबंधन (QMS), उपकरण प्रबंधन (EAM), दस्तावेज़ प्रबंधन (DMS), BI बोर्ड।

### अनुरोध जीवनचक्र

![Request Lifecycle](./diagrams/request-lifecycle-cn.svg)

**क्लाइंट से डेटाबेस तक संपूर्ण अनुरोध पथ**: क्लाइंट (Angular/React/Flutter/HarmonyOS) → Nginx SSL समाप्ति → क्रॉस-ओरिजिन हैंडलिंग → सुरक्षा फ़िल्टर → रेट लिमिट → [प्रशासन: JWT प्रमाणीकरण → RBAC अनुमति → ऑपरेशन लॉग] → कंट्रोलर → सेवा परत → मॉडल परत → कैश/डेटाबेस/खोज इंजन → JSON प्रतिक्रिया। आरेख में कैश हिट और कैश मिस दोनों पथ शामिल हैं। (API संस्करण अब URL पथ में समाहित है, कोई अलग सत्यापन चरण नहीं; भाषा `app/common/I18n.php` द्वारा `Accept-Language` से निर्धारित होती है।)

### सुरक्षा गहन रक्षा आर्किटेक्चर

![Security Architecture](./diagrams/security-architecture-cn.svg)

**गहन रक्षा पैनोरमा (L0–L12)**: L0 भौतिक नेटवर्क → L1 ट्रांसमिशन सुरक्षा → L2 HTTP सुरक्षा हेडर → L3 अनुरोध सत्यापन → L4 इनपुट सैनिटाइज़ेशन → L5 CSRF सुरक्षा → L6 रेट लिमिट → L7 प्रमाणीकरण (JWT+Captcha+ब्लैकलिस्ट+सत्र नियंत्रण) → L8 RBAC प्राधिकरण → L9 डेटा सुरक्षा (ट्रांसमिशन एन्क्रिप्शन+भंडारण एन्क्रिप्शन+ID ओबफस्केशन+डेटा मास्किंग) → L10 ऑडिट निगरानी → L11 अनुपालन प्रकटीकरण → L12 ऑब्ज़र्वेबिलिटी (X-Trace-Id वितरित ट्रेसिंग + व्यावसायिक मेट्रिक्स + ऑडिट संवर्धन)। निष्पादन योग्य श्रृंखला की 7 परत मिडलवेयर के लिए `docs/SECURITY.md` देखें; 35 प्रकार के हमला डिटेक्टर के लिए `config/plugin/erikwang2013/security-php/app.php` देखें।

## डिफ़ॉल्ट स्थानीय डोमेन

प्रोजेक्ट डिफ़ॉल्ट रूप से स्थानीय डोमेन **`http://erp.test`** का उपयोग करता है (Flutter क्लाइंट का डिफ़ॉल्ट API पता और बैकएंड Web प्रवेश बिंदु का अभिसमय; HarmonyOS क्लाइंट डिफ़ॉल्ट रूप से एमुलेटर होस्ट मशीन `http://10.0.2.2:8788` की ओर इशारा करता है)।

- **स्थानीय पहुँच**: hosts में एक पंक्ति `127.0.0.1 erp.test` जोड़ें, और Web सर्वर/रिवर्स प्रॉक्सी को बैकएंड लिसन पोर्ट पर इंगित करें (डिफ़ॉल्ट `8788`, `.env` की `APP_HTTP_PORT` देखें, इंस्टॉलेशन विज़ार्ड या `.env` में बदला जा सकता है; WebSocket डिफ़ॉल्ट `8282` ↔ `APP_WS_PORT`)।
- **परिनियोजन डोमेन बदलें**:
  - Flutter बिल्ड इंजेक्शन: `flutter build web --dart-define=API_BASE_URL=https://आपका-डोमेन`
  - HarmonyOS: `apps/harmonyos/entry/src/main/ets/utils/Config.ets` की `BASE_URL` संपादित करें (रीड-ओनली कॉन्स्टेंट, डिफ़ॉल्ट `http://10.0.2.2:8788`)
  - एमुलेटर डिबग के लिए अस्थायी रूप से `http://10.0.2.2:8788` पर वापस बदला जा सकता है (होस्ट मशीन तक पहुँच)
- सभी इंटरफ़ेस संस्करण पथ में रखे गए हैं (`/admin/v1`, `/api/v1`, `/open/v1`), क्लाइंट को केवल रूट पता कॉन्फ़िगर करना होता है।

### 4. फुल-टेक्स्ट सर्च इंजन (वैकल्पिक)

इंडेक्स सिंक `erikwang2013/webman-scout` से लागू होता है (मॉडल में `Searchable` trait जोड़ने पर सहेजते समय इंडेक्स स्वतः सिंक होता है)। **Elasticsearch** और **OpenSearch** दोनों इंजन समर्थित हैं, इनमें से एक चुनें:

**① संगत क्लाइंट इंस्टॉल करें (Composer पैकेज और ड्राइवर का मेल होना अनिवार्य, गलत इंस्टॉल पर "Please install the ... client" त्रुटि आएगी)**

| इंजन | Composer क्लाइंट |
|---|---|
| Elasticsearch | `composer require elasticsearch/elasticsearch:^9.5` |
| OpenSearch | `composer require opensearch-project/opensearch-php:^2.0` |

**② `.env` में ड्राइवर चुनें**

```ini
# elasticsearch | opensearch（与上面安装的客户端一致）
SCOUT_DRIVER=opensearch
# 索引名称前缀 / 分片 / 副本 / 批量块大小 / 软删除（两种引擎通用）
SCOUT_PREFIX=erp_
SCOUT_SHARDS=1
SCOUT_REPLICAS=0
SCOUT_CHUNK_SIZE=500
SCOUT_SOFT_DELETE=true
```

**③ कनेक्शन कॉन्फ़िगरेशन (दोनों इंजन इसे अलग-अलग स्थान से पढ़ते हैं)**

- **Elasticsearch**: `.env` की `SCOUT_HOSTS` (कई नोड अल्पविराम से अलग, जैसे `http://localhost:9200`), बिना प्रमाणीकरण सीधा कनेक्शन;
- **OpenSearch**: आधिकारिक इमेज डिफ़ॉल्ट रूप से सुरक्षा प्लगइन सक्षम करती है (स्व-हस्ताक्षरित TLS + खाता प्रमाणीकरण), यह `config/scout.php` के `opensearch` अनुभाग से पढ़ता है, `SCOUT_HOSTS` नहीं:

  ```ini
  # .env
  SCOUT_OPENSEARCH_HOST=https://localhost:9200
  SCOUT_OPENSEARCH_USERNAME=admin
  SCOUT_OPENSEARCH_PASSWORD=你的密码
  ```

  `config/scout.php` के `opensearch` अनुभाग में डिफ़ॉल्ट `ssl_verification=false` है (स्थानीय स्व-हस्ताक्षरित प्रमाणपत्र); उत्पादन में इसे `true` करें और प्रमाणपत्र कॉन्फ़िगर करें, कमज़ोर पासवर्ड कभी न रखें।

> इस प्रोजेक्ट के Docker Compose में Elasticsearch अंतर्निहित है (`open-admin-es` सेवा): Docker परिनियोजन में **elasticsearch ड्राइवर + ES क्लाइंट** चुनें; बाहरी/स्वतंत्र OpenSearch कंटेनर के लिए **opensearch ड्राइवर + opensearch-php** चुनें।
>
> **इंडेक्स का दायरा**: `app/model/` के सभी 224 मॉडल में `Searchable` है, लिखने/सॉफ़्ट-डिलीट पर `ModelObserver` से इंडेक्स सिंक होता है; इनमें AdminUser, Customer, Product, Supplier — ये 4 मॉडल कस्टम `toSearchableArray()` से व्हाइटलिस्ट फ़ील्ड रखते हैं, शेष मॉडल डिफ़ॉल्ट (पूरी पंक्ति) के अनुसार इंडेक्स होते हैं।
>
> **इंजन अनुपलब्ध होने पर बिज़नेस लेखन प्रभावित नहीं होता** (प्रमाणित: ड्राइवर को अप्राप्य पोर्ट पर इंगित करने के बाद भी `save()` सफल रहा, केवल एक अतिरिक्त कनेक्शन टाइमआउट का समय लगा) —— सर्च इंजन एक वैकल्पिक घटक है, इसे इंस्टॉल न करने पर भी पूरा बिज़नेस चलता है।
>
> **दायरे की व्याख्या**: इस प्रोजेक्ट में अभी केवल **इंडेक्स सिंक** जोड़ा गया है (लिखने/सॉफ़्ट-डिलीट पर तत्काल सिंक), कोई सर्च API या सर्च इंटरफ़ेस उपलब्ध नहीं है; बिज़नेस को खोज चाहिए तो स्वयं Scout की क्वेरी API कॉल करें (प्रशासन सूची पृष्ठ के फ़िल्टर बैकएंड `where` क्वेरी से जाते हैं, सर्च इंजन से नहीं)।

## डेटाबेस मानदंड

- **टेबल उपसर्ग**: `erp_`
- **प्राथमिक कुंजी**: सभी तालिकाओं की प्राथमिक कुंजी `id BIGINT UNSIGNED NOT NULL` है, **AUTO_INCREMENT निषिद्ध**
- **ID जनरेशन**: प्राथमिक कुंजी ID एप्लिकेशन परत में `SnowflakeService::generate()` से उत्पन्न होती है, वितरित रूप से अद्वितीय
- **अनिवार्य फ़ील्ड**: प्रत्येक तालिका में `id`, `created_at`, `updated_at` होना चाहिए
- **सॉफ्ट डिलीट**: सॉफ्ट डिलीट आवश्यकता वाली तालिकाओं में `deleted_at DATETIME DEFAULT NULL` जोड़ें
- **संवेदनशील फ़ील्ड**: फोन नंबर, ईमेल, पहचान पत्र नंबर आदि `encryptable` प्लगइन से स्वतः एन्क्रिप्ट/डिक्रिप्ट होते हैं, डेटाबेस फ़ील्ड सिफरटेक्स्ट को `VARCHAR(500)` में संग्रहीत करती है

| `413` | अनुरोध निकाय बहुत बड़ा | SecurityFilter ट्रिगर, 10MB से अधिक |
| `405` | अनुरोध विधि अनुमत नहीं | SecurityFilter ट्रिगर, केवल GET/POST/PUT/DELETE/OPTIONS/HEAD |
| `415` | असमर्थित मीडिया प्रकार | SecurityFilter ट्रिगर, Content-Type JSON नहीं |
| `429` | बहुत अधिक अनुरोध | RateLimit ट्रिगर / खाता लॉक (5 बार लॉगिन विफल पर 15 मिनट लॉक) |
| `500` | सर्वर आंतरिक त्रुटि | |

### अंतर्राष्ट्रीयकरण

अनुरोध हेडर `Accept-Language` स्वतः भाषा बदलता है (zh-CN → चीनी, en → English), डिफ़ॉल्ट चीनी।

### ID प्रसंस्करण

- **अनुरोध/प्रतिक्रिया में ID**: hashids से एन्क्रिप्ट करके स्ट्रिंग बनती है, वास्तविक डेटाबेस ID उजागर नहीं होती
- **इंटरफ़ेस पथ**: `GET /admin/v1/user/{hashid}` — पथ में `{id}` hashid स्ट्रिंग है
- **डेटाबेस भंडारण**: BIGINT मूल मान, snowflake से उत्पन्न

### API संस्करण

API संस्करण URL पथ में रखा जाता है (जैसे `/admin/v1/*`, `/api/v1/*`, `/open/v1/*`), **क्लाइंट को किसी संस्करण हेडर की आवश्यकता नहीं**:

- संस्करणित सार्वजनिक इंटरफ़ेस सीधे संबंधित संस्करण कंट्रोलर क्लास से जुड़ते हैं (`app/api/v1/controller/`)
- नया संस्करण जोड़ते समय नया `/api/vN` रूट समूह पंजीकृत करें, कंट्रोलर संस्करण अनुसार `app/api/vN/` में रखें
- पुराना `v()` गतिशील पार्सिंग और `ApiVersion` अनुरोध हेडर मिडलवेयर दोनों हटा दिए गए हैं

### रेट लिमिट

Redis स्लाइडिंग विंडो एल्गोरिदम पर आधारित, डिफ़ॉल्ट 60 बार/मिनट/IP/रूट। संवेदनशील इंटरफ़ेस अधिक सख्त:
- लॉगिन: 10 बार/मिनट
- पंजीकरण: 5 बार/मिनट (डिफ़ॉल्ट रूप से बंद, `REGISTRATION_ENABLED=1` से खोलें)

प्रतिक्रिया हेडर में `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` होते हैं। सीमा पार करने पर 429 लौटता है और `Retry-After` संलग्न होता है।

### मिडलवेयर आर्किटेक्चर

वैश्विक मिडलवेयर सभी अनुरोधों पर लागू होता है, क्रम से निष्पादित:

```
Cors (CORS पूर्व-प्रसंस्करण + प्रतिक्रिया हेडर)
  → SecurityFilter (HTTP विधि प्रतिबंध/अनुरोध बॉडी आकार/Content-Type जाँच/XSS/SQL इंजेक्शन/पाथ ट्रैवर्सल/कमांड इंजेक्शन/CSRF हमला अवरोध)
  → RateLimit (Redis स्लाइडिंग विंडो रेट लिमिट + खाता लॉक: 5 बार लॉगिन विफल → 15 मिनट लॉक)
  → TracingId (चेन ट्रेसिंग ID)
```

रूट समूह मिडलवेयर: `/admin/v1` पर `AdminAuth` (JWT प्रमाणीकरण + ब्लैकलिस्ट) → `AdminPermission` (RBAC अनुमति) → `OperationLog` (POST/PUT/DELETE स्वतः लॉग, स्रोत-एंड पहचान सहित); `/open/v1` पर `OpenApiAuth`; TMS ट्रैकिंग कॉलबैक पर `TrackingSignature`। भाषा `app/common/I18n.php` द्वारा `Accept-Language` से तय होती है, यह मिडलवेयर नहीं है।

`/health` और `/api/docs` और `/install` सार्वजनिक एंडपॉइंट हैं, केवल `Cors → SecurityFilter → RateLimit → TracingId` से गुजरते हैं।

सुरक्षा संवर्द्धन:
- **खाता लॉक**: लगातार 5 बार लॉगिन विफल होने पर खाता स्वतः 15 मिनट लॉक हो जाता है, लॉक अवधि में लॉगिन 429 लौटाता है
- **समवर्ती सत्र सीमा**: एक उपयोगकर्ता के पास अधिकतम 3 वैध टोकन, अधिक होने पर सबसे पुराना टोकन स्वतः ब्लैकलिस्ट में जाता है
- **security.txt**: `GET /.well-known/security.txt` RFC 9116 मानक सुरक्षा संपर्क जानकारी प्रदान करता है
- **Nginx सुरक्षा कॉन्फ़िगरेशन**: `docs/nginx-security.conf` देखें, पूर्ण रिवर्स प्रॉक्सी सुरक्षा सुदृढ़ीकरण उदाहरण

### प्रमाणीकरण

लॉगिन और पंजीकरण के लिए पहले **क्लिक कैप्चा** सत्यापन आवश्यक है:

1. क्लाइंट `POST /api/v1/captcha/generate` से कैप्चा छवि (base64 PNG) और टेक्स्ट लक्ष्य सूची प्राप्त करता है
2. उपयोगकर्ता छवि में संबंधित टेक्स्ट स्थानों पर क्रम से क्लिक करता है, क्लिक निर्देशांक `[{x, y}, ...]` एकत्र करता है
3. लॉगिन के समय `captcha_key` और `clicks` साथ सबमिट करें, सर्वर पहले कैप्चा फिर क्रेडेंशियल सत्यापित करता है

```http
POST /api/v1/auth/login
Content-Type: application/json

{
  "username": "admin",
  "password": "******",
  "captcha_key": "abc123...",
  "clicks": [{"x": 120, "y": 85}, {"x": 210, "y": 140}, {"x": 95, "y": 170}]
}
```

प्रशासन के बाद के इंटरफ़ेस के लिए JWT प्रमाणीकरण आवश्यक है:

```http
Authorization: Bearer <token>
```

लॉगिन सफल होने पर access_token लौटता है, वैधता 2 घंटे; इसके अलावा refresh_token लौटता है, वैधता 14 दिन।

लॉगआउट पर टोकन Redis ब्लैकलिस्ट में जाता है, वैधता अवधि में दोबारा उपयोग नहीं हो सकता। POST /admin/v1/profile/logout

### संवेदनशील ऑपरेशन की द्वितीयक पुष्टि

उपयोगकर्ता, भूमिका, अनुमति आदि हटाने जैसे संवेदनशील ऑपरेशनों के लिए अनुरोध निकाय में वर्तमान लॉगिन उपयोगकर्ता का `password` पास करके पहचान की द्वितीयक पुष्टि करनी होती है:

```http
DELETE /admin/v1/user/{id}
Content-Type: application/json
Authorization: Bearer <token>

{ "password": "******" }
```

### CI/CD

GitHub Actions सतत एकीकरण पाइपलाइन: `.github/workflows/ci.yml`, पाँच जॉब:

| जॉब | सामग्री |
|------|------|
| `php` (PHP 8.3 / 8.4 मैट्रिक्स, MySQL 8 + Redis 7 सेवा सहित) | composer सत्यापन और सुरक्षा ऑडिट → `php -l` → **PHPStan** (level 5 + baseline) → **PHP CS Fixer** (dry-run) → पूर्ण `install.sql` आयात → **PHPUnit** (इंटीग्रेशन केस सहित) → pcov कवरेज संग्रह → कवरेज थ्रेशोल्ड (समग्र ≥ 4%, `app/service` ≥ 10%, क्रमशः कड़ा) |
| `flutter` | `flutter analyze` + `flutter test` (`continue-on-error: true`, वातावरण स्थिर होने पर कड़ा करें) |
| `docs` | `bash scripts/doc-stats.sh --check`: README और docs में `stats:key=value` एनोटेशन की स्रोत-कोड वास्तविक गणना से संगति जाँचता है (कंट्रोलर/सेवा/मॉडल/तालिका/टेस्ट संख्या आदि), विचलन पर रेड |
| `e2e` | वास्तविक webman सेवा शुरू → स्वास्थ्य जाँच → HTTP कोर चेन स्मोक + प्रशासन API कवरेज |
| `release` | `main` पर push और उपरोक्त जॉब पास होने पर patch+1 के अनुसार tag बनाकर Release प्रकाशित (नीचे देखें) |

> फ्रंटएंड स्टैटिक जाँच का दायरा: CI अभी केवल Flutter चलाता है; Angular/React (`tsc --noEmit`) और HarmonyOS (`hvigorw assembleHap`) स्थानीय रूप से या बाद में जोड़े गए जॉब में चलाने होंगे।

### रिलीज़ प्रक्रिया (संस्करण वृद्धि)

`main` पर push करने और php / docs / e2e जाँच के पूर्णतः पास होने के बाद, `ci.yml` का `release` जॉब स्वतः नवीनतम tag के **patch+1** के अनुसार नया संस्करण tag बनाकर push करता है (`v1.1.4` → `v1.1.5`), और फिर उसी नाम का GitHub Release बनाता है (`--generate-notes` से स्वतः परिवर्तन विवरण उत्पन्न)।

- **ट्रिगर**: केवल `main` पर push (PR से ट्रिगर नहीं होता; tag push शाखा फ़िल्टर से मेल नहीं खाता, अतः यह वर्कफ़्लो पुनरावर्ती रूप से ट्रिगर नहीं होगा)
- **इडेम्पोटेंट**: दूरस्थ पर समान नाम का tag या release पहले से होने पर (समवर्ती CI / मैन्युअल रूप से बनाया गया) स्वतः छोड़ देता है, कोई त्रुटि नहीं
- **स्थानीय पूर्वाभ्यास**: `bash scripts/bump-version.sh --check` अगला संस्करण संख्या छापता है (रीड-ओनली, दूरस्थ पर कुछ नहीं लिखता)

### डेटाबेस बैकअप

`database/backup/` निर्देशिका:

- `backup.sh` — mysqldump + gzip बैकअप, 30 दिन पुराने बैकअप स्वतः साफ़ करता है
- `restore.sh` — इंटरैक्टिव पुनर्स्थापना, उपलब्ध बैकअप सूचीबद्ध करता है
