## 3. सहयोग मोड

### 3.1 सामान्य नियम (रूट CLAUDE.md से लिया गया)

- **SendMessage-First**: agents के बीच SendMessage से सीधे संवाद, पोल नहीं, साझा परिवर्तनीय स्थिति नहीं;
- **नामकरण अनिवार्य**: प्रत्येक agent का नाम होना चाहिए (`name: "role"`);
- **एक बार spawn**: स्वतंत्र उप-कार्य एक बार में पृष्ठभूमि में उठाएँ, Lead रुककर परिणाम की प्रतीक्षा करता है, स्थिति पोल नहीं करता;
- **संदेश अनिवार्य**: प्रत्येक prompt में लिखा हो "पूरा होने पर SendMessage किसे, क्या भेजें"।

### 3.2 तीन ऑर्केस्ट्रेशन टोपोलॉजी

| मोड | प्रवाह | उपयोग परिदृश्य |
|------|------|----------|
| **Pipeline** | Lead → आर्किटेक्ट → बैकएंड → टेस्ट → समीक्षा | अनुक्रमिक निर्भरता वाला फ़ीचर विकास (नए मॉड्यूल, क्रॉस-मॉड्यूल डेटा प्रवाह) |
| **Fan-out** | Lead → A, B, C → Lead संकलन | परस्पर स्वतंत्र समानांतर कार्य (बहु-पेज, बहु-मॉड्यूल शोध) |
| **Supervisor** | Lead ↔ सदस्य बहु-राउंड आदान-प्रदान | निरंतर समन्वय वाला जटिल कार्य (माइक्रोसर्विस विभाजन, बड़े पैमाने पर रीफैक्टरिंग) |

### 3.3 कार्य रूटिंग तालिका

| कार्य प्रकार | ऑर्केस्ट्रेशन | भाग लेने वाली भूमिकाएँ |
|----------|------|----------|
| नया मॉड्यूल / नया फ़ीचर (जैसे DMS, BI गहनता) | pipeline | Lead → आर्किटेक्ट (तालिका डिज़ाइन) → बैकएंड → टेस्ट → समीक्षा |
| इंजन-स्तर एल्गोरिदम (दोहरी प्रविष्टि / वेतन / MRP) | pipeline + TDD | Lead → व्यावसायिक इंजन विशेषज्ञ (डिज़ाइन) → टेस्ट (सीमा केस पहले) → समीक्षा |
| फ्रंटएंड पेज (Flutter / HarmonyOS समानांतर) | fan-out | Lead → फ्रंटएंड×2 + बैकएंड (API संरेखण) समानांतर → Lead संकलन |
| क्रॉस-मॉड्यूल डेटा प्रवाह (क्रय→इन्वेंटरी→देय आदि) | pipeline | Lead → आर्किटेक्ट → बैकएंड → टेस्ट → समीक्षा |
| माइक्रोसर्विस विभाजन / बड़े पैमाने पर रीफैक्टरिंग | supervisor | Lead ↔ आर्किटेक्ट + बैकएंड + समीक्षा बहु-राउंड |
| सुरक्षा / प्रदर्शन विशेष | एकल-थ्रेड गहन | Lead → सुरक्षा/DevOps इंजीनियर → समीक्षा |
| बग फिक्स (एक फ़ाइल / 1-2 पंक्तियाँ) | टीम में नहीं | Lead सीधे संभालता है, या 1 agent पूरा करता है |
| तीन शाखा अंतर / संस्करण रिलीज़ | pipeline | Lead → संस्करण समन्वयक → टेस्ट (क्रॉस-शाखा रिग्रेशन) → समीक्षा |

### 3.4 गुणवत्ता द्वार (कमिट से पहले अनिवार्य, समीक्षक द्वारा रक्षित)

## 5. कार्यान्वयन चरण

1. **भूमिका परिभाषाएँ पूरी करें**: `.claude/agents/` में planner / sparc / testing / swarm / consensus पहले से हैं, `business-engineer`, `frontend-flutter`, `frontend-harmonyos`, `researcher`, `edition-coordinator` पाँच परिभाषाएँ कम हैं; मौजूदा YAML/MD प्रारूप में एक-एक फ़ाइल जोड़ते ही माउंट पूरा;
2. **रूटिंग स्थिर करें**: §3.3 रूटिंग तालिका `.claude-flow/hooks` की routing तर्क में लिखें, `UserPromptSubmit` हुक स्वतः कार्य को संबंधित भूमिका को सौंपे;
3. **मेमोरी विभाजन**: `.claude-flow` में `agentScopes` (`defaultScope: project`) खुला है, सुझाव `backend / frontend / ops / security` चार क्षेत्रों में संग्रह, वित्त इंजन कॉन्टेक्स्ट फ्रंटएंड कार्यों को दूषित करने से बचाएं;
4. **पायलट चलाएँ**: एक क्रॉस-मॉड्यूल कार्य चुनें (जैसे DMS गहनता या BI बोर्ड पुनरावृत्ति) §3.3 रूटिंग अनुसार पूरा एक राउंड चलाएँ, संदेश श्रृंखला और द्वार सत्यापित करने के बाद प्रचार करें।
