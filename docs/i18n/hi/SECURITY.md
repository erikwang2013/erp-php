## 1. गहन रक्षा परिदृश्य

सिस्टम 7-परत गहन रक्षा मॉडल अपनाता है, बाहर से अंदर तक हर परत दुर्भावनापूर्ण अनुरोधों को फ़िल्टर करती है, यह सुनिश्चित करती है कि किसी भी एक परत के विफल होने पर भी अगली रक्षा पंक्ति काम करे।

संपूर्ण मिडलवेयर चेन निम्नलिखित क्रम में निष्पादित होती है (`config/middleware.php` देखें):

```
अनुरोध → Cors → SecurityFilter → RateLimit → [रूट समूह मिडलवेयर: AdminAuth → AdminPermission → OperationLog] → Controller
```

| परत | मिडलवेयर/तंत्र | सुरक्षा लक्ष्य |
|----|--------|---------|
| 1 | SecurityFilter | XSS / SQL इंजेक्शन / पाथ ट्रैवर्सल / कमांड इंजेक्शन / CSRF हमला रोकथाम |
| 2 | Cors | क्रॉस-ओरिजिन सुरक्षा + रिस्पॉन्स सुरक्षा हेडर इंजेक्शन |
| 3 | RateLimit | Redis स्लाइडिंग विंडो रेट लिमिट, ब्रूट-फोर्स रोकथाम |
| 4 | AdminAuth | JWT प्रमाणीकरण + ब्लैकलिस्ट लॉगआउट |
| 5 | AdminPermission | RBAC method.path ग्रैन्युलैरिटी प्रमाणीकरण |
| 6 | OperationLog | ऑपरेशन ऑडिट + स्रोत एंड ट्रैकिंग |
| 7 | डेटा एन्क्रिप्शन | Hashids ID ऑब्स्क्यूरेशन + Encryptable DB एन्क्रिप्शन + EncryptionService ट्रांसमिशन एन्क्रिप्शन |

फ्रंटएंड तीन परतों (Flutter) में अलग इनपुट सत्यापन है, बैकएंड किसी पर भी भरोसा नहीं करता, हर परत स्वतंत्र रूप से रक्षा करती है।

## 2. हमला पहचान इंजन

### 2.0 HTTP विधि प्रतिबंध

SecurityFilter सभी हमला पहचान से पहले HTTP विधि की जाँच करता है, केवल निम्न मानक विधियों की अनुमति देता है:

```
GET, POST, PUT, DELETE, OPTIONS, HEAD
```

गैर-मानक विधियाँ (जैसे TRACE, CONNECT, PATCH, कस्टम विधियाँ आदि) सीधे **405 Method Not Allowed** लौटाती हैं, रिस्पॉन्स बॉडी खाली HTML होती है, आगे की हमला पहचान या व्यावसायिक तर्क में प्रवेश नहीं होता।

यह गहन रक्षा की पहली रक्षा पंक्ति है, प्रभावी रूप से रोकती है:
- TRACE क्रॉस-साइट ट्रैकिंग हमला (XST)
- CONNECT टनल प्रॉक्सी दुरुपयोग
- गैर-मानक WebDAV विधि प्रोबिंग
- स्वचालित स्कैनर का HTTP विधि एन्यूमरेशन

### 2.1 XSS क्रॉस-साइट स्क्रिप्टिंग

सभी रेगेक्स `SecurityFilter::PATTERNS['XSS']` से आते हैं, केस-असंवेदनशील मिलान होता है।

| पहचान पैटर्न | रेगेक्स | रक्षा किए गए हमले |
|----------|------|-----------|
| स्क्रिप्ट टैग | `<\s*\/?\s*s\s*c\s*r\s*i\s*p\s*t\b` | `<script>`, `<script >`, `< script>` जैसे स्पेस वेरिएंट |
| इवेंट एट्रिब्यूट | `\bon\w+\s*=\s*[\"\']?\s*(?:javascript\|vbscript):` | `onclick="javascript:..."` जैसे इनलाइन इवेंट |
| JS स्यूडो-प्रोटोकॉल | `(?:javascript\|vbscript)\s*:\s*(?:[^\s]*\s*)?(?:eval\|alert\|prompt\|confirm\|document\.cookie\|location\s*=)` | `javascript:eval(...)`, `javascript:alert(1)` आदि |
| Data URI XSS | `data\s*:\s*text\s*\/\s*html\s*(?:;base64)?\s*,` | `data:text/html,<script>`, `data:text/html;base64,...` आदि |
| टेम्पलेट इंजेक्शन | `\{\{.*?\}\}` | `{{constructor}}`, `{{7*7}}` जैसे सर्वर/Angular/Vue टेम्पलेट इंजेक्शन |

### 2.2 SQL इंजेक्शन

| पहचान पैटर्न | रेगेक्स | रक्षा किए गए हमले |
|----------|------|-----------|
| UNION संयुक्त क्वेरी | `\bUNION\s+(?:ALL\s+)?SELECT\b` | `UNION SELECT`, `UNION ALL SELECT` डेटा निकालना |
| OR हमेशा-सत्य इंजेक्शन | `(?:[\"\']\s*OR\s+[\"\']?\s*\d+\s*=\s*\d+\|[\"\']\s*OR\s+[\"\']?1[\"\']?\s*=\s*[\"\']?1)` | `' OR 1=1--`, `" OR '1'='1'` |
| तालिका संरचना विनाश | `\b(?:DROP\|ALTER\|TRUNCATE)\s+(?:TABLE\|DATABASE\|INDEX\|VIEW)\b` | `DROP TABLE users`, `TRUNCATE TABLE logs` |
| स्टोर्ड प्रोसीजर कॉल | `\b(?:xp_cmdshell\|sp_executesql\|sp_addsrvrolemember)\b` | MSSQL एक्सटेंडेड स्टोर्ड प्रोसीजर कमांड निष्पादन |
| मेटाडेटा प्रोबिंग | `\b(?:INFORMATION_SCHEMA\|sys\.(?:tables\|columns\|databases)\|pg_class\|sqlite_master\|mysql\.(?:user\|db))\b` | MySQL/PG/SQLite/MSSQL डेटाबेस संरचना प्रोबिंग |
| कमेंट बायपास | `(?:[\"\'])\s*(?:--\|#)\s*[\"\']?\s*(?:OR\|AND\|SELECT\|INSERT\|UPDATE\|DELETE\|DROP)` | `'-- OR SELECT`, `'# AND UPDATE` कमेंट बायपास |

### 2.3 पाथ ट्रैवर्सल

| पहचान पैटर्न | रेगेक्स | रक्षा किए गए हमले |
|----------|------|-----------|
| डायरेक्टरी बैकट्रैकिंग | `\.\.[\/\\\\]{2,}` | `../`, `..\`, `....//` बहु-स्तरीय डायरेक्टरी बैकट्रैकिंग |
| संवेदनशील फ़ाइल प्रोबिंग | `\/(?:etc\/(?:passwd\|shadow\|hosts)\|proc\/self\|boot\.ini\|win\.ini\|WEB-INF\|\.env\|\.git\/)` | `/etc/passwd`, `/proc/self/environ`, `.env`, `.git/HEAD` आदि |
| नल-बाइट ट्रंकेशन | `%00` | `../../../etc/passwd%00.jpg` एक्सटेंशन सत्यापन बायपास |

### 2.4 कमांड इंजेक्शन

| पहचान पैटर्न | रेगेक्स | रक्षा किए गए हमले |
|----------|------|-----------|
| पाइप/सेमीकोलन कमांड | `[;\|&]\s*(?:ls\|cat\|rm\|wget\|curl\|nc\|bash\|sh\|cmd\|powershell\|python\|perl)\b` | `;cat /etc/passwd`, `\|bash` |
| बैकटिक सब्स्टिट्यूशन | `` `[^`]*\b(?:cat\|ls\|id\|whoami\|pwd\|rm\|wget\|curl)\b[^`]*` `` | `` `cat /etc/passwd` `` |
| $() सब्स्टिट्यूशन | `\$\(\s*(?:cat\|ls\|id\|whoami\|rm\|wget\|curl)\b` | `$(whoami)`, `$(cat flag)` |
| रिमोट डाउनलोड पाइप | `(?:wget\|curl)\s+.*(?:\b-o\b\|\b-O\b\|pipe\|bash\|python).*\bhttps?:\/\/` | `wget URL -O - \| bash`, `curl URL \| python` |

### 2.5 CSRF क्रॉस-साइट अनुरोध फोर्जरी

सत्यापन तर्क `SecurityFilter::checkCsrf()` में लागू किया गया है:

```php
// केवल POST/PUT/DELETE सत्यापन ट्रिगर करते हैं
// Origin और Referer दोनों खाली → पास (गैर-ब्राउज़र क्लाइंट)
// Origin गैर-खाली → Origin डोमेन को Host से तुलना करें
```

तुलना नियम:
- Host से `www.` उपसर्ग हटाकर Origin डोमेन से सटीक तुलना करें
- यदि Host Origin का पैरेंट डोमेन है (जैसे `Origin: app.example.com`, `Host: example.com` — `str_contains($originHost, '.' . $hostOnly)` ट्रिगर होता है), पास करें
- न सटीक मिलान, न सबडोमेन → 403 लौटाएँ, CSRF हमला मानें

नोट: गैर-ब्राउज़र क्लाइंट (जैसे बिना Origin/Referer के curl) सीधे पास होते हैं, CSRF सुरक्षा केवल ब्राउज़र वातावरण में प्रभावी है।

### 2.6 दुर्भावनापूर्ण फ़ाइल अपलोड

| पहचान पैटर्न | रेगेक्स | रक्षा किए गए हमले |
|----------|------|-----------|
| डबल एक्सटेंशन भेष | `\.(?:php\d?\|phtml\|phar\|cgi\|pl\|py\|jsp\|asp)x?\.(?:png\|jpg\|gif\|pdf)` | `shell.php.png`, `shell.phar.jpg` व्हाइटलिस्ट बायपास |
| PHP एक्सटेंशन | `\.php\s*$/m` | अनुरोध पैरामीटर में सीधे `.php` पाथ |

## 3. हमला एस्केलेशन और IP ब्लैकलिस्ट

SecurityFilter में अंतर्निहित हमला एस्केलेशन तंत्र है, एक ही IP के लगातार स्कैनिंग हमलों को रोकता है।

### एस्केलेशन प्रक्रिया

```
पहली स्कैन हिट → Redis INCR security_escalate:{ip} = 1, TTL=60s
दूसरी स्कैन हिट → INCR → 2
...
पाँचवीं स्कैन हिट → INCR → 5
    → प्रतिबंध ट्रिगर: SETEX security_ban:{ip} 900 1
    → काउंटर साफ़ करें DEL security_escalate:{ip}
    → सुरक्षा लॉग लिखें: [SECURITY] IP banned 15min
```

### प्रतिबंध अवधि में व्यवहार

हर अनुरोध SecurityFilter में प्रवेश करते समय पहले `isBanned()` जाँचता है:

```php
if (Redis::get("security_ban:{$ip}")) {
    return response('<h1>403 Forbidden</h1>', 403);
}
```

प्रतिबंधित IP के सभी अनुरोध (कानूनी अनुरोध सहित) 15 मिनट तक सीधे 403 लौटाते हैं, आगे की व्यावसायिक तर्क पूरी तरह स्किप होती है।

### कॉन्फ़िग कॉन्स्टेंट

| कॉन्स्टेंट | मान | अर्थ |
|------|-----|------|
| ESCALATE_LIMIT | 5 | 60 सेकंड विंडो में ट्रिगर थ्रेशोल्ड |
| ESCALATE_WINDOW | 60 | काउंटर विंडो (सेकंड) |
| BAN_DURATION | 900 | ब्लैकलिस्ट अवधि (सेकंड), यानी 15 मिनट |

### सुरक्षा लॉग

फ़ाइल स्थान: `runtime/logs/security.log`

लॉग प्रारूप उदाहरण:
```
2026-05-20 14:32:11 [SECURITY] XSS attack blocked | IP: 192.168.1.100 | Path: /admin/user | Field: body.username | Source: body | Payload: <script>alert(1)</script>
2026-05-20 14:32:15 [SECURITY] IP banned 15min | IP: 192.168.1.100 | Triggers: 5
```

### अनुरोध बॉडी आकार सीमा

`Content-Length > 10MB` सीधे 413 Payload Too Large लौटाता है, DoS बड़े अनुरोध बॉडी हमले से बचाता है।

### Content-Type सत्यापन

POST/PUT अनुरोध **अनिवार्य रूप से** `Content-Type` को `application/json` या `application/x-www-form-urlencoded` घोषित करना चाहिए, अन्यथा 415 Unsupported Media Type लौटता है। फ़ाइल अपलोड अनुरोध (file फ़ील्ड वाले) इस जाँच को स्किप करते हैं।

## 4. रिस्पॉन्स सुरक्षा हेडर

सभी हेडर `Cors` मिडलवेयर में इंजेक्ट होते हैं, `$response->withHeaders()` के माध्यम से हर रिस्पॉन्स में जुड़ते हैं।

| हेडर | मान | भूमिका |
|----|-----|------|
| Access-Control-Allow-Origin | `*` | किसी भी ओरिजिन को क्रॉस-डोमेन अनुमति (इंट्रानेट प्रबंधन बैकएंड परिदृश्य) |
| Access-Control-Allow-Methods | `GET,POST,PUT,DELETE,OPTIONS` | अनुमत विधियों का सेट |
| Access-Control-Allow-Headers | `Authorization,Content-Type,API-Version` | अनुमत कस्टम हेडर |
| Access-Control-Max-Age | `86400` | प्रीफ़्लाइट अनुरोध कैश 24 घंटे |
| X-Content-Type-Options | `nosniff` | ब्राउज़र MIME स्निफिंग प्रतिबंधित |
| X-Frame-Options | `DENY` | सभी iframe एम्बेडिंग प्रतिबंधित, क्लिकजैकिंग रोकथाम |
| X-XSS-Protection | `1; mode=block` | ब्राउज़र बिल्ट-इन XSS फ़िल्टर सक्षम और पेज रेंडरिंग रोकना |
| Referrer-Policy | `strict-origin-when-cross-origin` | समान-ओरिजिन पर पूर्ण URL, क्रॉस-डोमेन पर केवल डोमेन |
| Permissions-Policy | `camera=(), microphone=(), geolocation=()` | पूरी साइट पर कैमरा/माइक्रोफ़ोन/जियोलोकेशन API अक्षम |

OPTIONS प्रीफ़्लाइट अनुरोध सीधे 204 खाली रिस्पॉन्स लौटाते हैं, आगे की मिडलवेयर चेन में नहीं जाते।

### 4.2 Content-Security-Policy (CSP)

अन्य सुरक्षा हेडर के साथ Cors मिडलवेयर में इंजेक्ट होता है, गहन रक्षा प्रदान करता है, ब्राउज़र द्वारा लोड और निष्पादित की जा सकने वाली संसाधन स्रोतों को सीमित करता है।

| हेडर | मान | भूमिका |
|----|-----|------|
| Content-Security-Policy | `default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` | स्क्रिप्ट/स्टाइल/छवि/कनेक्शन/फ़्रेम/फ़ॉर्म आदि संसाधन स्रोतों को सीमित करता है |
| X-Permitted-Cross-Domain-Policies | `none` | Adobe Flash/PDF जैसे क्रॉस-डोमेन पॉलिसी फ़ाइल लोडिंग प्रतिबंधित |

CSP नीति मुख्य बिंदु:
- `default-src 'self'`: डिफ़ॉल्ट रूप से केवल समान-ओरिजिन संसाधन अनुमत
- `script-src 'self' 'unsafe-inline' 'unsafe-eval'`: समान-ओरिजिन स्क्रिप्ट + इनलाइन स्क्रिप्ट (Flutter Web के लिए आवश्यक) + eval (Flutter Web डिबग के लिए आवश्यक)
- `frame-ancestors 'none'`: किसी भी पेज में iframe एम्बेडिंग प्रतिबंधित, X-Frame-Options: DENY के साथ दोहरी सुरक्षा
- `base-uri 'self'`: `<base>` टैग केवल समान-ओरिजिन की ओर इंगित कर सकता है
- `form-action 'self'`: फ़ॉर्म केवल समान-ओरिजिन पर सबमिट हो सकता है

## 5. रेट लिमिटिंग नीति

### एल्गोरिदम

Redis Sorted Set स्लाइडिंग विंडो + Lua एटॉमिक स्क्रिप्ट, प्रमुख ऑपरेशन:

```lua
-- 1. विंडो के बाहर की पुरानी रिकॉर्ड साफ़ करें
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, windowStart)
-- 2. वर्तमान विंडो काउंट जाँचें
local count = redis.call('ZCARD', KEYS[1])
-- 3. सीमा पार होने पर {0, count} लौटाएँ, अन्यथा ZADD करें और {1, count+1} लौटाएँ
if count >= limit then return {0, count} end
redis.call('ZADD', KEYS[1], now, now . '.' . random)  -- यादृच्छिक सफ़िक्स समान मिलीसेकंड ओवरराइट से बचाता है
redis.call('EXPIRE', KEYS[1], window + 10)
```

Lua स्क्रिप्ट Redis सर्वर पर सिंगल-थ्रेडेड निष्पादित होती है, **स्वाभाविक रूप से एटॉमिक**, TOCTOU (Time-of-check to Time-of-use) रेस कंडीशन समाप्त करती है।

### रेट लिमिट कॉन्फ़िग

| रूट | सीमा | विंडो | परिदृश्य |
|------|------|------|------|
| डिफ़ॉल्ट (सभी रूट) | 60 बार/मिनट | 60s | सामान्य API |
| `/api/auth/login` | 10 बार/मिनट | 60s | लॉगिन (ब्रूट-फोर्स रोकथाम) |
| `/api/auth/register` | 5 बार/मिनट | 60s | रजिस्टर (बैच रजिस्ट्रेशन रोकथाम; डिफ़ॉल्ट रूप से बंद, `REGISTRATION_ENABLED=1` की आवश्यकता) |

### रिस्पॉन्स हेडर

रेट लिमिट ट्रिगर होने पर HTTP 429 और JSON बॉडी लौटती है:
```json
{"code": 429, "message": "बहुत अधिक अनुरोध, कृपया बाद में पुनः प्रयास करें", "data": []}
```

सभी रिस्पॉन्स (सामान्य रिस्पॉन्स सहित) निम्न हेडर ले जाते हैं:

| हेडर | विवरण |
|----|------|
| X-RateLimit-Limit | वर्तमान विंडो में अधिकतम अनुमत अनुरोध संख्या |
| X-RateLimit-Remaining | वर्तमान विंडो में शेष उपलब्ध अनुरोध संख्या |
| X-RateLimit-Reset | विंडो रीसेट का Unix टाइमस्टैम्प |
| Retry-After | केवल रेट लिमिट पर, सुझावित प्रतीक्षा सेकंड |

### डाउनग्रेड नीति

Redis असामान्यता (कनेक्शन टाइमआउट, अनुपलब्धता आदि) पर **fail-open**:

```php
try {
    $result = Redis::eval($lua, ...);
} catch (\Throwable $e) {
    return $handler($request); // Redis down, सभी अनुरोध पास करें
}
```

थोड़े समय के लिए रेट लिमिट सुरक्षा खोना बेहतर है, सामान्य व्यावसायिक अनुरोधों को ब्लॉक नहीं करना चाहिए।

### 5.4 खाता लॉक तंत्र

लॉगिन इंटरफ़ेस रेट लिमिटिंग के अलावा, अतिरिक्त रूप से **खाता लॉक** तंत्र जोड़ता है, विशिष्ट उपयोगकर्ताओं के खिलाफ लक्षित ब्रूट-फोर्स रोकता है।

**लॉक प्रक्रिया**:

```
लॉगिन विफल → Redis INCR account_lockout:{userId} TTL=900s
लगातार 5 विफलताएँ → Redis SETEX account_locked:{userId} 900 1
            → 429 लौटाएँ "खाता लॉक हो गया है, कृपया 15 मिनट बाद प्रयास करें"
            → काउंटर साफ़ करें DEL account_lockout:{userId}
```

**लॉक अवधि में व्यवहार**:

लॉक अवधि में सभी लॉगिन अनुरोध सीधे 429 लौटाते हैं, पासवर्ड सत्यापन नहीं होता, ब्रूट-फोर्स प्रयास पूरी तरह रोके जाते हैं।

**कॉन्फ़िग कॉन्स्टेंट**:

| कॉन्स्टेंट | मान | अर्थ |
|------|-----|------|
| MAX_LOGIN_ATTEMPTS | 5 | अधिकतम लगातार विफलता संख्या |
| LOCKOUT_DURATION | 900 | लॉक अवधि (सेकंड), यानी 15 मिनट |

नोट: खाता लॉक `userId` पर आधारित है, IP पर नहीं, इसलिए हमलावर IP बदलकर लॉक को बायपास नहीं कर सकता। IP रेट लिमिट (10 बार/मिनट) के साथ मिलकर दोहरी सुरक्षा बनती है:
- IP स्तर: 10 बार/मिनट रेट लिमिट वितरित ब्रूट-फोर्स रोकता है
- खाता स्तर: 5 विफलताओं पर लॉक लक्षित ब्रूट-फोर्स रोकता है

## 6. प्रमाणीकरण और अनुमति प्रमाणीकरण

### 6.1 JWT प्रमाणीकरण

AdminAuth मिडलवेयर में लागू, प्रमाणीकरण आवश्यक रूट समूहों पर माउंट होता है।

**पैरामीटर कॉन्फ़िग** (`config/plugin/erikwang2013/jwt/jwt`, `.env` से इंजेक्ट):

| पैरामीटर | मान | विवरण |
|------|-----|------|
| एल्गोरिदम | HS256 | HMAC-SHA256 सममित हस्ताक्षर |
| कुंजी | `JWT_SECRET` | पर्यावरण चर इंजेक्शन, उत्पादन में बदलना आवश्यक |
| access_token TTL | 7200s (2h) | `JWT_TTL` |
| refresh_token TTL | 1209600s (14d) | `JWT_REFRESH_TTL` |
| जारीकर्ता | `open-admin` | `JWT_ISSUER` |
| श्रोता | `open-admin` | `JWT_AUDIENCE` |

**Token निष्कर्षण**: `Authorization: Bearer <token>` हेडर से, `Bearer ` उपसर्ग हटाकर मूल JWT प्राप्त करें।

**प्रमाणीकरण प्रक्रिया**:
1. खाली token → सीधे 401 `{"code": 401, "message": "लॉगिन नहीं"}` 
2. Redis ब्लैकलिस्ट `jwt_blacklist:{md5(token)}` जाँचें → हिट → 401 `Token अमान्य हो गया है, कृपया पुनः लॉगिन करें`
3. JWT decode → विफल (समाप्त/हस्ताक्षर अमेल) → 401 `Token समाप्त या अमान्य`
4. सफल → `$request->adminId` और `$request->adminUsername` इंजेक्ट करें

**ब्लैकलिस्ट तंत्र**: उपयोगकर्ता लॉगआउट करते समय, `md5(token)` Redis में लिखा जाता है, TTL JWT शेष वैधता अवधि पर सेट होता है। Redis विफलता पर ब्लैकलिस्ट जाँच स्किप होती है (fail-open), इस समय लॉगआउट किया गया Token थोड़े समय के लिए उपयोग हो सकता है, लेकिन JWT की स्वयं की अल्पकालिक वैधता (2h) बैकअप सुरक्षा के रूप में काम करती है।

### 6.2 समवर्ती सत्र सीमा

Token लीक होने के बाद मल्टी-डिवाइस दुरुपयोग रोकने के लिए, सिस्टम एक ही उपयोगकर्ता के एक साथ मान्य Token की संख्या सीमित करता है।

**सीमा तर्क**:

```
लॉगिन सफल → नया Token जारी करें
         → वर्तमान उपयोगकर्ता के मान्य Token संख्या पूछें: Redis SCARD user_tokens:{userId}
         → यदि संख्या >= 3 (MAX_CONCURRENT_SESSIONS):
            → निर्माण समय के आरोही क्रम में, सबसे पुराना Token हटाएँ:
              Redis SREM user_tokens:{userId} <oldest_token_id>
              Redis SETEX jwt_blacklist:{md5(oldest_token)} TTL remaining
         → नया Token सेट में जोड़ें: Redis SADD user_tokens:{userId} <new_token_id>
            Redis SET user_token:{token_id} {userId} EX {TTL}
```

**कॉन्फ़िग कॉन्स्टेंट**:

| कॉन्स्टेंट | मान | अर्थ |
|------|-----|------|
| MAX_CONCURRENT_SESSIONS | 3 | एक ही उपयोगकर्ता के लिए अधिकतम समवर्ती Token संख्या |

**बाहर निकाला जाने का परिदृश्य**: जब उपयोगकर्ता चौथे डिवाइस पर लॉगिन करता है, पहले डिवाइस का Token बलपूर्वक ब्लैकलिस्ट में डाला जाता है, बाद के अनुरोध 401 "Token अमान्य हो गया है, कृपया पुनः लॉगिन करें" लौटाते हैं।

लॉगआउट पर, वर्तमान Token सेट से हट जाता है। Token स्वाभाविक रूप से समाप्त होने पर, Redis key स्वचालित रूप से अमान्य हो जाती है, सेट सदस्य घट जाते हैं।

### 6.3 RBAC अनुमति मॉडल

AdminPermission मिडलवेयर में लागू।

**डेटा मॉडल**: User -> Role -> Permission तीन-स्तरीय संबंध

- `erik_admin_user` (उपयोगकर्ता तालिका)
- `erik_admin_user_role` (उपयोगकर्ता-भूमिका संबंध तालिका)
- `erik_admin_role` (भूमिका तालिका)
- `erik_admin_role_permission` (भूमिका-अनुमति संबंध तालिका)
- `erik_admin_permission` (अनुमति तालिका)

**अनुमति प्रकार**:
| type | अर्थ | उदाहरण |
|------|------|------|
| 1 | मेनू अनुमति | बाएँ नेविगेशन दृश्यता नियंत्रित करता है |
| 2 | बटन अनुमति | पेज में ऑपरेशन बटन नियंत्रित करता है (नया/संपादित/हटाएँ) |
| 3 | API अनुमति | बैकएंड इंटरफ़ेस कॉल नियंत्रित करता है |

API अनुमति पहचानकर्ता प्रारूप: `{method}.{path}`

उदाहरण:
- `post.admin/user` — उपयोगकर्ता बनाएँ
- `put.admin/user` — उपयोगकर्ता संपादित करें
- `delete.admin/user` — उपयोगकर्ता हटाएँ
- `get.admin/user` — उपयोगकर्ता सूची देखें

**प्रमाणीकरण प्रक्रिया**:
1. `$request->adminId` खाली → पास (रूट पर प्रमाणीकरण पूर्व-आवश्यकता कॉन्फ़िग नहीं)
2. उपयोगकर्ता प्राप्त करें → भूमिकाएँ (`status=0` की अक्षम भूमिकाएँ स्किप करें) → अनुमति सूची
3. सुपर एडमिन (`slug = '*'`) → सीधे पास
4. `strtolower(method) . '.' . trim(path, '/')` बनाएँ → अनुमति सूची से तुलना करें
5. मिलान विफल → 403 `{"code": 403, "message": "पहुंच की अनुमति नहीं"}`

**द्वितीय पुष्टि**: BaseController `confirmPassword()` विधि प्रदान करता है, संवेदनशील ऑपरेशन (उपयोगकर्ता हटाना, डेटा निर्यात आदि) में Controller परत में वर्तमान पासवर्ड की अतिरिक्त आवश्यकता होती है, सत्र हाईजैक के बाद अनधिकृत ऑपरेशन रोकता है।

**सहनशीलता**: लॉग लिखने में असामान्यता व्यावसायिक अनुरोध को ब्लॉक नहीं करती (`catch (\Throwable)` मौन रूप से निगल जाता है)।

## 8. डेटा सुरक्षा

सिस्टम तीन-परत डेटा सुरक्षा नीति अपनाता है, डेटा प्रवाह के तीन चरणों के अनुरूप।

### 8.1 ट्रांसमिशन परत — EncryptionService

`EncryptionService` `erikwang2013/encryption` पैकेज का उपयोग करता है, API अनुरोध/रिस्पॉन्स में संवेदनशील फ़ील्ड को एन्क्रिप्ट/डिक्रिप्ट करता है।

**तकनीकी विवरण**:
- एल्गोरिदम: `aes-256-cbc-hmac` (अंतर्निहित HMAC हस्ताक्षर टैम्पर-प्रूफ)
- कुंजी: `ENCRYPTION_KEY` पर्यावरण चर, स्वचालित रूप से 32 बाइट में संरेखित
- उपयोग: क्लाइंट और API के बीच मोबाइल नंबर, ID कार्ड नंबर जैसे फ़ील्ड ट्रांसमिशन

**मास्किंग उपकरण विधियाँ**:
- `maskPhone('13812341234')` → `138****1234`
- `maskEmail('abc@example.com')` → `a***@example.com` (उपयोगकर्ता नाम 2 वर्ण से अधिक) या `a**@example.com`

### 8.2 स्टोरेज परत — Encryptable Cast

`AdminUser` मॉडल `Erikwang2013\Encryptable\Encryptable` Eloquent cast का उपयोग करता है, संबंधित फ़ील्ड:

- `email` → Encryptable के रूप में cast, स्वचालित एन्क्रिप्ट/डिक्रिप्ट
- `phone` → Encryptable के रूप में cast, स्वचालित एन्क्रिप्ट/डिक्रिप्ट
- `id_card` → Encryptable के रूप में cast, स्वचालित एन्क्रिप्ट/डिक्रिप्ट

डेटाबेस में लिखते समय स्वचालित रूप से सिफरटेक्स्ट में एन्क्रिप्ट होता है, पढ़ते समय स्वचालित रूप से प्लेनटेक्स्ट में डिक्रिप्ट होता है। डेटाबेस स्टोरेज कॉलम प्रकार `VARCHAR(500)` है, सिफरटेक्स्ट base64 रूप में संग्रहीत होता है।

**कुंजी प्रणाली**: ट्रांसमिशन परत एन्क्रिप्शन (`ENCRYPTION_KEY`) से स्वतंत्र रूप से `ENCRYPTABLE_KEY` उपयोग होता है, एक कुंजी के लीक होने से दूसरी परत अमान्य नहीं होती।

कुंजी रोटेशन: `ENCRYPTION_PREVIOUS_KEYS` पर्यावरण चर ऐतिहासिक कुंजी सूची (कॉमा-सेपरेटेड) का समर्थन करता है, पुराना डेटा पढ़ते समय ऐतिहासिक कुंजी से डिक्रिप्ट प्रयास, लिखते समय वर्तमान कुंजी से पुनः एन्क्रिप्ट।

### 8.3 डिस्प्ले परत — ID ऑब्स्क्यूरेशन और मास्किंग

**Hashids ID ऑब्स्क्यूरेशन**: `HashidsService` `erikwang2013/hashids` पैकेज का उपयोग करता है।

- बाहरी API द्वारा लौटाए गए डेटाबेस BIGINT ID hash स्ट्रिंग में एन्कोड होते हैं (जैसे `xK3mN9qR2pL7wV8b`)
- क्लाइंट अनुरोध में hash स्ट्रिंग भेजता है, बैकएंड स्वचालित रूप से मूल ID में डिकोड करता है
- साल्ट `HASHIDS_SALT` पर्यावरण चर से इंजेक्ट, साल्ट अलग होने पर एन्कोड/डिकोड परिणाम पूरी तरह अलग
- hash न्यूनतम लंबाई 16 वर्ण, 62-वर्ण अल्फ़ान्यूमेरिक वर्ण सेट उपयोग
- BaseController `encodeId()`, `decodeId()`, `encodeIds()` सुविधाजनक विधियाँ प्रदान करता है

**निर्यात मास्किंग**: Excel/PDF निर्यात में (ExportController), संवेदनशील फ़ील्ड एकीकृत रूप से मास्क होते हैं:
- मोबाइल नंबर: `138****1234`
- ईमेल: `a***@example.com`
- ID कार्ड: पूरी तरह छिपाकर `********`

## 9. कुंजी प्रबंधन

सभी कुंजियाँ `.env` पर्यावरण चर के माध्यम से इंजेक्ट होती हैं, कॉन्फ़िग फ़ाइलें `getenv()` से पढ़ती हैं और अंतर्निहित फॉलबैक डिफ़ॉल्ट मान रखती हैं (केवल विकास वातावरण के लिए सुरक्षित)।

| पर्यावरण चर | उपयोग | पैकेज | उत्पादन आवश्यकता |
|----------|------|-----|---------|
| JWT_SECRET | JWT हस्ताक्षर कुंजी | erikwang2013/jwt-webman | 64+ वर्ण यादृच्छिक स्ट्रिंग |
| JWT_ALGORITHM | JWT हस्ताक्षर एल्गोरिदम | वही | HS256 बनाए रखें |
| HASHIDS_SALT | ID एन्कोडिंग साल्ट | erikwang2013/hashids | यादृच्छिक स्ट्रिंग |
| SNOWFLAKE_DATACENTER_ID | डेटासेंटर ID (0-31) | erikwang2013/snowflake-php | सिंगल डेटासेंटर डिफ़ॉल्ट रखें |
| ENCRYPTION_KEY | API ट्रांसमिशन परत एन्क्रिप्शन कुंजी | erikwang2013/encryption | 32 बाइट यादृच्छिक स्ट्रिंग |
| ENCRYPTABLE_KEY | DB स्टोरेज परत एन्क्रिप्शन कुंजी | erikwang2013/encryptable | 32 बाइट यादृच्छिक स्ट्रिंग, ट्रांसमिशन कुंजी से अलग |

**सुरक्षा आवश्यकताएँ**:
- `.env` फ़ाइल `.gitignore` में जोड़ी गई है, संस्करण रिपॉजिटरी में सबमिट करना सख्त वर्जित
- `.env.example` सार्वजनिक टेम्पलेट फ़ाइल है, इसमें वास्तविक कुंजियाँ नहीं होतीं
- उत्पादन वातावरण में **अनिवार्य रूप से** सभी डिफ़ॉल्ट कुंजियों को यादृच्छिक स्ट्रिंग से बदलें
- कुंजी जनरेशन के लिए `openssl rand -base64 32` उपयोग करने की सलाह

| परत | कॉन्फ़िग कुंजी | कुंजी पर्यावरण चर |
|----|--------|-------------|
| ट्रांसमिशन एन्क्रिप्शन | `config/encryption.php` → `key` | `ENCRYPTION_KEY` |
| स्टोरेज एन्क्रिप्शन | `config/encryptable.php` → `key` | `ENCRYPTABLE_KEY` |

## 10. security.txt (RFC 9116)

सिस्टम `/.well-known/security.txt` पर RFC 9116 मानक के अनुरूप सुरक्षा संपर्क जानकारी एंडपॉइंट प्रदान करता है, ताकि सुरक्षा शोधकर्ता भेद्यता खोजने पर रिपोर्ट चैनल जल्दी पा सकें।

**पहुंच विधि**:

```
GET /.well-known/security.txt
```

**रिस्पॉन्स सामग्री**:

```text
Contact: mailto:security@erik.xyz
Expires: 2027-05-20T00:00:00.000Z
Preferred-Languages: zh, en
Canonical: https://erik.xyz/.well-known/security.txt
Policy: https://erik.xyz/security-policy
```

**फ़ील्ड विवरण**:

| फ़ील्ड | विवरण |
|------|------|
| Contact | सुरक्षा भेद्यता रिपोर्ट संपर्क विधि |
| Expires | फ़ाइल समाप्ति समय, नियमित अपडेट आवश्यक |
| Preferred-Languages | पसंदीदा संचार भाषा |
| Canonical | इस फ़ाइल का कैनोनिकल URL |
| Policy | सुरक्षा नीति/भेद्यता प्रकटीकरण नीति लिंक |

यह एंडपॉइंट रेट लिमिट, प्रमाणीकरण जैसे मिडलवेयर प्रतिबंधों से मुक्त है, कोई भी सीधे पहुंच सकता है।

## 11. Nginx सुरक्षा कॉन्फ़िग

प्रोजेक्ट `nginx-security.conf` को उत्पादन वातावरण के Nginx रिवर्स प्रॉक्सी सुरक्षा सुदृढ़ीकरण संदर्भ कॉन्फ़िग के रूप में प्रदान करता है।

**शामिल सुरक्षा उपाय**:

| कॉन्फ़िग आइटम | भूमिका |
|--------|------|
| `server_tokens off` | Nginx संस्करण संख्या छिपाता है |
| `client_max_body_size 10m` | अनुरोध बॉडी आकार सीमित करता है, SecurityFilter के साथ समन्वित |
| `limit_req_zone` | Nginx स्तर पर अनुरोध आवृत्ति सीमा |
| `limit_conn_zone` | समवर्ती कनेक्शन संख्या सीमा |
| `add_header` सुरक्षा हेडर | Nginx स्तर पर X-XSS-Protection जैसे सुरक्षा हेडर जोड़ता है |
| `if ($request_method)` | Nginx स्तर पर गैर-मानक HTTP विधियाँ अस्वीकार करता है |
| SSL/TLS कॉन्फ़िग | आधुनिक TLS 1.2/1.3 कॉन्फ़िग, कमजोर सिफर सूट अक्षम |
| बैकएंड हेडर छिपाना | `proxy_hide_header` webman संस्करण जैसे संवेदनशील हेडर हटाता है |

**उपयोग विधि**: `nginx-security.conf` की कॉन्फ़िग को अपने Nginx server ब्लॉक में विलय करें, वास्तविक डोमेन और प्रमाणपत्र पाथ के अनुसार समायोजित करें।

## 12. खतरा मॉडल

### 12.1 संरक्षित खतरे

| खतरा प्रकार | हमला वेक्टर | रक्षा परतें |
|----------|---------|---------|
| HTTP विधि दुरुपयोग | TRACE/TRACK XST हमला, CONNECT टनल प्रॉक्सी, WebDAV विधि प्रोबिंग | SecurityFilter 405 विधि व्हाइटलिस्ट (GET/POST/PUT/DELETE/OPTIONS/HEAD) |
| लक्षित ब्रूट-फोर्स | विशिष्ट उपयोगकर्ता के खिलाफ बार-बार पासवर्ड प्रयास | खाता लॉक (5 विफलताओं पर 15 मिनट लॉक) + RateLimit (लॉगिन 10/मिनट) + Captcha |
| ब्रूट-फोर्स | वितरित IP से बार-बार उपयोगकर्ता नाम/पासवर्ड प्रयास | RateLimit (लॉगिन 10/मिनट) + Captcha |
| XSS क्रॉस-साइट स्क्रिप्टिंग | `<script>`, onerror, javascript: | SecurityFilter (5 पैटर्न) + X-XSS-Protection रिस्पॉन्स हेडर + CSP |
| SQL इंजेक्शन | UNION SELECT, OR 1=1, कमेंट बायपास | SecurityFilter (6 पैटर्न) + Eloquent ORM पैरामीटराइज़्ड क्वेरी |
| CSRF क्रॉस-साइट अनुरोध फोर्जरी | दुर्भावनापूर्ण वेबसाइट अनुरोध भेजना | SecurityFilter Origin/Referer सत्यापन |
| पाथ ट्रैवर्सल | `../../etc/passwd` | SecurityFilter पाथ ट्रैवर्सल पैटर्न + UploadController एक्सटेंशन व्हाइटलिस्ट |
| कमांड इंजेक्शन | `;ls`, `` `whoami` ``, `$(cat ...)` | SecurityFilter (4 पैटर्न) |
| सत्र हाईजैक | JWT Token चुराना | JWT अल्पकालिक वैधता (2h) + ब्लैकलिस्ट लॉगआउट + संवेदनशील ऑपरेशन द्वितीय पासवर्ड पुष्टि |
| ID एन्यूमरेशन | संख्यात्मक ID ट्रैवर्स कर डेटा मात्रा अनुमान | Hashids यादृच्छिक स्ट्रिंग में ऑब्स्क्यूरेशन |
| डेटा लीक | DB डंप / मिडलमैन / लॉग लीक | तीन-परत एन्क्रिप्शन/मास्किंग + OperationLog संवेदनशील फ़ील्ड फ़िल्टर |
| DoS हमला | बड़ा अनुरोध बॉडी / उच्च आवृत्ति अनुरोध | अनुरोध बॉडी 10MB सीमा + RateLimit 60/मिनट + IP ब्लैकलिस्ट |
| अनुमति वृद्धि | कम अनुमति वाला उपयोगकर्ता प्रबंधन इंटरफ़ेस पहुँचता है | RBAC method.path ग्रैन्युलैरिटी प्रमाणीकरण |
| फ़ाइल अपलोड हमला | shell.php.png डबल एक्सटेंशन | SecurityFilter दुर्भावनापूर्ण फ़ाइल पहचान |

### 12.2 ज्ञात सीमाएँ

| सीमा | प्रभाव क्षेत्र | शमन उपाय |
|------|---------|---------|
| CSRF सुरक्षा केवल ब्राउज़र के लिए प्रभावी | गैर-ब्राउज़र क्लाइंट (curl, Postman, मोबाइल App) Origin/Referer जाँच को बायपास कर सकते हैं | गैर-ब्राउज़र क्लाइंट स्वाभाविक रूप से CSRF हमलों से मुक्त; JWT प्रमाणीकरण पर निर्भरता, Cookie के बजाय |
| Redis अनुपलब्ध होने पर रेट लिमिट और ब्लैकलिस्ट fail-open होते हैं | हमलावर रेट लिमिट और उच्च आवृत्ति रोकथाम को बायपास कर सकता है | Redis उपलब्धता अलर्ट की निगरानी; JWT अल्पकालिक वैधता बैकअप के रूप में |
| कोई स्वतंत्र WAF इंजन नहीं | SecurityFilter `@preg_match` रेगेक्स मिलान उपयोग करता है, समर्पित WAF नियम इंजन नहीं | उत्पादन में Nginx ModSecurity या Cloudflare WAF लगाने की सलाह |
| JWT स्टेटलेस, सक्रिय रूप से अमान्य नहीं किया जा सकता | Token समाप्त होने से पहले सर्वर से सक्रिय रूप से रद्द नहीं किया जा सकता (ब्लैकलिस्ट को छोड़कर) | ब्लैकलिस्ट + अल्पकालिक 2h TTL जोखिम विंडो कम करता है |
| IP ब्लैकलिस्ट केवल मेमोरी में | Redis रीस्टार्ट पर ब्लैकलिस्ट खो जाती है | प्रतिबंध अवधि केवल 15 मिनट, प्रभाव सीमित |
| एडमिन एंडपॉइंट पर विशेष रेट लिमिट नहीं | एडमिन इंटरफ़ेस सामान्य इंटरफ़ेस के साथ 60/मिनट डिफ़ॉल्ट सीमा साझा करता है | एडमिन ऑपरेशन आवृत्ति स्वाभाविक रूप से कम, अभी विभेदन आवश्यक नहीं |
| `@preg_match` त्रुटि दबाता है | विकृत रेगेक्स इनपुट पर मौन विफलता | `preg_last_error()` से निगरानी जोड़ी जा सकती है, वर्तमान में लागू नहीं |
