## 2. Архитектура бэкенда

### 2.1 Слоистая структура

| Слой | Каталог | Обязанности |
|---|------|------|
| Маршруты | `config/route.php` | сопоставление URL с контроллерами, привязка middleware, версионированные маршруты |
| Middleware | `app/middleware/` | блокировка атак (SecurityFilter), лимит запросов (RateLimit), аутентификация (JWT), авторизация (RBAC), версия API (ApiVersion) |
| Контроллеры | 14 шт.: Dashboard/User/Role/Permission/Config/Log/Profile/Export/Import/Upload/Health/Docs (админка) + Captcha/Auth (API v1) | валидация параметров запроса, вызов бизнес-логики, форматирование ответа |
| Бизнес-сервисы | `app/service/` | переиспользуемая бизнес-логика (зарезервировано) |
| Модели данных | `app/model/` | ORM-сопоставление, связи, шифрование/дешифрование полей |
| Общие утилиты | `app/common/` | сервисы Hashids, Snowflake, Encryption |

### 2.2 Жизненный цикл запроса

```
Запрос клиента
  │
  ▼
webman HTTP Server (workerman)
  │
  ▼
Сопоставление Route
  │
  ▼
Цепочка middleware:
  SecurityFilter ──────► проверка HTTP-метода → 405 (только GET/POST/PUT/DELETE/OPTIONS/HEAD)
  │                     блокировка XSS/SQL-инъекций/обхода путей/инъекций команд/CSRF (403)
  ▼
  RateLimit ───────────► лимит скользящим окном Redis
  │ (при превышении 429 + заголовок Retry-After)
  ▼
  ApiVersion ─────────► проверка заголовка API-Version, внедрение $request->apiVersion
  │ (при ошибке 400)
  ▼
  AdminAuth ──────────► проверка JWT, внедрение $request->adminId
  │ (при ошибке 401)
  ▼
  AdminPermission ────► проверка прав RBAC (кэш Redis 60s)
  │ (при ошибке 403)
  ▼
  OperationLog ───────► запись журнала операций (POST/PUT/DELETE), автодетект источника
  │
  ▼
Controller::method()
  │
  ├─► валидация параметров (validator)
  ├─► подтверждение чувствительных операций (confirmPassword)
  ├─► decodeId() — hashid → BIGINT
  ├─► операции Model (автоматическое шифрование/дешифрование encryptable)
  ├─► encodeId() — BIGINT → hashid
  └─► Response JSON
```

### 2.3 Жизненный цикл ID

```
Генерация (Snowflake) → хранение (MySQL BIGINT) → передача (Hashids-кодирование) → наружу (строка hash)
                                                                    │
                            HashidsService::decode() ←──────────────┘
```

### 2.4 Система шифрования данных

```
Транспортный слой (encryption)     — AES-256-CBC, отдельный ключ
Слой хранения (encryptable)        — AES-128-ECB, отдельный ключ, автобработка через $casts Model
Слой отображения (mask)            — телефон: 138****1234, email: a***@example.com
```

### 3.3 Спецификация первичного ключа

- Тип: `BIGINT UNSIGNED NOT NULL`
- Особенность: **без автоинкремента**, генерируется на прикладном уровне алгоритмом Snowflake
- Преимущества: глобальная уникальность, распределённая дружественность, трендовый рост полезен для индексов, не раскрывает объём бизнеса
- Конфигурация: datacenter_id(0-31) + worker_id(0-31), поддержка 1024 узлов конкурентно

## 4. Дизайн API

### 4.1 Спецификация URL

```
Публичные интерфейсы:  /api/captcha/{generate|verify}
           /api/auth/{login|register|refresh}

Админка:   /admin/{resource}[/{hashid}]
          /admin/export/{excel|pdf}

Маршруты ресурсов:
  GET    /admin/user          → список
  POST   /admin/user          → создание
  GET    /admin/user/{hashid} → детали
  PUT    /admin/user/{hashid} → обновление
  DELETE /admin/user/{hashid} → удаление (требуется подтверждение паролем)

Системная конфигурация:  /admin/config[/{hashid}]
Журнал операций:  /admin/log
Личный кабинет:  /admin/profile[/password|/logout]
Импорт:     /admin/import/users
Загрузка:     /admin/upload
Массовые:     /admin/user/batch/{destroy|status}
Документация:     /api/docs     (OpenAPI 3.0)
Здоровье:     /health
```

### 4.2 Стратегия версий API

Версия API задаётся заголовком запроса, **в пути URL не отражается**:

```http
API-Version: v1
```

| Механизм | Описание |
|------|------|
| Версия по умолчанию | при отсутствии заголовка `API-Version` — по умолчанию `v1` |
| Проверка | middleware `ApiVersion`, неподдерживаемая версия возвращает 400 |
| Маршруты | вспомогательная функция `v()` динамически разрешает класс контроллера по версии |
| Каталоги | контроллеры сгруппированы по версиям: `app/api/{version}/controller/` |

Пример расширения — добавление API v2:
1. Создайте `app/api/v2/controller/AuthController.php`
2. В константе `SUPPORTED` middleware `ApiVersion` добавьте `'v2'`
3. Определения маршрутов менять не нужно

```bash
# использование v1
curl -H "API-Version: v1" /api/auth/login

# использование v2
curl -H "API-Version: v2" /api/auth/login

# без заголовка, по умолчанию v1
curl /api/auth/login
```

### 4.3 Политика лимита запросов

Алгоритм скользящего окна на Redis Sorted Set, атомарное выполнение Lua-скрипта:

| Интерфейс | Ограничение |
|------|------|
| По умолчанию | 60 раз/мин/IP/маршрут |
| POST /api/auth/login | 10 раз/мин |
| POST /api/auth/register | 5 раз/мин |

При превышении возвращается 429, заголовки ответа содержат X-RateLimit-Limit / Remaining / Reset / Retry-After.

### 4.4 Единый формат ответа

```json
{
  "code": 0,
  "message": "success",
  "data": { ... }
}
```

| code | Значение | Сценарий |
|------|------|---------|
| 0 | Успех | обычный ответ |
| 400 | Ошибка параметров | неверный формат запроса |
| 401 | Не аутентифицирован | Token отсутствует/просрочен/недействителен |
| 403 | Нет прав | роль пользователя не содержит требуемое право |
| 404 | Не существует | ресурс не найден |
| 422 | Ошибка валидации | параметры формы не соответствуют правилам / неверное подтверждение пароля |
| 500 | Ошибка сервера | непредвиденное исключение |

### 4.5 Процесс аутентификации (включая капчу по клику)

```
Клиент                               Сервер
  │                                    │
  │  ① POST /api/captcha/generate     │ captcha_create('click')
  │◄── {key, image(base64), targets}  │
  │                                    │
  │  ② пользователь нажимает           │
  │     на позицию текста на картинке  │
  │                                    │
  │  ③ POST /api/auth/login           │
  │     {username, password,          │
  │      captcha_key, clicks}         │
  │────────────────────────────────►  │
  │                                    │ ① captcha_verify()
  │                                    │ ② password_verify()
  │                                    │ ③ jwt()->create()
  │◄── {access_token, refresh_token}  │
  │                                    │
  │  ④ GET /admin/dashboard           │
  │     Authorization: Bearer xxx     │
  │────────────────────────────────►  │ AdminAuth → AdminPermission
  │◄── 200 {dashboard data}           │
```

### 4.6 Модель прав (RBAC)

```
  Пользователь ──┬── Роль ──┬── Право
  User            Role        Permission
                 │
                 ├── type=1: меню (управляет видимостью боковой панели)
                 ├── type=2: кнопка (управляет операциями на странице)
                 └── type=3: API  (управляет доступом к интерфейсам)

  Формат идентификатора права: {method}.{path}
  Пример: get.admin/user  post.admin/user  delete.admin/user
  Идентификатор суперадминистратора: * (пропускает все проверки прав)
```

### 4.7 Повторное подтверждение чувствительных операций

При удалении пользователей, ролей, прав и других чувствительных операциях нужно передать в теле запроса пароль текущего пользователя для повторной проверки личности:

```
Клиент                           Сервер
  │                                │
  │  DELETE /admin/user/{hashid}  │
  │  { password: "******" }       │
  │────────────────────────────►  │
  │                                │ confirmPassword(adminId, password)
  │                                │ → неверный пароль возвращает 422
  │                                │ → верный пароль — продолжает выполнение
  │◄── 200 { code: 0 }           │
```

Перед выполнением операции удаления фронтенд показывает диалог подтверждения, собирает пароль пользователя и отправляет запрос.

## 6. Дизайн безопасности

### 6.1 Эшелонированная защита

| Уровень | Меры |
|------|------|
| Ограничение методов | SecurityFilter: белый список HTTP-методов, только GET/POST/PUT/DELETE/OPTIONS/HEAD, нестандартные методы возвращают 405 |
| Блокировка атак | middleware SecurityFilter: детект и блокировка XSS/SQL-инъекций/обхода путей/инъекций команд/CSRF |
| Проверка «человек или машина» | капча по клику (Click Captcha), обязательная проверка при входе/регистрации |
| Блокировка аккаунта | 5 неудачных входов подряд — блокировка на 15 минут, в период блокировки возвращается 429 |
| Ограничение сессий | у одного пользователя максимум 3 параллельных Token, при превышении самый старый Token автоматически в чёрный список |
| Лимит запросов | middleware RateLimit, скользящее окно Redis, атомарность Lua |
| CSP | заголовок Content-Security-Policy ограничивает источники ресурсов, защита от XSS и инъекций данных |
| Подтверждение операций | удаление и другие чувствительные операции требуют повторного ввода пароля текущего пользователя |
| Передача | HTTPS + JWT Bearer Token |
| ID интерфейсов | шифрование Hashids, наружу невозможно восстановить реальный ID |
| Тело запроса | AES-256-CBC шифрование чувствительных полей |
| База данных | первичный ключ BIGINT (не раскрывает шаг автоинкремента) |
| База данных | AES-128-ECB шифрование хранения чувствительных полей |
| Аутентификация | JWT HS256, срок 2 ч + refresh token |
| Авторизация | RBAC, контроль прав с гранулярностью method.path |
| Аудит | OperationLog фиксирует все операции (включая автодетект источника source) |

### 6.2 Управление ключами

```
JWT_SECRET          → внедрение через переменную окружения, случайная строка 64 символа
HASHIDS_SALT        → уникальная соль, при утечке требуется глобальная замена
ENCRYPTION_KEY      → ключ шифрования передачи API, 32 байта
ENCRYPTABLE_KEY     → ключ шифрования хранения в БД, независим от ключа передачи
SCOUT_HOSTS         → адрес ES, развёртывание во внутренней сети
```

### 6.3 Защита чувствительных данных

| Сценарий | Поле | Меры |
|------|------|------|

### 8.2 Docker Compose (рекомендуется для продакшена)

`docker-compose.yml` в корне проекта оркестрирует все сервисы указанной топологии:

| Сервис | Образ/сборка | Порт | Описание |
|------|----------|------|------|
| `nginx` | nginx:alpine | 80, 443 | обратный прокси + статические файлы + Gzip |
| `app` | локальная сборка `Dockerfile` | 8787 | PHP 8.3 + OPcache + webman |
| `mysql` | mysql:8.0 | 3306 | основная БД, постоянный том данных |
| `redis` | redis:7-alpine | 6379 | кэш / лимит запросов / капча |
| `elasticsearch` | elasticsearch:8.x | 9200 | полнотекстовый поиск |

Перед запуском замените ключи `JWT_SECRET`, `HASHIDS_SALT`, `ENCRYPTION_KEY` в `docker-compose.yml` на случайные строки.

```bash
cp .env.docker .env
docker-compose up -d
```

### 8.3 CI/CD

Непрерывная интеграция GitHub Actions определена в `.github/workflows/ci.yml`:
- Проверка синтаксиса PHP (`php -l`)
- Юнит-тесты PHPUnit
- Статический анализ Flutter (`flutter analyze`)

### 8.4 Резервное копирование базы данных

`database/backup/backup.sh` — резервная копия mysqldump + gzip, автоматическая очистка бэкапов старше 30 дней.
`database/backup/restore.sh` — интерактивный выбор и восстановление бэкапа.

### 8.5 Мониторинг

Эндпоинт `GET /metrics` (`MetricsController`) отдаёт в формате Prometheus text 5 метрик gauge: общее количество HTTP-запросов, количество активных пользователей, статус подключения к БД/Redis, объём используемой памяти.
