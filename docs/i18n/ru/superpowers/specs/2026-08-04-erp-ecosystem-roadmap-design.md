## 2. Общая стратегия

```
Последовательный каскад: P0 → P1 → P2 → P3
Подзадачи с независимостью внутри каждого этапа можно вести параллельно
```

### 2.1 Выбор технологий фронтенда

- **Web-панель управления**: Flutter Web, переиспользование существующего кода `apps/flutter`, стиль PC-панели управления, управление состоянием GetX
- **Мобильный**: Flutter (iOS/Android), общий с Web бизнес-код `apps/flutter/lib/app/`
- **HarmonyOS**: ArkTS, выравнивание по функционалу Flutter

### 2.2 Стратегия бэкенда

- **Промышленный уровень** (класс A): двойная запись, расчёт зарплаты, движок MRP — полные алгоритмы, полная обработка граничных случаев, готово к продакшену
- **Ядро работает** (класс B): управление качеством, система уведомлений, BI-панели — реализованы ключевые правила, дальнейшая итерация по потребности

## 4. P1 — Глубина бизнеса (4-6 недель)

> **Цель**: модернизировать ключевые модули со скелета CRUD до настоящих движков бизнес-расчётов

### 4.1 Движок двойной записи в финансах (промышленный уровень)

```
app/service/finance/
├── DoubleEntryService.php        # проверка баланса дебета и кредита + автогенерация проводок
├── PeriodCloseService.php        # закрытие периода (перенос прибыли/перенос затрат)
├── AccountBalanceService.php     # сводка остатков по счетам (помесячно/поквартально/по годам)
├── ConsolidationService.php      # консолидированная отчётность в мультивалюте (пересчёт по курсу)
└── FinancialRatioService.php     # автоматический расчёт финансовых коэффициентов

app/controller/finance/
├── PeriodCloseController.php     # операция закрытия периода
├── AccountBalanceController.php  # запрос остатков по счетам
└── FinancialRatioController.php  # запрос анализа коэффициентов
```

**Ключевые правила**:
- При сохранении документа принудительно действует «нет дебета без кредита, дебет и кредит должны быть равны»
- Проверенный документ нельзя изменить, требуется сторно красным
- Закрытие периода: остатки счётов категории прибылей/убытков → прибыль текущего года, поддержка многошагового переноса
- Мультивалюта: пересчёт по курсу на конец периода, автоматический расчёт курсовых разниц

### 4.2 Движок расчёта зарплаты (промышленный уровень)

```
app/service/hr/
├── SalaryEngineService.php       # главный движок расчёта зарплаты
├── SocialInsuranceService.php    # расчёт соцстрахования (пенсионное/медицинское/по безработице/производственный травматизм/по беременности)
├── HousingFundService.php        # расчёт жилищного фонда
├── TaxCalculatorService.php      # расчёт подоходного налога по прогрессивным ставкам
└── BankPayrollService.php        # экспорт файлов банковской выплаты зарплаты

app/controller/hr/
└── PayrollController.php         # расчёт/выплата/запрос зарплаты
```

**Ключевые правила**:
- Верхний/нижний предел базы соцстрахования (ежегодно корректируется городами, конфигурируется)
- База жилищного фонда + ставка взносов (5%-12%, конфигурируется)
- Таблица прогрессивных ставок подоходного налога (3%-45%, годовой перерасчёт)
- Формат банковской выплаты: поддержка основных банков ICBC/BOC/CCB/CMB и др.
- Генерация расчётных листков (со всеми деталями)

### 4.3 Движок MRP (промышленный уровень)

```
app/service/manufacturing/
├── MrpEngineService.php           # главный движок расчёта MRP
├── DemandForecastService.php      # сводка потребностей (заказы+прогноз+страховой запас)
├── NetRequirementService.php      # расчёт чистой потребности (валовая-в наличии-в пути)
├── BomExplosionService.php        # разворачивание BOM (послойно до сырья)
└── OrderSuggestionService.php     # генерация предложений по заказам (закупка/производство/аутсорсинг)

app/model/
├── MfgMrpRunLog.php              # журнал расчётов MRP
└── MfgOrderSuggestion.php        # предложения по заказам
```

**Ключевые правила**:
- Послойное разворачивание BOM с учётом нормы потерь
- Чистая потребность = валовая потребность - остатки на складе - в пути + уже распределённое + страховой запас
- Код нижнего уровня (LLC) гарантирует однократный расчёт одного материала
- Обратный расчёт даты предлагаемого заказа по времени упреждения
- Правила партий: фиксированная партия/экономичная партия/по потребности

## 11. Риски и их снижение

| Риск | Влияние | Меры снижения |
|------|------|----------|
| Производительность Flutter Web хуже нативного JS | Торможение больших таблиц | Клиентская пагинация + виртуальная прокрутка + Web Worker |
| Изменение законодательства в зарплатном движке | Некорректные результаты расчёта | Соцстрахование/налоговые ставки конфигурируются, без хардкода |
| Таймаут расчётов MRP на больших объёмах данных | Прерывание расчёта | Пакетная обработка + обратный вызов прогресса |
| Слишком много длинных WebSocket-соединений | Давление на память сервера | workerman от природы высококонкурентен + ограничение числа соединений |
| Упущение изоляции данных арендаторов | Утечка данных | Глобальный middleware TenantScope + покрытие тестами |

## 12. Что не делается (явные исключения)

- ❌ Без разбиения на микросервисы — текущей монолитной архитектуры достаточно, сложная логика инкапсулируется в сервисном слое
- ❌ Без Kubernetes — Docker Compose удовлетворяет текущий масштаб
- ❌ Без функций AI/ML — их нет в дорожной карте MVP
- ❌ Без разработки отдельных нативных iOS/Android-приложений — кроссплатформенный Flutter уже покрывает
- ❌ Без GraphQL — RESTful API достаточно, стратегия версий API зрелая
- ❌ Без электронной подписи/интеграции оборудования WMS (PDA/сканеры штрих-кодов) — только программный уровень
