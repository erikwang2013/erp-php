## Детали проблем второй ревизии (исправлены)

#### 🔴 N1. В конфигурации CI `working-directory` указывает на несуществующий каталог `service/`

**Файл**: `.github/workflows/ci.yml`

В workflow CI у **всех шагов** `working-directory` указывает на `service/`:
```yaml
- name: Install dependencies
  working-directory: service    # ❌ такого каталога нет
  run: composer install --no-interaction
```

composer.json/vendor в корне проекта находится в `/home/wwwroot/erp-php/`, каталога `service/` не существует, из-за чего **GitHub Actions CI вообще не запускался**.

Та же проблема в ключе composer-кэша: `hashFiles('service/composer.lock')` должно быть `hashFiles('composer.lock')`.

**Исправление**: удалить все строки `working-directory: service`, исправить путь кэша.

---

#### 🔴 N2. Сервисный слой критически отсутствует — 72 контроллера при 3 сервисах

Вся бизнес-логика встроена в контроллеры, что приводит к:

- сложности повторного использования кода, невозможности вызова бизнес-логики между модулями
- возможности только интеграционного тестирования, невозможности юнит-тестирования ядра бизнеса

**Исправление**: поэтапно выделять слой Service по модулям; контроллер отвечает только за запрос/ответ.

### Новые важные находки

#### 🟡 N3. Мёртвый код: `app/model/Test.php`

Модель `Test` на 33 строки сопоставляется с таблицей `test` и **нигде в кодовой базе не используется**. Временный файл, оставшийся с этапа разработки.

**Исправление**: удалить `app/model/Test.php`.

---

#### 🟡 N4. PHPStan в CI помечен как `continue-on-error: true`

PHPStan в CI имеет `continue-on-error: true` — даже новые ошибки не блокируют CI. Проверка PHPStan фактически фиктивна.

**Исправление**: изменить на `continue-on-error: false` или с baseline падать только при новых ошибках.

---

#### 🟡 N5. `config/dependence.php` пуст

Конфигурация зависимостей контейнера — пустой массив, возможности внедрения зависимостей webman не используются. Если слой Service будет расширяться, нужна слабая связность через контейнер.

**Исправление**: зарегистрировать Service-классы в конфигурации контейнера.

---

#### 🟡 N6. В Dockerfile отсутствует расширение Redis

В Dockerfile установлены `pcntl`, `event`, `gd`, `pdo_mysql`, но **расширение Redis не установлено**. Redis — обязательная зависимость RateLimit/Session/Queue/JWT-чёрного списка.

**Исправление**: добавить `pecl install redis && docker-php-ext-enable redis`.

---

#### 🟡 N7. База PHPStan — 6169 строк при Level 5

После предыдущих исправлений baseline разросся с 1419 до 6169 строк (возможно, из-за повышения level или расширения области сканирования). Level 5 PHPStan низковат для проекта на PHP 8.1+.

**Исправление**: поэтапно чистить baseline, повышать до Level 6-7.

## II. Ревизия безопасности

### 2.1 Сильные стороны безопасности

- **Многоуровневая цепочка промежуточного ПО**: Locale → Cors → SecurityFilter → RateLimit → Auth → Permission → OpsLog (9 промежуточных ПО)
- **Обнаружение атак уровня WAF**: XSS (5 шаблонов), SQL-инъекции (6 шаблонов), обход путей (3 шаблона), инъекции команд (4 шаблона), вредоносная загрузка файлов (2 шаблона)
- **Эскалация атак и баны**: 5 срабатываний/60 с → временный чёрный список Redis на 15 минут
- **Ограничение частоты**: Redis + атомарное скользящее окно Lua, вход (10 раз/мин), регистрация (5 раз/мин)
- **JWT-чёрный список**: поддержка активного аннулирования токенов
- **Журнал операций**: полная запись операций записи, чувствительные поля password/token/secret автоматически маскируются
- **Хеширование паролей**: единообразно `password_hash(PASSWORD_BCRYPT)`
- **Проверка CSRF Origin/Referer**: SecurityFilter выполняет междоменную проверку операций записи
- **security.txt (RFC 9116)**: `/.well-known/security.txt` настроен
- **Заголовки безопасности ответа**: CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy
- **Принудительная проверка Content-Type**: POST/PUT обязаны объявлять `application/json` или `application/x-www-form-urlencoded`
- **Ограничение размера тела запроса**: максимум 10 МБ
- **Белый список HTTP-методов**: только GET/POST/PUT/DELETE/OPTIONS

### 2.2 Исправленные проблемы безопасности

- ✅ 120/121 модель защищена через `$guarded`/`$fillable`
- ✅ `app.debug` через переменную окружения
- ✅ Cookie сессии `secure`/`same_site` через переменные окружения
- ✅ CVE symfony/polyfill-intl-idn обновлён

### 2.3 Остаточные риски безопасности

Общее качество проекта **хорошее**. Проблемы безопасности P0 (защита массового присваивания, захардкоженная конфигурация) решены и проверены в предыдущей ревизии.

**Три ключевые проблемы этой ревизии**:

1. **Ошибка пути `service/` в конфигурации CI** — все шаги CI полностью неработоспособны, это самая срочная проблема (исправляется за 10 минут)
2. **Сервисный слой критически отсутствует** — 72 контроллера при 3 сервисах, бизнес-логика связана с обработкой запросов; это крупнейший архитектурный технический долг
3. **В Dockerfile нет расширения Redis** — влияет на RateLimit/Session/чёрный список в Docker-среде

После исправления проблемы пути CI (P0) рекомендуется в первую очередь выработать архитектурные стандарты слоя Service и в следующих итерациях функций постепенно переносить бизнес-логику из контроллеров в сервисы.
