## О проекте

open-erp — это **открытая полнофункциональная ERP-система** для малого и среднего бизнеса, охватывающая полный цикл закупок, продаж и складского учёта, финансовый учёт, производство (BOM/MRP/сдельная оплата по операциям/загрузка мощностей), CRM, workflow согласования, управление персоналом, уведомления и пользовательские отчёты. Бэкенд построен на webman v2 + MySQL 8.0 (префикс таблиц `erp_`, глобально уникальные первичные ключи Snowflake); панель управления реализована в трёх вариантах — Angular 22 (`apps/angular/`), React 19 + Vite (`apps/react/`) и Flutter 3.x Web (`apps/flutter/`), мобильный клиент — нативный HarmonyOS (`apps/harmonyos/`).

Ключевая идея системы — **документ как движок, автоматические связи**: утверждение бизнес-документа автоматически запускает движение запасов, формирование дебиторки/кредиторки и отнесение затрат; workflow согласования и уведомления пронизывают все ключевые документы; MRP рассчитывает потребность в материалах по заказам на продажу и BOM и формирует предложения по закупке/производству, замыкая сквозной цикл от приёма заказа до приёмки закупки и от планирования производства до закрытия периода в финансах.

## Описание проекта

- **Точная десятичная арифметика**: суммы, количества и веса считаются через bcmath, скользящая средневзвешенная себестоимость, взаимозачёт дебиторки/кредиторки и вывод отчётов дают строковую точность без ошибок плавающей точки
- **Корпоративный базовый уровень безопасности**: JWT-токены + RBAC-авторизация на уровне методов, эшелонированная оборона (панорама уровней L0–L12 + 35 классов детекторов атак + цепочка из 7 middleware: XSS/SQL-инъекции/CSRF/лимит запросов/CSP и др.), шифрование хранения чувствительных полей и шифрование передачи в API, полный аудит операций
- **Конфигурируемость**: многоузловые workflow согласования (включая полотно визуального конструктора процессов), движок шаблонов печати документов (подстановка плейсхолдеров + вывод PDF через dompdf + этикетки с QR-кодом), блокировка по кредитному лимиту клиента в реальном времени, сквозная прямая и обратная прослеживаемость партий/серийных номеров
- **Прослеживаемость данных**: каждое движение фиксируется построчно, партии и серийные номера проходят весь жизненный цикл приход → выдача → расход → прослеживание, себестоимость считается до строки документа
- **Простота развёртывания**: запуск одной командой через Docker Compose v2 (MySQL/Redis/Elasticsearch), локально достаточно `composer install`
- **Интернационализация**: 13 языков (zh/en/ja/ko/de/fr/es/pt/ru/ar/hi/bn/id), сообщения бэкенда и интерфейсы обеих веб-панелей Angular/React покрыты полностью, словари фронтенда загружаются лениво по языкам, README дополнительно доступен на 12 языках

## Модули ERP

Потоки данных между бизнес-модулями:

- Приёмка закупок → автоматическое оприходование (скользящее средневзвешенное) → автоматическая кредиторка
- Отгрузка продаж → автоматическое списание → автоматическая дебиторка
- Платежи → зачёт дебиторки/кредиторки → обновление журнала
- Проводки → автоматическое обновление Главной книги (по счетам) + вспомогательной книги (по операциям)
- Балансовый отчёт → автосводка исходящих остатков Главной книги
- Отчёт о движении денежных средств → автосводка кассового/банковского журнала (операционная/инвестиционная/финансовая деятельность)
- Workflow → бизнес-документы на согласование → многоузловое движение → результат согласования возвращается в модуль
- Уведомления → согласования/предупреждения/события системы → реальная рассылка → отметка о прочтении
- MRP → на основе заказов продаж + BOM → расчёт потребности в материалах → закупочные/производственные рекомендации
- OMS → импорт многоканальных заказов → резервирование остатков (ATP) → создание исполнения → передача в WMS на комплектацию/упаковку
- WMS → агрегация волн → задачи комплектации → подтверждение → завершение упаковки → генерация накладной TMS
- TMS → сравнение тарифов → создание накладной → подтверждение отгрузки (stockOut+AR) → трекинг → получение
- Поступление в WMS → ASN → приёмка → контроль качества → подтверждение размещения (stockIn+AP) → обновление остатков
- RMA → заявка на возврат → согласование → возврат на склад → возврат средств

## Интернационализация

Система поддерживает **13 языков**: `zh` (по умолчанию), `en`, `ja`, `ko`, `de`, `fr`, `es`, `pt`, `ru`, `ar`, `hi`, `bn`, `id`.

| Слой | Расположение словаря | Объём |
|---|---------|------|
| Сообщения бэкенда | `resource/translations/{язык}/` | 13 каталогов языков: `zh_CN` 565 записей, остальные 11 языков по 544 записи, `en` 30 записей (критерий: листовые записи; метки полей в `attributes` файла `validation.php` учитываются, ключи группировки — нет) |
| Веб-интерфейс админки Angular | `apps/angular/src/app/core/zh-*.ts` (исходный словарь `zh-en/`, 4 объединённых фрагмента) | Исходный словарь из 1456 ключей × 11 новых языков |
| Веб-интерфейс админки React | `apps/react/src/lib/i18n/zh*.ts` | Исходный словарь из 1451 ключа × 11 новых языков |

- **«Английский как ключ» на бэкенде**: ключи сообщений бэкенда сами являются английским текстом; в `en` поддерживается лишь небольшой набор сопоставлений (имена правил фреймворка и т. п.), полный словарь не нужен
- **Ленивая загрузка по языку**: 12 словарей фронтенда собираются каждый в отдельный chunk и подгружаются по требованию при смене языка, не увеличивая объём первой загрузки
- **Точки переключения**: отдельная иконка globe в верхней панели + выпадающее меню в личном кабинете (одинаково в Angular и React)
- **Уровень API**: автодетект по заголовку `Accept-Language` (zh-CN → китайский, en → English, остальные языки — по списку), по умолчанию китайский
- **Генераторы**: `scripts/gen-be-locales.mjs` (бэкенд), `scripts/gen-fe-locales.mjs --app angular|react` (фронтенд); поддерживают продолжение с точки останова

### Топология системы

![System Architecture](diagrams/system-architecture-cn.svg)

**Пятиуровневая архитектура**: клиентский слой → шлюз/пограничный слой (обратный прокси Nginx) → прикладной слой (webman v2 + цепочка middleware + аутентификация/авторизация + бизнес-логика + общие сервисы) → слой хранения (MySQL + Redis + Elasticsearch) → эксплуатационный слой (CI/CD + Docker + Prometheus)

### Бизнес-процессы

![Business Flowchart](diagrams/business-flowchart-cn.svg)

**Связка семи бизнес-доменов**: закупки → склад → продажи → финансы образуют ядро цепочки поставок; CRM управляет продажами; производственный MRP на основе заказов продаж + BOM формирует планы закупок и производства; workflow согласования, уведомления, проекты, HR — поддерживающие модули на всём пути.

**23 бизнес-домена, 227 таблиц, 159 контроллеров**: аутентификация/безопасность, дашборд, системное управление, защита, эксплуатация/мониторинг, товары, закупки, продажи, склад, финансы (14 подмодулей), CRM (10 подмодулей), workflow согласования, уведомления, проекты, HR, производство (MRP), пользовательские отчёты, OMS, WMS, TMS, QMS, EAM, DMS, BI-панели.

### Жизненный цикл запроса

![Request Lifecycle](diagrams/request-lifecycle-cn.svg)

**Полный путь запроса от клиента до БД**: клиент (Angular/React/Flutter/HarmonyOS) → Nginx (termination SSL) → CORS → фильтр безопасности → лимит запросов → [админка: JWT-аутентификация → RBAC → журнал операций] → контроллер → слой сервисов → слой моделей → кэш/БД/поиск → JSON-ответ. На диаграмме показаны пути попадания и промаха кэша. (Версия API уже включена в путь URL, отдельного шага проверки нет; язык определяется через `app/common/I18n.php` по заголовку `Accept-Language`.)

### Эшелонированная оборона

![Security Architecture](diagrams/security-architecture-cn.svg)

**Панорама эшелонированной обороны (L0–L12)**: L0 физическая сеть → L1 безопасность транспорта → L2 HTTP-заголовки безопасности → L3 проверка запросов → L4 очистка ввода → L5 защита CSRF → L6 лимит запросов → L7 аутентификация (JWT+Captcha+чёрный список+контроль сессий) → L8 авторизация RBAC → L9 защита данных (шифрование транспорта+хранения+обфускация ID+маскирование) → L10 аудит/мониторинг → L11 раскрытие для соответствия → L12 наблюдаемость (распределённая трассировка X-Trace-Id + бизнес-метрики + усиленный аудит). Исполняемая цепочка из 7 middleware описана в `docs/SECURITY.md`; 35 классов детекторов атак — в `config/plugin/erikwang2013/security-php/app.php`.

## Использование

### 1. Вход

При первом использовании откройте веб-установщик `http://localhost:8788/install`, чтобы завершить установку и создать учётную запись администратора. Если система уже установлена, откройте консоль, введите учётные данные и пройдите капчу с кликами для входа.

### 2. Навигация

После входа модули доступны через боковое меню: панель управления, товары, закупки, продажи, склад, финансы, CRM, workflow согласования, уведомления, проекты, персонал, производство, пользовательские отчёты, OMS/WMS/TMS, BI-панели и администрирование системы (пользователи/роли/конфигурация/журналы). На десктопе меню зафиксировано, на мобильных сворачивается в выдвижную панель.

### 3. Права и безопасность

- Функции и API управляются через RBAC; меню и интерфейсы без прав недоступны (403)
- Чувствительные операции (удаление пользователей/ролей) требуют повторного ввода текущего пароля в теле запроса
- После выхода токен немедленно попадает в чёрный список

### 4. Полнотекстовый поиск (опционально)

Синхронизация индекса реализована через `erikwang2013/webman-scout` (после добавления модели трейта `Searchable` индекс синхронизируется автоматически при сохранении). Поддерживаются два движка — **Elasticsearch** и **OpenSearch**, нужно выбрать один:

**① Установить соответствующий клиент (пакет Composer и драйвер должны совпадать, иначе появится ошибка "Please install the ... client")**

| Движок | Клиент Composer |
|---|---|
| Elasticsearch | `composer require elasticsearch/elasticsearch:^9.5` |
| OpenSearch | `composer require opensearch-project/opensearch-php:^2.0` |

**② Настроить `.env` и выбрать драйвер**

```ini
# elasticsearch | opensearch (должен совпадать с установленным выше клиентом)
SCOUT_DRIVER=opensearch
# Префикс имени индекса / шарды / реплики / размер пакета / мягкое удаление (общее для обоих движков)
SCOUT_PREFIX=erp_
SCOUT_SHARDS=1
SCOUT_REPLICAS=0
SCOUT_CHUNK_SIZE=500
SCOUT_SOFT_DELETE=true
```

**③ Настройка подключения (движки читают её из разных мест)**

- **Elasticsearch**: `SCOUT_HOSTS` в `.env` (несколько узлов через запятую, например `http://localhost:9200`), прямое подключение без аутентификации;
- **OpenSearch**: официальный образ по умолчанию включает плагин безопасности (самоподписанный TLS + аутентификация по аккаунту), настройки берутся из секции `opensearch` файла `config/scout.php`, `SCOUT_HOSTS` не читается:

  ```ini
  # .env
  SCOUT_OPENSEARCH_HOST=https://localhost:9200
  SCOUT_OPENSEARCH_USERNAME=admin
  SCOUT_OPENSEARCH_PASSWORD=ваш-пароль
  ```

  В `config/scout.php` секция `opensearch` по умолчанию содержит `ssl_verification=false` (локальный самоподписанный сертификат); в продакшене следует поставить `true` и настроить сертификаты, слабые пароли недопустимы.

> В Docker Compose этого проекта Elasticsearch встроен (сервис `open-admin-es`): при развёртывании через Docker выбирайте **драйвер elasticsearch + клиент ES**; для внешнего/отдельного контейнера OpenSearch — **драйвер opensearch + opensearch-php**.
>
> **Охват индексации**: все 224 модели в `app/model/` используют `Searchable`, запись в БД или мягкое удаление сразу синхронизирует индекс через `ModelObserver`; у четырёх из них — AdminUser, Customer, Product, Supplier — переопределён `toSearchableArray()` с белым списком полей, остальные модели индексируются по умолчанию (вся строка).
>
> **Недоступность движка не влияет на запись бизнес-данных** (проверено: после указания драйвера на недостижимый порт `save()` всё равно успешен, добавляется лишь одна задержка на таймаут соединения) — поисковый движок является опциональным компонентом, весь функционал работает и без него.
>
> **Оговорка об охвате**: в проекте сейчас подключена только **синхронизация индекса** (синхронизация при записи/мягком удалении), интерфейс поиска или страница поиска не предоставляются; при необходимости поиска вызывайте query-API Scout самостоятельно (фильтрация в списках админки выполняется серверными запросами `where` и не использует поисковый движок).

### Интернационализация

Заголовок `Accept-Language` автоматически переключает язык (zh-CN → китайский, en → English), по умолчанию китайский.

### Обработка ID

- **ID в запросах/ответах**: шифруются hashids в строки, реальные ID БД не раскрываются
- **Пути эндпоинтов**: `GET /admin/v1/user/{hashid}` — `{id}` в пути это hashid-строка
- **Хранение в БД**: исходное значение BIGINT, сгенерировано snowflake
- **Соглашение для фронтенда**: все `*_id` (включая идентификаторы строк деталей `items[].*_id`) передаются обратно как **непрозрачные строки**; запрещено преобразование через `Number()`/`parseInt()` и проверки на истинность — hashid может быть полностью цифровой строкой, и по самому значению его невозможно отличить от «голого» ID или sentinel-значения `0` (контракт — `tests/FieldContractRegressionTest.php`)

### Версия API

Версия API находится в пути URL (например, `/admin/v1/*`, `/api/v1/*`, `/open/v1/*`), **клиенту не нужен никакой заголовок версии**:

- Версионированные публичные интерфейсы напрямую привязаны к классу контроллера соответствующей версии (`app/api/v1/controller/`)
- Для новой версии регистрируется новая группа маршрутов `/api/vN`, контроллеры версии размещаются в `app/api/vN/`
- Прежний динамический разбор через `v()` и middleware заголовка `ApiVersion` удалены

### Лимит запросов

Алгоритм скользящего окна на Redis, по умолчанию 60 запросов/мин/IP/маршрут. Чувствительные эндпоинты строже:
- Вход: 10 запросов/мин
- Регистрация: 5 запросов/мин (по умолчанию выключено, включить через `REGISTRATION_ENABLED=1`)

Ответ содержит заголовки `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`. Превышение возвращает 429 с заголовком `Retry-After`.

### Архитектура middleware

Глобальные middleware применяются ко всем запросам по порядку:

```
Cors (предобработка CORS + заголовки ответа)
  → SecurityFilter (ограничение методов/размер тела/проверка Content-Type/XSS/SQL-инъекции/обход путей/инъекции команд/CSRF)
  → RateLimit (скользящее окно Redis + блокировка аккаунта: 5 неудач — блок 15 минут)
  → TracingId (идентификатор сквозного трассирования)
```

Middleware групп маршрутов: `/admin/v1` — `AdminAuth (JWT-аутентификация + чёрный список) → AdminPermission (RBAC) → OperationLog (автозапись POST/PUT/DELETE с определением источника)`; `/open/v1` — `OpenApiAuth`; обратный вызов трекинга TMS — `TrackingSignature`. Язык определяется в `app/common/I18n.php` по заголовку `Accept-Language`, это не middleware.

`/health`, `/api/docs` и `/install` — публичные эндпоинты, проходят только `Cors → SecurityFilter → RateLimit → TracingId`.

Усиление безопасности:
- **Блокировка аккаунта**: 5 неудачных входов подряд — аккаунт блокируется на 15 минут, вход возвращает 429
- **Ограничение параллельных сессий**: не более 3 действующих токенов на пользователя; при превышении самый старый токен автоматически попадает в чёрный список
- **security.txt**: `GET /.well-known/security.txt` предоставляет контактную информацию по стандарту RFC 9116
- **Конфигурация Nginx**: пример усиления обратного прокси — `docs/nginx-security.conf`

### Аутентификация

Вход и регистрация требуют проверки **капчи по клику**:

1. Клиент запрашивает `POST /api/v1/captcha/generate` и получает изображение капчи (base64 PNG) и список целей
2. Пользователь кликает по соответствующим местам на изображении в указанном порядке, собираются координаты кликов `[{x, y}, ...]`
3. При входе отправляются `captcha_key` и `clicks`; сервер сначала проверяет капчу, затем учётные данные

```http
POST /api/v1/auth/login
Content-Type: application/json

{
  "username": "admin",
  "password": "******",
  "captcha_key": "abc123...",
  "clicks": [{"x": 120, "y": 85}, {"x": 210, "y": 140}, {"x": 95, "y": 170}]
}
```

Дальнейшие запросы админки требуют JWT:

```http
Authorization: Bearer <token>
```

После успешного входа возвращается access_token (срок 2 часа) и refresh_token (срок 14 дней).

При выходе токен попадает в чёрный список Redis и не может использоваться до истечения срока. POST /admin/v1/profile/logout

### Повторное подтверждение чувствительных операций

Чувствительные операции (удаление пользователя, роли, прав и т.п.) требуют передачи `password` текущего пользователя в теле запроса для повторного подтверждения:

```http
DELETE /admin/v1/user/{id}
Content-Type: application/json
Authorization: Bearer <token>

{ "password": "******" }
```

### Процесс релиза (инкремент версии)

После push в `main` и успешного прохождения всех проверок php / docs / e2e задание `release` в `ci.yml` автоматически создаёт и отправляет новый тег версии по правилу **patch+1** от последнего тега (`v1.1.4` → `v1.1.5`), после чего создаёт одноимённый GitHub Release (`--generate-notes` формирует описание изменений автоматически).

- **Триггер**: только push в `main` (PR не запускает; push тега не соответствует фильтру ветки и не вызывает этот workflow рекурсивно)
- **Идемпотентность**: если тег или release с таким именем уже есть на удалённом репозитории (параллельный CI / проставлен вручную), шаг пропускается без ошибки
- **Локальная проверка**: `bash scripts/bump-version.sh --check` печатает следующую версию (только чтение, удалённый репозиторий не изменяется)
