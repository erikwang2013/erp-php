## Документация API

Проект автоматически генерирует интерактивную документацию API через [erikwang2013/apidoc-php](https://github.com/erikwang2013/apidoc-php).

**Доступ:** после запуска сервиса откройте `http://localhost:8788/apidoc`

**Группы документации:**
| Группа | Описание | Модулей |
|------|------|--------|
| Админка (Admin) | Все эндпоинты системы управления | 25 модулей |
| Клиентское API (Service API) | Лёгкие эндпоинты для мобильного/веб-клиента | 3 модуля |

**Глобальные заголовки запросов:**
| Заголовок | Описание |
|--------|------|
| `Authorization` | JWT Bearer Token |
| `Accept-Language` | Язык интернационализации, поддерживается 13 языков (zh/en/ja/ko/de/fr/es/pt/ru/ar/hi/bn/id), по умолчанию `zh_CN` |

> **О версиях**: версионирование через путь URL во всей системе — админка `/admin/v1`, клиент `/api/v1`, открытые интерфейсы `/open/v1`;
> номер версии находится в пути URL, **заголовок версии не требуется**; исключения: `GET /api/docs` (документация OpenAPI) и
> колбэк трекинга перевозчика `/api/tms/tracking/callback` (подпись HMAC, без версии).

**Соглашение об аннотациях:** все методы контроллеров аннотированы серией аннотаций `@Apidoc\*` с указанием имени интерфейса, описания, URL, метода запроса, параметров и структуры ответа.

## 1. Обзор

Открытая админка (open-admin) построена на webman v2 и предоставляет RESTful JSON API. Версионирование — через путь URL: эндпоинты админки смонтированы в `/admin/v1` (JWT-аутентификация + проверка прав RBAC), клиентские — в `/api/v1`, открытые — в `/open/v1`; номер версии включён в путь URL, заголовка версии нет.

- **Базовый URL**: `http://localhost:8788`
- **Версия API**: версионирование через путь URL, номер версии в пути (админка `/admin/v1`, клиент `/api/v1`, открытые интерфейсы `/open/v1`), заголовок версии не нужен

> **Обзор эндпоинтов**: аутентификация(5) | дашборд(1) | пользователи(7) | роли(4) | права(4) | конфигурация(4) | логи(1) | личный кабинет(3) | импорт/экспорт(3) | загрузка(1) | эксплуатация(4: health/metrics/docs/security.txt) | всего 37 эндпоинтов
- **Аутентификация**: `Authorization: Bearer <token>` (JWT)
- **Формат ответа**: `{ "code": 0, "message": "success", "data": {...} }`
- **Эндпоинт документации**: `GET /api/docs` возвращает спецификацию OpenAPI 3.0 JSON

### Интернационализация

API автоматически переключает язык по заголовку `Accept-Language`, поддерживается 13 языков: `zh_CN` (китайский, по умолчанию), `en` (English), `ja` (日本語), `ko` (한국어), `de` (Deutsch), `fr` (Français), `es` (Español), `pt` (Português), `ru` (Русский), `ar` (العربية), `hi` (हिन्दी), `bn` (বাংলা), `id` (Bahasa Indonesia).

| Первый языковой тег в заголовке | Разрешается в |
|---------|------|
| `zh`, `zh-CN`, `zh-TW` | `zh_CN` китайский (по умолчанию) |
| `en`, `en-US` | `en` English |
| `ja` / `ko` / `de` / `fr` / `es` / `pt` / `ru` / `ar` / `hi` / `bn` / `id` | соответствующий язык (региональный суффикс игнорируется, например `de-DE` → `de`) |

Правила разбора (`app/common/I18n.php` `getLocale()`):

- браузер упорядочивает теги по убыванию языковых предпочтений, **берётся только первый тег** (часть до запятой), значение q не разбирается;
- региональный подтег игнорируется, остаётся только основной языковой подтег (`zh-CN` → `zh`, `de-DE` → `de`);
- `zh*` всегда отображается в `zh_CN`; остальные основные языковые подтеги используются как есть;
- при отсутствии или пустом заголовке используется `config('translation.locale')` = `zh_CN`.

Цепочка отката (`trans()`): язык запроса → `zh_CN` → `en` → возврат самого ключа (английский как ключ, поэтому ключ и есть английский оригинал). **`en` в откате не участвует** — при запросе `en` ищется только словарь `en`, при отсутствии сразу возвращается key.

```bash
# ответ на английском
curl -H "Accept-Language: en" http://localhost:8788/admin/v1/product

# ответ на японском
curl -H "Accept-Language: ja" http://localhost:8788/admin/v1/product

# ответ на китайском (по умолчанию)
curl http://localhost:8788/admin/v1/product
```

Поле `message` в ответе возвращается на соответствующем языке. Файлы словарей находятся в `resource/translations/<locale>/{common,modules,validation}.php`.

### Требования к запросам

- Разрешены только методы `GET` / `POST` / `PUT` / `DELETE` / `OPTIONS` / `HEAD`; другие HTTP-методы (например, TRACE, CONNECT, PATCH) возвращают 405
- Все запросы `POST` / `PUT` должны указывать `Content-Type: application/json` (кроме загрузки файлов), иначе возвращается 415
- Размер тела запроса не должен превышать 10MB, иначе возвращается 413
- Фильтр безопасности сканирует все входные данные на XSS, SQL-инъекции, обход путей, инъекции команд — при срабатывании возвращается 403
- 5 неудачных входов подряд блокируют аккаунт (15 минут); во время блокировки вход возвращает 429
- Один пользователь может одновременно удерживать не более 3 действующих токенов; при превышении самый старый токен автоматически попадает в чёрный список

## 2. Коды ошибок

| code | Значение | Сценарии |
|------|------|---------|
| 0 | Успех | |
| 400 | Ошибка параметров запроса | Некорректный формат запроса |
| 401 | Не авторизован | Отсутствует / истёк / в чёрном списке |
| 403 | Нет прав / блокировка безопасности | Недостаточно прав RBAC / срабатывание SecurityFilter |
| 404 | Ресурс не найден | Цель запроса/обновления/удаления не существует |
| 405 | Метод не разрешён | Разрешены только GET/POST/PUT/DELETE/OPTIONS/HEAD, нестандартные методы отклоняются |
| 413 | Тело запроса слишком велико | Content-Length более 10MB |
| 415 | Неподдерживаемый тип носителя | Content-Type запроса POST/PUT не JSON и не загрузка файла |
| 422 | Ошибка валидации параметров | Отсутствуют обязательные поля, неверный формат, не пройдена бизнес-проверка |
| 429 | Слишком много запросов | Сработал RateLimit / блокировка аккаунта (5 неудачных входов подряд — блок 15 минут) |
| 500 | Внутренняя ошибка сервера | |

## 3. Публичные эндпоинты

```
GET /health
```

- **Аутентификация**: не требуется
- **Лимит запросов**: нет

**Пример ответа**:
```json
{
  "code": 0,
  "message": "success",
  "data": {
    "app": "open-admin",
    "version": "1.0",
    "php": "8.3.0",
    "database": "ok",
```

Значения `database`, `redis`, `elasticsearch`: `"ok"` | `"unavailable"`. `elasticsearch` возвращает `"unavailable"`, если ES недоступен; при статусе кластера не green/yellow возвращается фактическое значение status (например, `"red"`).

**Возможные ошибки**:

- 401: Неверное имя пользователя или пароль
- 403: Аккаунт отключён
- 429: Аккаунт заблокирован, повторите через 15 минут (срабатывает после 5 неудачных входов)

### 3.6 Регистрация

```
POST /api/v1/auth/register
```

- **Аутентификация**: не требуется
- **Версия**: путь URL содержит /api/v1, заголовка версии нет
- **Лимит запросов**: 5/мин (по IP + путь)
- **Переключатель**: по умолчанию выключен (`REGISTRATION_ENABLED=0`), при выключении возвращается 403; необходимо явно включить в `.env` (`REGISTRATION_ENABLED=1`)

**Тело запроса**:
```json
{
  "username": "newuser",
  "password": "123456",
  "real_name": "Новый пользователь",
  "captcha_key": "abc123def456",
  "clicks": [
    { "x": 120, "y": 85 },
    { "x": 310, "y": 42 }
  ]
}
```

| Поле | Тип | Обязательно | Правила валидации | Описание |
|------|------|------|---------|------|
| username | string | да | min:3, max:50 | Имя пользователя (уникальное) |
| password | string | да | min:6, max:32 | Пароль (хранится bcrypt-хэшем) |
| real_name | string | да | max:50 | Реальное имя |
| captcha_key | string | да | | key капчи |
| clicks | array{object} | да | min:2 | Массив координат кликов |

**Пример ответа**:
```json
{
  "code": 0,
  "message": "Регистрация успешна",
  "data": {
    "access_token": "eyJhbGciOiJIUzI1NiIs...",
    "refresh_token": "eyJhbGciOiJIUzI1NiIs...",
    "expires_in": 7200,
    "user": {
      "id": "e5f6g7h8",
      "username": "newuser",
      "real_name": "Новый пользователь"
    }
  }
}
```

После успешной регистрации сразу возвращаются JWT-токены, статус пользователя по умолчанию — включён (status=1). Эндпоинт доступен только при `REGISTRATION_ENABLED=1`.

### 10.3 Выход

```

```

- **Аутентификация**: JWT

**Тело запроса**: нет (без requestBody, токен читается из заголовка Authorization)

**Пример ответа**:
```json
{

  "message": "Вы вышли",
  "data": []
}
```

Логика выхода: декодируется JWT, вычисляется оставшийся срок действия (exp - now), md5-хэш токена записывается в чёрный список Redis `jwt_blacklist:{md5}` с TTL = оставшийся срок. Токены из чёрного списка блокируются в middleware `AdminAuth` с ответом 401.

Без токена возвращается 401. Если токен истёк/недействителен (декодирование бросило исключение), выход всё равно считается успешным.

## 13. Заголовки ответов

Все эндпоинты (инжектируются на уровне глобальных middleware) содержат следующие заголовки ответов:

| Заголовок | Описание |
|----|------|
| `X-RateLimit-Limit` | Верхняя граница лимита (число запросов) |
| `X-RateLimit-Remaining` | Оставшееся число запросов |
| `X-RateLimit-Reset` | Время сброса окна лимита |
| `Retry-After` | Возвращается только при срабатывании лимита, рекомендуемое число секунд ожидания |
| `X-Content-Type-Options` | `nosniff` (по умолчанию webman, запрет MIME-сниффинга) |
| `X-Frame-Options` | `DENY` (предоставляется CORS-промежуточным слоем/базовой конфигурацией webman) |

Детали лимита:
- Глобальный лимит по умолчанию: 60/мин / IP+путь
- Эндпоинт входа `/api/v1/auth/login`: 10/мин
- Эндпоинт регистрации `/api/v1/auth/register`: 5/мин
- Атомарный алгоритм скользящего окна на Redis (Lua ZSET), исключает гонки TOCTOU
- При недоступности Redis — fail open (пропуск), запросы не блокируются

## 14. Процесс аутентификации

Полная последовательность аутентификации:

```
1. Клиент запрашивает POST /api/v1/captcha/generate
   (путь URL содержит /api/v1, заголовка версии нет)
    ↓
   Сервер возвращает: key + изображение base64 + подсказки целей кликов

2. Пользователь кликает по целям на изображении, фронт/клиент собирает координаты кликов

3. Клиент запрашивает POST /api/v1/auth/login
   (заголовки: Content-Type: application/json; путь URL содержит /api/v1)
   тело: { username, password, captcha_key, clicks: [{x,y}, ...] }
    ↓
   Сервер:
   a. валидация параметров → 422
   b. проверка капчи → 422
   c. проверка учётных данных → 401
   d. проверка статуса аккаунта → 403
   e. выпуск JWT (access + refresh) → 200
   f. обновление last_login_at / last_login_ip
    ↓
   Клиент сохраняет: access_token, refresh_token, expires_in

4. Последующие запросы с JWT
   заголовок: Authorization: Bearer <access_token>
    ↓
   middleware AdminAuth:
   a. извлечение Bearer-токена
   b. проверка чёрного списка (Redis jwt_blacklist:{md5}) → 401
   c. декодирование JWT, проверка срока → 401
   d. установка $request->adminId = поле sub
    ↓
   middleware AdminPermission:
   a. разбор идентификатора прав для ресурсного маршрута
   b. запрос ролей пользователя → права ролей, сопоставление
   c. нет прав → 403
    ↓
   Controller обрабатывает запрос
    ↓
   Response + заголовки X-RateLimit-*

5. Обновление до истечения Access Token
   Клиент запрашивает POST /api/v1/auth/refresh
   тело: { refresh_token: "..." }
    ↓
   Сервер декодирует refresh_token → выпускает новые access + refresh
    ↓
   Клиент обновляет локальные токены

6. Выход
   Клиент запрашивает POST /admin/v1/profile/logout
   заголовок: Authorization: Bearer <access_token>
    ↓
   Сервер:
   a. декодирует JWT, получает оставшийся TTL
   b. записывает в чёрный список Redis: jwt_blacklist:{md5(token)} = 1, TTL = оставшийся срок
   c. возвращает успех
```

### Структура JWT

- **access_token**: `{ sub: <user_id>, username: "<name>" }`, TTL по умолчанию 7200 секунд (управляется конфигурацией JWT `default_expire`)
- **refresh_token**: `{ sub: <user_id>, token_type: "refresh" }`, TTL по умолчанию 1209600 секунд (управляется `refresh_expire`, т.е. 14 дней)

### Управление безопасностью

- Пароли хранятся хэшем `PASSWORD_BCRYPT`
- Чувствительные поля (phone, email, id_card) прозрачно шифруются/дешифруются на уровне БД через `erikwang2013/encryptable`
- ID на уровне API передаются зашифрованными через `erikwang2013/hashids`, чтобы не раскрывать последовательность исходных snowflake ID
- SecurityFilter глобально сканирует XSS, SQL-инъекции, обход путей, инъекции команд; один IP с 5 срабатываниями за 60 секунд попадает во временный чёрный список на 15 минут
- Чувствительные операции (удаление пользователя, роли, права, конфигурации) требуют повторного подтверждения паролем текущего пользователя
- Ограничение параллельных сессий: не более 3 действующих токенов на пользователя; при входе с 4-го устройства самый старый токен принудительно попадает в чёрный список
- Блокировка аккаунта: 5 неудачных входов подряд — блокировка на 15 минут, во время блокировки возвращается 429

### 16.19 Кросс-модульная автоматизация

Следующие эндпоинты запускают кросс-модульную автоматизацию, помечены 🔗:

| Эндпоинт | Автоматические действия |
|------|---------|
| 🔗 POST /admin/v1/purchase/receive | Автоматический вызов InventoryService.stockIn() — обновление остатков + пересчёт скользящего средневзвешенного; вызов FinanceService.createAp() — генерация записи кредиторки |
| 🔗 POST /admin/v1/sales/delivery | Автоматический вызов InventoryService.stockOut() — списание (по скользящему средневзвешенному); вызов FinanceService.createAr() — генерация записи дебиторки |
