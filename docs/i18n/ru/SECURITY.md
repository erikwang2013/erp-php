## 1. Обзор многоуровневой защиты

Система использует модель защиты из 7 уровней: злонамеренные запросы отфильтровываются снаружи внутрь, гарантируя, что при отказе любого отдельного уровня остаются последующие рубежи обороны.

Вся цепочка промежуточного ПО выполняется в следующем порядке (см. `config/middleware.php`):

```
Запрос → Cors → SecurityFilter → RateLimit → [промежуточное ПО группы маршрутов: AdminAuth → AdminPermission → OperationLog] → Controller
```

| Уровень | Промежуточное ПО/механизм | Цель защиты |
|---------|---------------------------|-------------|
| 1 | SecurityFilter | Блокировка XSS / SQL-инъекций / обхода путей / инъекций команд / CSRF-атак |
| 2 | Cors | Безопасность междоменных запросов + внедрение заголовков безопасности ответа |
| 3 | RateLimit | Скользящее окно ограничения на Redis, защита от перебора |
| 4 | AdminAuth | JWT-аутентификация + чёрный список при выходе |
| 5 | AdminPermission | Авторизация RBAC с гранулярностью method.path |
| 6 | OperationLog | Аудит операций + трассировка клиента |
| 7 | Шифрование данных | Hashids-обфускация ID + шифрование Encryptable в БД + шифрование передачи EncryptionService |

Клиент (Flutter) имеет собственную независимую проверку ввода, бэкенд не доверяет клиенту — каждый уровень защищается независимо.

## 2. Движок обнаружения атак

### 2.0 Ограничение HTTP-методов

SecurityFilter перед всеми проверками атак сначала проверяет HTTP-метод, разрешены только стандартные методы:

```
GET, POST, PUT, DELETE, OPTIONS, HEAD
```

Нестандартные методы (например, TRACE, CONNECT, PATCH, пользовательские методы и т. д.) сразу возвращают **405 Method Not Allowed** с пустым HTML-телом ответа, не переходя к дальнейшему обнаружению атак или бизнес-логике.

Это первый рубеж многоуровневой защиты, эффективно предотвращает:
- Межсайтовое отслеживание TRACE (XST)
- Злоупотребление CONNECT-туннелями через прокси
- Зондирование нестандартных методов WebDAV
- Перечисление HTTP-методов автоматическими сканерами

### 2.1 XSS (межсайтовый скриптинг)

Все регулярные выражения взяты из `SecurityFilter::PATTERNS['XSS']`, сопоставление без учёта регистра.

| Шаблон обнаружения | Регулярное выражение | Защищает от атак |
|--------------------|----------------------|------------------|
| Теги script | `<\s*\/?\s*s\s*c\s*r\s*i\s*p\s*t\b` | `<script>`, `<script >`, `< script>` и другие варианты с пробелами |
| Атрибуты событий | `\bon\w+\s*=\s*[\"\']?\s*(?:javascript\|vbscript):` | Инлайн-события вида `onclick="javascript:..."` |
| Псевдопротокол JS | `(?:javascript\|vbscript)\s*:\s*(?:[^\s]*\s*)?(?:eval\|alert\|prompt\|confirm\|document\.cookie\|location\s*=)` | `javascript:eval(...)`, `javascript:alert(1)` и т. п. |
| Data URI XSS | `data\s*:\s*text\s*\/\s*html\s*(?:;base64)?\s*,` | `data:text/html,<script>`, `data:text/html;base64,...` и т. п. |
| Инъекция шаблонов | `\{\{.*?\}\}` | Инъекции шаблонов серверных/Angular/Vue, напр. `{{constructor}}`, `{{7*7}}` |

### 2.2 SQL-инъекции

| Шаблон обнаружения | Регулярное выражение | Защищает от атак |
|--------------------|----------------------|------------------|
| UNION-запросы | `\bUNION\s+(?:ALL\s+)?SELECT\b` | Слив базы через `UNION SELECT`, `UNION ALL SELECT` |
| OR-всегда-истина | `(?:[\"\']\s*OR\s+[\"\']?\s*\d+\s*=\s*\d+\|[\"\']\s*OR\s+[\"\']?1[\"\']?\s*=\s*[\"\']?1)` | `' OR 1=1--`, `" OR '1'='1'` |
| Разрушение структуры таблиц | `\b(?:DROP\|ALTER\|TRUNCATE)\s+(?:TABLE\|DATABASE\|INDEX\|VIEW)\b` | `DROP TABLE users`, `TRUNCATE TABLE logs` |
| Вызов хранимых процедур | `\b(?:xp_cmdshell\|sp_executesql\|sp_addsrvrolemember)\b` | Выполнение команд через расширенные хранимые процедуры MSSQL |
| Зондирование метаданных | `\b(?:INFORMATION_SCHEMA\|sys\.(?:tables\|columns\|databases)\|pg_class\|sqlite_master\|mysql\.(?:user\|db))\b` | Зондирование структуры БД MySQL/PG/SQLite/MSSQL |
| Обход через комментарии | `(?:[\"\'])\s*(?:--\|#)\s*[\"\']?\s*(?:OR\|AND\|SELECT\|INSERT\|UPDATE\|DELETE\|DROP)` | Обход через комментарии: `'-- OR SELECT`, `'# AND UPDATE` |

### 2.3 Обход путей

| Шаблон обнаружения | Регулярное выражение | Защищает от атак |
|--------------------|----------------------|------------------|
| Возврат по каталогам | `\.\.[\/\\\\]{2,}` | Многоуровневый возврат `../`, `..\`, `....//` |
| Зондирование чувствительных файлов | `\/(?:etc\/(?:passwd\|shadow\|hosts)\|proc\/self\|boot\.ini\|win\.ini\|WEB-INF\|\.env\|\.git\/)` | `/etc/passwd`, `/proc/self/environ`, `.env`, `.git/HEAD` и т. п. |
| Усечение нулевым байтом | `%00` | Обход проверки расширения через `../../../etc/passwd%00.jpg` |

### 2.4 Инъекции команд

| Шаблон обнаружения | Регулярное выражение | Защищает от атак |
|--------------------|----------------------|------------------|
| Команды через конвейер/точку с запятой | `[;\|&]\s*(?:ls\|cat\|rm\|wget\|curl\|nc\|bash\|sh\|cmd\|powershell\|python\|perl)\b` | `;cat /etc/passwd`, `\|bash` |
| Подстановка через обратные кавычки | `` `[^`]*\b(?:cat\|ls\|id\|whoami\|pwd\|rm\|wget\|curl)\b[^`]*` `` | `` `cat /etc/passwd` `` |
| Подстановка $() | `\$\(\s*(?:cat\|ls\|id\|whoami\|rm\|wget\|curl)\b` | `$(whoami)`, `$(cat flag)` |
| Удалённая загрузка через конвейер | `(?:wget\|curl)\s+.*(?:\b-o\b\|\b-O\b\|pipe\|bash\|python).*\bhttps?:\/\/` | `wget URL -O - \| bash`, `curl URL \| python` |

### 2.5 CSRF (межсайтовая подделка запросов)

Логика проверки реализована в `SecurityFilter::checkCsrf()`:

```php
// Проверка срабатывает только для POST/PUT/DELETE
// Если и Origin, и Referer пусты → пропуск (не браузерный клиент)
// Если Origin не пуст → сравнение домена Origin с Host
```

Правила сравнения:
- Убрать префикс `www.` у Host и точно сравнить с доменом Origin
- Если Host — родительский домен Origin (например, `Origin: app.example.com`, `Host: example.com` — срабатывает `str_contains($originHost, '.' . $hostOnly)`), пропустить
- Ни точное совпадение, ни субдомен → вернуть 403, квалифицировать как CSRF-атаку

Примечание: не браузерные клиенты (например, curl без Origin/Referer) пропускаются напрямую; защита CSRF действует только в браузерной среде.

### 2.6 Вредоносная загрузка файлов

| Шаблон обнаружения | Регулярное выражение | Защищает от атак |
|--------------------|----------------------|------------------|
| Маскировка двойным расширением | `\.(?:php\d?\|phtml\|phar\|cgi\|pl\|py\|jsp\|asp)x?\.(?:png\|jpg\|gif\|pdf)` | Обход белого списка через `shell.php.png`, `shell.phar.jpg` |
| Расширение PHP | `\.php\s*$/m` | Передача пути `.php` прямо в параметрах запроса |

## 3. Эскалация атак и IP-чёрный список

SecurityFilter имеет встроенный механизм эскалации атак для защиты от непрерывного сканирования с одного IP.

### Процесс эскалации

```
1-е попадание сканера → Redis INCR security_escalate:{ip} = 1, TTL=60s
2-е попадание сканера → INCR → 2
...
5-е попадание сканера → INCR → 5
    → Срабатывание блокировки: SETEX security_ban:{ip} 900 1
    → Очистка счётчика DEL security_escalate:{ip}
    → Запись в журнал безопасности: [SECURITY] IP banned 15min
```

### Поведение в период блокировки

Каждый запрос при входе в SecurityFilter сначала проверяет `isBanned()`:

```php
if (Redis::get("security_ban:{$ip}")) {
    return response('<h1>403 Forbidden</h1>', 403);
}
```

Заблокированный IP в течение 15 минут получает 403 на все запросы (включая легитимные), последующая бизнес-логика полностью пропускается.

### Константы конфигурации

| Константа | Значение | Смысл |
|-----------|----------|-------|
| ESCALATE_LIMIT | 5 | Порог срабатываний в окне 60 с |
| ESCALATE_WINDOW | 60 | Окно счётчика (секунды) |
| BAN_DURATION | 900 | Длительность чёрного списка (секунды), т. е. 15 минут |

### Журнал безопасности

Расположение файла: `runtime/logs/security.log`

Пример формата журнала:
```
2026-05-20 14:32:11 [SECURITY] XSS attack blocked | IP: 192.168.1.100 | Path: /admin/user | Field: body.username | Source: body | Payload: <script>alert(1)</script>
2026-05-20 14:32:15 [SECURITY] IP banned 15min | IP: 192.168.1.100 | Triggers: 5
```

### Ограничение размера тела запроса

`Content-Length > 10MB` → сразу возвращается 413 Payload Too Large, защита от DoS-атак со сверхбольшими телами запросов.

### Проверка Content-Type

Запросы POST/PUT **обязаны** объявлять `Content-Type` как `application/json` или `application/x-www-form-urlencoded`, иначе возвращается 415 Unsupported Media Type. Запросы с загрузкой файлов (с полем file) пропускают эту проверку.

## 4. Заголовки безопасности ответа

Все заголовки внедряются в промежуточном ПО `Cors` через `$response->withHeaders()` и добавляются к каждому ответу.

| Заголовок | Значение | Назначение |
|-----------|----------|------------|
| Access-Control-Allow-Origin | `*` | Разрешены кросс-доменные запросы из любых источников (сценарий внутренней админ-панели) |
| Access-Control-Allow-Methods | `GET,POST,PUT,DELETE,OPTIONS` | Разрешённый набор методов |
| Access-Control-Allow-Headers | `Authorization,Content-Type,API-Version` | Разрешённые пользовательские заголовки |
| Access-Control-Max-Age | `86400` | Кэширование preflight-запроса на 24 часа |
| X-Content-Type-Options | `nosniff` | Запрет MIME-сниффинга браузера |
| X-Frame-Options | `DENY` | Запрет встраивания в любые iframe, защита от кликджекинга |
| X-XSS-Protection | `1; mode=block` | Включение встроенного XSS-фильтра браузера с блокировкой отрисовки страницы |
| Referrer-Policy | `strict-origin-when-cross-origin` | На том же источнике отправляется полный URL, кросс-доменно — только домен |
| Permissions-Policy | `camera=(), microphone=(), geolocation=()` | Отключение API камеры/микрофона/геолокации на всём сайте |

OPTIONS-preflight запросы сразу возвращают пустой ответ 204, не переходя в дальнейшую цепочку промежуточного ПО.

### 4.2 Content-Security-Policy (CSP)

Внедряется вместе с другими заголовками безопасности в промежуточном ПО Cors, обеспечивая защиту в глубину — ограничение источников ресурсов, которые браузер может загружать и выполнять.

| Заголовок | Значение | Назначение |
|-----------|----------|------------|
| Content-Security-Policy | `default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` | Ограничение источников скриптов/стилей/изображений/соединений/фреймов/форм и других ресурсов |
| X-Permitted-Cross-Domain-Policies | `none` | Запрет загрузки кросс-доменных файлов политик Adobe Flash/PDF |

Ключевые пункты политики CSP:
- `default-src 'self'`: по умолчанию разрешены только ресурсы того же источника
- `script-src 'self' 'unsafe-inline' 'unsafe-eval'`: разрешены скрипты того же источника + инлайн-скрипты (необходимо для Flutter Web) + eval (необходимо для отладки Flutter Web)
- `frame-ancestors 'none'`: запрет встраивания в iframe любой страницей — двойная страховка с X-Frame-Options: DENY
- `base-uri 'self'`: ограничение тега `<base>` только тем же источником
- `form-action 'self'`: формы могут отправляться только на тот же источник

## 5. Стратегия ограничения частоты

### Алгоритм

Redis Sorted Set (скользящее окно) + атомарный Lua-скрипт, ключевые операции:

```lua
-- 1. Очистка старых записей за пределами окна
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, windowStart)
-- 2. Проверка счётчика текущего окна
local count = redis.call('ZCARD', KEYS[1])
-- 3. При превышении лимита вернуть {0, count}, иначе ZADD и вернуть {1, count+1}
if count >= limit then return {0, count} end
redis.call('ZADD', KEYS[1], now, now . '.' . random)  -- случайный суффикс против перезаписи в ту же миллисекунду
redis.call('EXPIRE', KEYS[1], window + 10)
```

Lua-скрипт выполняется на сервере Redis в один поток — **естественно атомарно**, устраняя состояние гонки TOCTOU (Time-of-check to Time-of-use).

### Конфигурация ограничения

| Маршрут | Лимит | Окно | Сценарий |
|---------|-------|------|----------|
| По умолчанию (все маршруты) | 60 раз/мин | 60с | Общий API |
| `/api/auth/login` | 10 раз/мин | 60с | Вход (защита от перебора) |
| `/api/auth/register` | 5 раз/мин | 60с | Регистрация (защита от массовой регистрации; по умолчанию выключена, включается `REGISTRATION_ENABLED=1`) |

### Заголовки ответа

При срабатывании ограничения возвращается HTTP 429 с JSON-телом:
```json
{"code": 429, "message": "Слишком много запросов, попробуйте позже", "data": []}
```

Все ответы (включая обычные) несут следующие заголовки:

| Заголовок | Описание |
|-----------|----------|
| X-RateLimit-Limit | Максимальное число запросов, разрешённых в текущем окне |
| X-RateLimit-Remaining | Оставшееся число запросов в текущем окне |
| X-RateLimit-Reset | Unix-временная метка сброса окна |
| Retry-After | Только при ограничении, рекомендуемое число секунд ожидания |

### Стратегия деградации

При сбое Redis (таймаут соединения, недоступность и т. п.) — **fail-open**:

```php
try {
    $result = Redis::eval($lua, ...);
} catch (\Throwable $e) {
    return $handler($request); // Redis недоступен, пропустить все запросы
}
```

Лучше на короткое время потерять защиту от ограничения, чем блокировать нормальные бизнес-запросы.

### 5.4 Механизм блокировки учётной записи

Интерфейс входа помимо ограничения частоты дополнительно имеет механизм **блокировки учётной записи** для защиты от целенаправленного перебора по конкретному пользователю.

**Процесс блокировки**:

```
Неудачный вход → Redis INCR account_lockout:{userId} TTL=900s
5 неудач подряд → Redis SETEX account_locked:{userId} 900 1
                → Возврат 429 «Учётная запись заблокирована, попробуйте через 15 минут»
                → Очистка счётчика DEL account_lockout:{userId}
```

**Поведение в период блокировки**:

Все запросы входа в период блокировки сразу возвращают 429 без проверки пароля — попытки перебора полностью исключены.

**Константы конфигурации**:

| Константа | Значение | Смысл |
|-----------|----------|-------|
| MAX_LOGIN_ATTEMPTS | 5 | Максимальное число последовательных неудач |
| LOCKOUT_DURATION | 900 | Длительность блокировки (секунды), т. е. 15 минут |

Примечание: блокировка основана на `userId`, а не на IP, поэтому смена IP не обходит блокировку. В сочетании с IP-ограничением (10 раз/мин) образуется двойная защита:
- На уровне IP: 10 раз/мин ограничивает распределённый перебор
- На уровне учётной записи: блокировка после 5 неудач ограничивает целевой перебор

## 6. Аутентификация и авторизация

### 6.1 JWT-аутентификация

Реализована в промежуточном ПО AdminAuth, монтируется на группах маршрутов, требующих аутентификации.

**Настройка параметров** (`config/plugin/erikwang2013/jwt/jwt`, значения из `.env`):

| Параметр | Значение | Описание |
|----------|----------|----------|
| Алгоритм | HS256 | Симметричная подпись HMAC-SHA256 |
| Ключ | `JWT_SECRET` | Из переменной окружения, в проде обязателен к замене |
| TTL access_token | 7200с (2ч) | `JWT_TTL` |
| TTL refresh_token | 1209600с (14д) | `JWT_REFRESH_TTL` |
| Эмитент | `open-admin` | `JWT_ISSUER` |
| Аудитория | `open-admin` | `JWT_AUDIENCE` |

**Извлечение токена**: из заголовка `Authorization: Bearer <token>`, снятие префикса `Bearer ` даёт исходный JWT.

**Процесс аутентификации**:
1. Пустой токен → сразу 401 `{"code": 401, "message": "Не выполнен вход"}`
2. Проверка чёрного списка Redis `jwt_blacklist:{md5(token)}` → попадание → 401 `Токен недействителен, войдите заново`
3. Декодирование JWT → ошибка (истёк/не совпала подпись) → 401 `Токен истёк или недействителен`
4. Успех → внедрение `$request->adminId` и `$request->adminUsername`

**Механизм чёрного списка**: при выходе пользователя `md5(token)` записывается в Redis с TTL, равным оставшемуся сроку действия JWT. При сбое Redis проверка чёрного списка пропускается (fail-open); в этом случае вышедший из системы токен может кратковременно использоваться, но короткий срок действия самого JWT (2ч) служит подстраховкой.

### 6.2 Ограничение параллельных сессий

Для защиты от злоупотребления токеном после утечки на нескольких устройствах система ограничивает число одновременно действительных токенов одного пользователя.

**Логика ограничения**:

```
Успешный вход → Выдача нового токена
              → Запрос числа действительных токенов пользователя: Redis SCARD user_tokens:{userId}
              → Если число >= 3 (MAX_CONCURRENT_SESSIONS):
                 → Сортировка по времени создания по возрастанию, удаление самого старого токена:
                   Redis SREM user_tokens:{userId} <oldest_token_id>
                   Redis SETEX jwt_blacklist:{md5(oldest_token)} TTL remaining
              → Добавление нового токена в набор: Redis SADD user_tokens:{userId} <new_token_id>
                 Redis SET user_token:{token_id} {userId} EX {TTL}
```

**Константы конфигурации**:

| Константа | Значение | Смысл |
|-----------|----------|-------|
| MAX_CONCURRENT_SESSIONS | 3 | Максимальное число параллельных токенов одного пользователя |

**Сценарий вытеснения**: когда пользователь входит на 4-м устройстве, токен 1-го устройства принудительно помещается в чёрный список, последующие запросы возвращают 401 «Токен недействителен, войдите заново».

При выходе текущий токен удаляется из набора. При естественном истечении токена Redis-ключ автоматически становится недействительным, число членов набора уменьшается.

### 6.3 Модель прав RBAC

Реализована в промежуточном ПО AdminPermission.

**Модель данных**: связь трёх уровней User -> Role -> Permission

- `erik_admin_user` (таблица пользователей)
- `erik_admin_user_role` (таблица связи пользователь-роль)
- `erik_admin_role` (таблица ролей)
- `erik_admin_role_permission` (таблица связи роль-право)
- `erik_admin_permission` (таблица прав)

**Типы прав**:
| type | Смысл | Пример |
|------|-------|--------|
| 1 | Право меню | Управление видимостью левой навигации |
| 2 | Право кнопки | Управление кнопками действий на странице (создание/редактирование/удаление) |
| 3 | Право API | Управление вызовом интерфейсов бэкенда |

Формат идентификатора права API: `{method}.{path}`

Например:
- `post.admin/user` — создание пользователя
- `put.admin/user` — редактирование пользователя
- `delete.admin/user` — удаление пользователя
- `get.admin/user` — просмотр списка пользователей

**Процесс авторизации**:
1. `$request->adminId` пуст → пропуск (маршрут не настроен на аутентификацию)
2. Получение пользователя → ролей (пропуск отключённых ролей `status=0`) → списка прав
3. Супер-администратор (`slug = '*'`) → прямой пропуск
4. Формирование `strtolower(method) . '.' . trim(path, '/')` → сравнение со списком прав
5. Нет совпадения → 403 `{"code": 403, "message": "Нет прав доступа"}`

**Повторное подтверждение**: BaseController предоставляет метод `confirmPassword()`; чувствительные операции (удаление пользователя, экспорт данных и т. д.) дополнительно требуют ввода текущего пароля на уровне контроллера, защищая от неавторизованных действий после перехвата сессии.

## 7. Журналы аудита

### 7.1 Журнал операций

Промежуточное ПО OperationLog автоматически записывает журнал операций для запросов POST / PUT / DELETE. GET-запросы не записываются.

**Записываемые поля**:

| Поле | Источник | Описание |
|------|----------|----------|
| id | SnowflakeService::generate() | Глобально уникальный ID |
| user_id | `$request->adminId` | ID оператора, 0 при отсутствии входа |
| action | `$request->method()` | Равно method |
| method | `$request->method()` | POST / PUT / DELETE |
| path | `$request->path()` | Путь запроса |
| ip | `$request->getRealIp()` | Реальный IP клиента |
| source | detectSource() | Платформа-источник клиента |
| input | Тело запроса (JSON после маскирования) | Отправленные данные операции |
| created_at | `date('Y-m-d H:i:s')` | Время операции |

**Фильтрация чувствительных полей**: рекурсивный обход тела запроса, значения следующих полей заменяются на `***`:

`password`, `old_password`, `new_password`, `new_password_confirmation`, `token`, `secret`, `access_token`, `refresh_token`

**Определение клиента** (`detectSource()`), по приоритету:

1. Сначала читается пользовательский заголовок `X-Client-Platform` (явное объявление нативного клиента)
2. Деградация до анализа строки User-Agent (порядок проверки в методе `detectSource()`):

| Платформа | Ключевые слова UA |
|-----------|-------------------|
| iPadOS | `iPad` |
| macOS | `Macintosh`, `Mac OS` |
| Windows | `Windows` |
| Linux | `Linux` |
| iOS | `iPhone`, `iOS`, `CFNetwork` |
| Android | `Android` |
| HarmonyOS | `HarmonyOS`, `OpenHarmony` |
| Web | Значение по умолчанию (последний вариант) |

**Устойчивость к ошибкам**: исключение при записи журнала не блокирует бизнес-запрос (`catch (\Throwable)` молча игнорируется).

### 7.2 Журнал безопасности

**Расположение файла**: `runtime/logs/security.log`

**Записываемое содержимое**:
- Журнал блокировок атак: категория атаки, IP, путь, поле, источник, фрагмент payload (первые 200 символов)
- Уведомления о блокировке IP: заблокированный IP, число срабатываний

Права записи в журнал: `FILE_APPEND | LOCK_EX` для безопасной записи при параллелизме.

## 8. Защита данных

Система использует трёхуровневую стратегию защиты данных, соответствующую трём этапам движения данных.

### 8.1 Транспортный уровень — EncryptionService

`EncryptionService` использует пакет `erikwang2013/encryption` для шифрования/дешифрования чувствительных полей в API-запросах/ответах.

**Технические детали**:
- Алгоритм: `aes-256-cbc-hmac` (встроенная HMAC-подпись против подделки)
- Ключ: переменная окружения `ENCRYPTION_KEY`, автоматическое выравнивание до 32 байт
- Используется для: передачи полей телефонного номера, номера удостоверения личности и т. п. между клиентом и API

**Вспомогательные методы маскирования**:
- `maskPhone('13812341234')` → `138****1234`
- `maskEmail('abc@example.com')` → `a***@example.com` (если имя пользователя длиннее 2 символов) или `a**@example.com`

### 8.2 Уровень хранения — Cast Encryptable

Модель `AdminUser` использует Eloquent cast `Erikwang2013\Encryptable\Encryptable`, соответствующие поля:

- `email` → cast в Encryptable, автоматическое шифрование/дешифрование
- `phone` → cast в Encryptable, автоматическое шифрование/дешифрование
- `id_card` → cast в Encryptable, автоматическое шифрование/дешифрование

При записи в базу данные автоматически шифруются в шифротекст, при чтении — автоматически расшифровываются. Тип колонки в БД — `VARCHAR(500)`, шифротекст хранится в base64.

**Система ключей**: независима от транспортного шифрования (`ENCRYPTION_KEY`) — используется `ENCRYPTABLE_KEY`; утечка одного ключа не выводит из строя другой уровень.

Ротация ключей: переменная окружения `ENCRYPTION_PREVIOUS_KEYS` поддерживает список исторических ключей (через запятую); при чтении старых данных пробуется расшифровка историческими ключами, при записи — повторное шифрование текущим ключом.

### 8.3 Уровень отображения — обфускация ID и маскирование

**Обфускация ID Hashids**: `HashidsService` использует пакет `erikwang2013/hashids`.

- BIGINT ID из БД, возвращаемые внешним API, кодируются в hash-строку (например, `xK3mN9qR2pL7wV8b`)
- Клиент передаёт hash-строку в запросах, бэкенд автоматически декодирует её в исходный ID
- Соль из переменной окружения `HASHIDS_SALT`; при разных солях результаты кодирования/декодирования полностью различаются
- Минимальная длина hash — 16 символов, используется 62-символьный буквенно-цифровой набор
- BaseController предоставляет удобные методы `encodeId()`, `decodeId()`, `encodeIds()`

**Маскирование при экспорте**: при экспорте Excel/PDF (ExportController) чувствительные поля единообразно маскируются:
- Телефон: `138****1234`
- Email: `a***@example.com`
- Удостоверение личности: полностью скрывается как `********`

## 9. Управление ключами

Все ключи внедряются через переменные окружения `.env`; файлы конфигурации читают их через `getenv()` со встроенными значениями по умолчанию (безопасно только в среде разработки).

| Переменная окружения | Назначение | Пакет | Требование для прода |
|----------------------|------------|-------|----------------------|
| JWT_SECRET | Ключ подписи JWT | erikwang2013/jwt-webman | Случайная строка из 64+ символов |
| JWT_ALGORITHM | Алгоритм подписи JWT | то же | Оставить HS256 |
| HASHIDS_SALT | Соль кодирования ID | erikwang2013/hashids | Случайная строка |
| SNOWFLAKE_DATACENTER_ID | ID центра обработки данных (0-31) | erikwang2013/snowflake-php | Оставить по умолчанию при одном ЦОД |
| ENCRYPTION_KEY | Ключ шифрования транспортного уровня API | erikwang2013/encryption | Случайная строка 32 байта |
| ENCRYPTABLE_KEY | Ключ шифрования уровня хранения БД | erikwang2013/encryptable | Случайная строка 32 байта, отличается от транспортного ключа |

**Требования безопасности**:
- Файл `.env` добавлен в `.gitignore`, строго запрещено коммитить в репозиторий
- `.env.example` — публичный файл-шаблон, реальных ключей не содержит
- В продакшене **обязательно** заменить все ключи по умолчанию на случайные строки
- Рекомендуется генерировать ключи командой `openssl rand -base64 32`

### Изоляция хранения ключей

| Уровень | Ключ конфигурации | Переменная окружения ключа |
|---------|-------------------|----------------------------|
| Транспортное шифрование | `config/encryption.php` → `key` | `ENCRYPTION_KEY` |
| Шифрование хранения | `config/encryptable.php` → `key` | `ENCRYPTABLE_KEY` |
| Обфускация ID | `config/hashids.php` → `connections.main.salt` | `HASHIDS_SALT` |
| Подпись JWT | `config/plugin/erikwang2013/jwt/jwt` | `JWT_SECRET` |

## 10. security.txt (RFC 9116)

Система предоставляет точку `/.well-known/security.txt` с контактной информацией безопасности по стандарту RFC 9116, чтобы исследователи безопасности быстро находили канал сообщения об уязвимостях.

**Способ доступа**:

```
GET /.well-known/security.txt
```

**Содержимое ответа**:

```text
Contact: mailto:security@erik.xyz
Expires: 2027-05-20T00:00:00.000Z
Preferred-Languages: zh, en
Canonical: https://erik.xyz/.well-known/security.txt
Policy: https://erik.xyz/security-policy
```

**Описание полей**:

| Поле | Описание |
|------|----------|
| Contact | Контакт для сообщения об уязвимостях безопасности |
| Expires | Дата истечения файла, требует периодического обновления |
| Preferred-Languages | Предпочтительные языки общения |
| Canonical | Канонический URL этого файла |
| Policy | Ссылка на политику безопасности/раскрытия уязвимостей |

Эта точка не ограничена промежуточным ПО (лимиты, аутентификация и т. п.), доступна любому напрямую.

## 11. Конфигурация безопасности Nginx

Проект предоставляет `nginx-security.conf` как эталонную конфигурацию усиления безопасности обратного прокси Nginx для продакшена.

**Включённые меры безопасности**:

| Пункт конфигурации | Назначение |
|--------------------|------------|
| `server_tokens off` | Скрытие номера версии Nginx |
| `client_max_body_size 10m` | Ограничение размера тела запроса, в связке с SecurityFilter |
| `limit_req_zone` | Ограничение частоты запросов на уровне Nginx |
| `limit_conn_zone` | Ограничение числа параллельных соединений |
| `add_header` заголовки безопасности | Добавление X-XSS-Protection и других заголовков безопасности на уровне Nginx |
| `if ($request_method)` | Отказ от нестандартных HTTP-методов на уровне Nginx |
| Конфигурация SSL/TLS | Современная конфигурация TLS 1.2/1.3, отключение слабых шифрнаборов |
| Скрытие заголовков бэкенда | `proxy_hide_header` удаляет чувствительные заголовки, такие как версия webman |

**Способ использования**: объедините конфигурацию из `nginx-security.conf` с вашим server-блоком Nginx, скорректировав домен и пути к сертификатам.

## 12. Модель угроз

### 12.1 Защищённые угрозы

| Тип угрозы | Вектор атаки | Уровни защиты |
|------------|--------------|---------------|
| Злоупотребление HTTP-методами | TRACE/TRACK XST, CONNECT-туннели, зондирование методов WebDAV | SecurityFilter — белый список методов 405 (GET/POST/PUT/DELETE/OPTIONS/HEAD) |
| Целевой перебор | Повторные попытки пароля по конкретному пользователю | Блокировка учётной записи (5 неудач → блокировка 15 мин) + RateLimit (вход 10/мин) + Captcha |
| Перебор | Распределённые IP повторно пробуют логин/пароль | RateLimit (вход 10/мин) + Captcha |
| XSS | `<script>`, onerror, javascript: | SecurityFilter (5 шаблонов) + заголовок X-XSS-Protection + CSP |
| SQL-инъекции | UNION SELECT, OR 1=1, обход через комментарии | SecurityFilter (6 шаблонов) + параметризованные запросы Eloquent ORM |
| CSRF | Подделка запросов со злонамеренных сайтов | Проверка Origin/Referer в SecurityFilter |
| Обход путей | `../../etc/passwd` | Шаблоны обхода путей в SecurityFilter + белый список расширений UploadController |
| Инъекции команд | `;ls`, `` `whoami` ``, `$(cat ...)` | SecurityFilter (4 шаблона) |
| Перехват сессии | Кража JWT-токена | Короткий срок JWT (2ч) + выход через чёрный список + повторное подтверждение пароля для чувствительных операций |
| Перечисление ID | Подбор числовых ID для оценки объёма данных | Обфускация Hashids в случайные строки |
| Утечка данных | Слив БД / man-in-the-middle / утечка журналов | Трёхуровневое шифрование/маскирование + фильтрация чувствительных полей OperationLog |
| DoS-атаки | Сверхбольшие тела запросов / высокая частота | Ограничение тела 10 МБ + RateLimit 60/мин + IP-чёрный список |
| Повышение привилегий | Доступ к административным интерфейсам пользователем с низкими правами | Авторизация RBAC с гранулярностью method.path |
| Атака при загрузке файлов | Двойное расширение shell.php.png | Обнаружение вредоносных файлов в SecurityFilter |

### 12.2 Известные ограничения

| Ограничение | Зона влияния | Меры смягчения |
|-------------|--------------|----------------|
| Защита CSRF действует только для браузеров | Не браузерные клиенты (curl, Postman, мобильные приложения) могут пропустить проверку Origin/Referer | Не браузерные клиенты по своей природе не подвержены CSRF; вместо Cookie используется JWT-аутентификация |
| При недоступности Redis ограничение и чёрный список деградируют до fail-open | Атакующий может обойти лимиты и блокировку высокой частоты | Мониторинг доступности Redis с оповещениями; короткий срок JWT как подстраховка |
| Нет отдельного WAF-движка | SecurityFilter использует сопоставление `@preg_match`, а не специализированный движок правил WAF | В проде рекомендуется Nginx ModSecurity или Cloudflare WAF перед системой |
| JWT без состояния нельзя принудительно аннулировать | До истечения токена сервер не может отозвать его активно (кроме чёрного списка) | Чёрный список + короткий TTL 2ч сокращают окно риска |
| IP-чёрный список хранится только в памяти | После перезапуска Redis чёрный список теряется | Длительность бана всего 15 минут, влияние ограничено |
| Нет особого ограничения для административных точек | Админ-интерфейсы разделяют общий лимит 60/мин | Частота админ-операций естественно низкая, различать пока не требуется |
| `@preg_match` подавляет ошибки | При некорректном regex молчаливый отказ | `preg_last_error()` можно мониторить; в текущей реализации не используется |
