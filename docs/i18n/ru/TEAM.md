## 3. Модели совместной работы

### 3.1 Общие правила (по корневому CLAUDE.md)

- **SendMessage-First**: agent общаются напрямую через SendMessage, без опроса и разделяемого изменяемого состояния;
- **Именование обязательно**: каждый agent должен быть назван (`name: "role"`);
- **Один спавн**: независимые подзадачи поднимаются в фоне одним разом, Lead останавливается и ждёт результат, не опрашивает статус;
- **Сообщение обязательно**: каждый prompt указывает «кому отправить SendMessage после завершения и что отправить».

### 3.2 Три оркестрационные топологии

| Режим | Поток | Сценарий использования |
|------|------|----------|
| **Pipeline** | Lead → архитектор → бэкенд → тест → рецензия | Разработка функций с последовательными зависимостями (новый модуль, межмодульный поток данных) |
| **Fan-out** | Lead → A, B, C → сводка у Lead | Параллельные независимые работы (несколько страниц, исследование нескольких модулей) |
| **Supervisor** | Lead ↔ участники, несколько раундов | Сложная работа с постоянной координацией (декомпозиция микросервисов, масштабный рефакторинг) |

### 3.3 Таблица маршрутизации задач

| Тип задачи | Оркестрация | Участвующие роли |
|----------|------|----------|
| Новый модуль / новая функция (например, углубление DMS, BI) | pipeline | Lead → архитектор (дизайн таблиц) → бэкенд → тест → рецензия |
| Алгоритмы движков (двойная запись / зарплаты / MRP) | pipeline + TDD | Lead → эксперт бизнес-движков (дизайн) → тест (граничные кейсы вперёд) → рецензия |
| Страницы фронтенда (Flutter / HarmonyOS параллельно) | fan-out | Lead → фронтенд×2 + бэкенд (выравнивание API) параллельно → сводка у Lead |
| Межмодульные потоки данных (закупки→склад→кредиторка и т.п.) | pipeline | Lead → архитектор → бэкенд → тест → рецензия |
| Декомпозиция микросервисов / масштабный рефакторинг | supervisor | Lead ↔ архитектор + бэкенд + рецензия, несколько раундов |
| Спецработы по безопасности / производительности | однониточное глубокое копание | Lead → инженер безопасности/DevOps → рецензия |
| Исправление багов (один файл / 1-2 строки) | вне команды | Lead обрабатывает сам, или делает 1 agent |
| Различия трёх веток / выпуск версий | pipeline | Lead → координатор версий → тест (регресс между ветками) → рецензия |

### 3.4 Качественный шлюз (обязателен перед коммитом, держит рецензент)

```
phpunit            # 137 тестов / 805 утверждений всё зелёное, новые кейсы коммитятся вместе с изменением
phpstan            # запрещены новые проблемы сверх baseline
php-cs-fixer       # --dry-run проходит
composer audit     # нет критичных уязвимостей зависимостей
```

Изменения, затрагивающие базу данных, обязательно проходят через архитектора (163 таблицы, schema: единственный источник истины — database/install.sql); изменения фронтенда обязательно прогоняют Flutter `flutter analyze` 0 error / 0 warning.

## 4. Рекомендации по размеру команды

| Формат работы | Рекомендуемый размер | Примечание |
|----------|----------|------|
| Повседневное обслуживание / мелкий ремонт | 1-2 человека | Lead обрабатывает сам, избегая чрезмерной оркестрации |
| Итерация одного модуля | 3 человека | Lead + бэкенд + тест |
| Кросс-модульная функция | 4-5 человек | Lead + архитектор + бэкенд + тест + рецензия |
| Параллельный фронтенд на двух платформах | 4-5 человек | Lead + Flutter + HarmonyOS + бэкенд (API) + тест |
| Движки / сложный рефакторинг | 5-7 человек | Всё вышеперечисленное + эксперт бизнес-движков или безопасность/DevOps |

> Совместимо с `.claude-flow/config.yaml` (`maxAgents: 15`, `hierarchical-mesh`, стратегия координации `consensus`), занятость одной задачи не превышает лимит.

## 5. Шаги внедрения

1. **Дополнить определения ролей**: в `.claude/agents/` уже есть planner / sparc / testing / swarm / consensus, не хватает пяти определений — `business-engineer`, `frontend-flutter`, `frontend-harmonyos`, `researcher`, `edition-coordinator`; добавьте по одному файлу в существующем формате YAML/MD — и монтирование готово;
2. **Закрепить маршрутизацию**: записать таблицу §3.3 в логику routing хуков `.claude-flow/hooks`, чтобы хук `UserPromptSubmit` автоматически направлял задачу соответствующей роли;
3. **Разделение памяти**: в `.claude-flow` уже включён `agentScopes` (`defaultScope: project`), рекомендуется хранить по четырём доменам `backend / frontend / ops / security`, чтобы контекст финансового движка не загрязнял фронтенд-задачи;
4. **Пилотный прогон**: выбрать одну кросс-модульную задачу (например, углубление DMS или итерация BI-панелей), полностью прогнать по §3.3, после проверки цепочки сообщений и шлюза — тиражировать.
