## 3. 協働パターン

### 3.1 通则（ルート CLAUDE.md を踏襲）

- **SendMessage-First**：agent 間は SendMessage で直接通信し、ポーリングせず、可変状態を共有しない；
- **命名必須**：各 agent に命名が必要（`name: "role"`）；
- **一度の spawn**：独立サブタスクは一括でバックグラウンド起動し、Lead は止まって結果を待ち、状態をポーリングしない；
- **メッセージ必携**：各 prompt に「完了したら SendMessage で誰へ何を送るか」を明記する。

### 3.2 3 種のオーケストレーション・トポロジー

| モード | フロー | 使用シーン |
|------|------|----------|
| **Pipeline** | Lead → アーキテクト → バックエンド → テスト → レビュー | 順序依存のある機能開発（新モジュール、モジュール横断データフロー） |
| **Fan-out** | Lead → A, B, C → Lead が集約 | 相互に独立した並行作業（複数ページ、複数モジュールの調査） |
| **Supervisor** | Lead ↔ メンバーの多ラウンド往復 | 継続的な調整が必要な複雑な作業（マイクロサービス分割、大規模リファクタリング） |

### 3.3 タスクルーティング表

| タスク種別 | 編成 | 参加ロール |
|----------|------|----------|
| 新モジュール / 新機能（例: DMS、BI 深化） | pipeline | Lead → アーキテクト(テーブル設計) → バックエンド → テスト → レビュー |
| エンジン級アルゴリズム（複式記帳 / 給与 / MRP） | pipeline + TDD | Lead → 業務エンジン専門家(設計) → テスト(境界ケース先行) → レビュー |
| フロントエンドページ（Flutter / HarmonyOS 並行） | fan-out | Lead → フロントエンド×2 + バックエンド(API 整合) 並行 → Lead が集約 |
| モジュール横断データフロー（購買→在庫→買掛など） | pipeline | Lead → アーキテクト → バックエンド → テスト → レビュー |
| マイクロサービス分割 / 大規模リファクタリング | supervisor | Lead ↔ アーキテクト + バックエンド + レビュー の多ラウンド |
| セキュリティ / 性能の専門対応 | 単線深掘り | Lead → セキュリティ/DevOps エンジニア → レビュー |
| バグ修正（単一ファイル / 1-2 行） | チームに入れない | Lead が直接処理、または 1 agent で完了 |
| 3 ブランチ差異 / バージョンリリース | pipeline | Lead → バージョンコーディネーター → テスト(ブランチ間回帰) → レビュー |

### 3.4 品質ゲート（コミット前必須、レビュアーが管理）

```
phpunit            # 137 テスト / 805 アサーション全緑、新規ケースは変更とともにコミット
phpstan            # baseline 外への新規問題は不可
php-cs-fixer       # --dry-run 合格
composer audit     # 高リスク依存関係の脆弱性なし
```

データベースに関わる変更は必ずアーキテクトを通過（163 表、schema は database/install.sql が唯一の事実源）。フロントエンドに関わる変更は Flutter の `flutter analyze` 0 error / 0 warning を必ず実行。

## 4. チーム規模の推奨

| 作業形態 | 推奨規模 | 説明 |
|----------|----------|------|
| 日常メンテナンス / 小修正 | 1-2 人 | Lead が直接処理し、過度な編成を避ける |
| 単一モジュールのイテレーション | 3 人 | Lead + バックエンド + テスト |
| モジュール横断機能 | 4-5 人 | Lead + アーキテクト + バックエンド + テスト + レビュー |
| フロントエンド双端並行 | 4-5 人 | Lead + Flutter + HarmonyOS + バックエンド(API) + テスト |
| エンジン級 / 複雑なリファクタリング | 5-7 人 | 上記全量 + 業務エンジン専門家またはセキュリティ/DevOps |

> `.claude-flow/config.yaml`（`maxAgents: 15`、`hierarchical-mesh`、`consensus` 調整戦略）と互換。単一タスクの占有が上限を超えないこと。

## 5. 導入ステップ

1. **ロール定義の補充**: `.claude/agents/` には planner / sparc / testing / swarm / consensus が既にあり、`business-engineer`、`frontend-flutter`、`frontend-harmonyos`、`researcher`、`edition-coordinator` の 5 定義が不足。既存の YAML/MD 形式に合わせて各 1 ファイル追加すればマウント完了；
2. **ルーティングの固定**: §3.3 ルーティング表を `.claude-flow/hooks` の routing ロジックに書き込み、`UserPromptSubmit` フックが自動でタスクを対応ロールに割り当てるようにする；
3. **記憶のドメイン分け**: `.claude-flow` は `agentScopes`（`defaultScope: project`）を有効化済み。`backend / frontend / ops / security` の 4 ドメインで保存することを推奨し、財務エンジンのコンテキストがフロントエンドタスクを汚染しないようにする；
4. **パイロット運用**: モジュール横断タスク（DMS 深化や BI ダッシュボードのイテレーションなど）を 1 つ選び、§3.3 ルーティングでフル 1 ラウンド実行し、メッセージチェーンとゲートを検証してから展開する。
