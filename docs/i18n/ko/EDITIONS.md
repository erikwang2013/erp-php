| 업무 모듈 | 6(계획값) | 6(계획값) | 19 <!-- stats:modules=19 --> |

> **통계 기준**: 저장소는 현재 풀 버전(Full) 한 벌의 코드만 구현합니다. Lite/Standard 열은 제품 계획값이며(코드베이스에 해당 브랜치 없음),
> doc-stats 검증에 참여하지 않습니다. Full 열의 숫자는 `scripts/doc-stats.sh`가 실측한 값(163 테이블 / 123 컨트롤러 / 19 업무 모듈)으로,
> `docs/FUNCTIONS.md` 부록의 기준과 일치합니다.

## 브랜치 전략(2026-08부터)

> 이 문서는 저장소 현재 버전의 브랜치 규약에 해당하며, `lite` / `standard` / `full` 3개 브랜치에 적용됩니다.

- **`main`은 유일한 개발 소스**: 모든 기능 개발, 결함 수정, 의존성 업그레이드는 반드시 `main`으로 병합합니다.
- **버전 브랜치는 릴리스 시에만 cherry-pick**: `lite` / `standard` / `full`은 더 이상 독립 개발 라인으로 일상 커밋을 받지 않으며,
  릴리스 시에만 버전 엔지니어가 `main`에서 해당 기능을 cherry-pick(또는 필요 시 전체 병합 1회)하고,
  브랜치에 각자의 트리밍 의도를 보존합니다(모듈 차이는 위 기능 비교표 참고).
- **트리밍 원칙**: 버전 브랜치 = main의 부분 집합. main 내용을 병합/이식할 때 충돌이 버전 트리밍 로직
  (예: EDITIONS.md의 모듈 차이, 라우트 트리밍)에 걸리면 브랜치의 트리밍 의도를 보존하고, 무관한 코드는 모두 main 버전을 기준으로 합니다.
- **검증**: 버전 브랜치 병합 후 `php -l` 전체 문법 검사를 통과해야 하며, 트리밍으로 적용 불가한 테스트는 건너뛰고 이유를 기록할 수 있습니다.
- **릴리스**: 버전 브랜치의 병합/이식은 버전 엔지니어가 수행하고 merge commit을 제출합니다. `main`의 커밋은 Lead가 통일적으로 수행합니다.
