## 适用场景

| 版本 | 推荐场景 |
|------|---------|
| **Lite** | 中小型商贸企业，以进销存+基础财务为核心，不需要审批流程和扩展模块 |
| **Standard** | 同等功能规模，精简数据表设计，适合定制化开发基础 |

## 分支策略（2026-08 起）

> 本文档对应仓库当前版本分支约定，适用于 `lite` / `standard` / `full` 三分支。

- **`main` 是唯一开发源**：所有功能开发、缺陷修复、依赖升级一律合入 `main`。
- **版本分支仅随发版 cherry-pick**：`lite` / `standard` / `full` 不再作为独立开发线接收日常提交，
  仅在发版时由版本工程师从 `main` cherry-pick 对应功能（或按需做一次整体合并），
  并在分支上保留各自的裁剪意图（模块差异见上文功能对比表）。
- **裁剪原则**：版本分支 = main 的子集。合并/移植 main 内容时，若冲突落在版本裁剪逻辑
  （如 EDITIONS.md 的模块差异、路由裁剪），保留分支的裁剪意图；无关代码一律以 main 版本为准。
- **验证**：版本分支合并后须通过 `php -l` 全量语法检查；因裁剪导致不适用的测试允许跳过并记录原因。
- **发布**：版本分支的合并/移植由版本工程师完成并提交 merge commit；`main` 的提交由 Lead 统一执行。
